Naming conventions命名規則

A variable or property name is [type][size]_[description].

変数名とプロパティ名は [型][サイズ]_[説明] の形にします。

cv_Vequilibrium

c complex · v column vector · description. More examples: lv_faultflag, im_solution, r_gain (scalar: no size letter).

c は複素数、v は列ベクトル、その後に説明が続きます。ほかの例: lv_faultflag、im_solution、r_gain（スカラーはサイズの文字なし）。

Type letter型の文字

ccomplex複素数rreal実数
llogical論理値sstring文字列
iindexインデックスncount個数
ffunction handle (a cell array when the variable is an array)関数ハンドル（変数が配列なら cell 配列）

Size letterサイズの文字

(none)（なし）scalarスカラー
vcolumn vector列ベクトル
rrow vector行ベクトル
mmatrix行列

Fixed prefixes決まった接頭辞

tab_
A table, whatever its size (tab_bus_data).表。サイズによらずこの接頭辞です（tab_bus_data）。
sct_
A struct, whatever its size (sct_stale); s alone means string.構造体。サイズによらずこの接頭辞です（sct_stale）。s だけなら文字列です。
a_
A cell array of GUILDA objects, named after the class (a_Bus, a_LocalController).GUILDA のオブジェクトの cell 配列で、クラス名を付けます（a_Bus、a_LocalController）。
Name-Value optionsName-Value オプション
UpperCamelCase as in MATLAB (Method, Tolerance, MaxIteration); see common options.MATLAB と同じ UpperCamelCase です（Method、Tolerance、MaxIteration）。共通のオプションを参照してください。
simulateFcn_
A private function in @PowerNetwork/private used only by the time simulation. A private function shared with other methods has no prefix.@PowerNetwork/private にあり、時間応答シミュレーションだけが使う private 関数です。ほかのメソッドと共有する private 関数には付けません。

Optional folders任意のフォルダ
GUILDA.addpath (run at startup) also adds _GUILDAverification and _GUILDAtextbook at the root when they exist, each folder only and not its subfolders, and GUILDA.rmpath removes them. Created on demand; safe to delete.必要に応じて作成されます。削除しても問題ありません。

Inside a class or package folder, a subfolder without an @ or + prefix is not on the path: for data or archived code only. A class folder keeps one method per file, @Class/<method>.m, wherever MATLAB allows it; a small model may be a single classdef file instead.クラスフォルダやパッケージフォルダの中で @ や + の接頭辞がないサブフォルダはパス外です。これらはデータやアーカイブしたコード専用です。クラスフォルダは、MATLAB が許す限り 1 ファイル 1 メソッド（@Class/<method>.m）にします。小さなモデルは単一の classdef ファイルでもかまいません。

The classdef file of a class folder keeps only the properties, the constructor, the get. / set. accessors, the Abstract declarations and the signatures of methods with attributes (Access, Static, Hidden), whose bodies are in their own files. A method with default attributes needs no declaration. A local function used only by the methods of the class goes in @Class/private/.クラスフォルダの classdef ファイルに残すのは、プロパティ、コンストラクター、get. / set. アクセサー、Abstract の宣言、属性（Access、Static、Hidden）付きメソッドのシグネチャだけです。属性付きメソッドの本体も、それぞれのファイルに置きます。既定の属性のメソッドは宣言不要です。そのクラスのメソッドだけが使うローカル関数は @Class/private/ に置きます。

There are two functionSignatures.json files because MATLAB applies a resources/functionSignatures.json only to the functions and classes of the folder that holds resources/, not to a subfolder that is a separate path entry such as _auxiliary/. GUILDA.update_keymap(Signature=true) writes both from the same entries, choosing the classes of _auxiliary/ by the location of their class folder.

functionSignatures.json が 2 つあるのは、MATLAB が resources/functionSignatures.json を、resources/ のあるフォルダの関数とクラスだけに使い、_auxiliary/ のように別のパスとして追加したサブフォルダには使わないためです。GUILDA.update_keymap(Signature=true) は同じ項目から両方を書き出し、_auxiliary/ のクラスはクラスフォルダの場所で選びます。

All outputs above except the functionSignatures.json files are listed in .gitignore. The model keys themselves are not generated: GUILDA.keymap reads them from the classes when first called, and GUILDA.update_keymap (also run at startup) reads them again.

Adding a modelモデルの追加

  1. Pick the base class and place. A package of _GUILDAobject (see Placement); one method per file in a class folder.基底クラスと場所を決めます。_GUILDAobject のパッケージに置きます（配置ルール）。クラスフォルダではメソッドごとに 1 ファイルです。
  2. Implement the contract below, and document it (Class Documentation).下の約束事を実装し、説明を書きます（クラスのドキュメント）。
  3. Register the key with GUILDA.update_keymap (or by starting GUILDA). Until then the key is rejected.GUILDA.update_keymap（または GUILDA の起動）でキーを登録します。登録するまでキーは拒否されます。
  4. Test it with validate and the test suite (see Testing).validate とテストスイートで確かめます（テストを参照）。

Rules for every modelすべてのモデルに共通の規則

  • The constructor is accessible only from the parent class (Access={?Bus}, {?Component}, {?PowerNetwork}), declared even when it only calls the superclass.
  • コンストラクタは親クラスからだけ呼べるようにします（Access={?Bus}、{?Component}、{?PowerNetwork}）。スーパークラスを呼ぶだけでも宣言します。
  • Model functions take (t, x, V, u, param, omega0), with V as [re; im]; they run at every evaluation, so their arguments blocks declare size and class only (hot path).
  • モデル関数の引数は (t, x, V, u, param, omega0) で、V は [re; im] です。評価のたびに呼ばれるため、arguments ブロックではサイズとクラスだけを宣言します（ホットパス）。
  • No model function receives the bus current; a component output depends only on x and V; the outputs of a global controller are 0 at its equilibrium; sv_u never uses the port names Vre, Vim, Ire, Iim.
  • モデル関数は母線電流を受け取りません。機器の出力は x と V だけで決まります。グローバル制御器の出力は平衡点で 0 です。sv_u にポート名 Vre、Vim、Ire、Iim を使いません。
  • Controller inputs connect by name; Xall and Yall observe all states or outputs (override set_inputs), X and Y are errors. A component has one "avr" or "local" slot (a "pss" under an AVR) and one "governor" slot, and they drive different inputs.
  • 制御器の入力は名前で接続します。Xall と Yall はすべての状態または出力を観測し（set_inputs を上書き）、X と Y はエラーです。機器には "avr" か "local" の枠（AVR の下に "pss"）と "governor" の枠が 1 つずつあり、両者は異なる入力を駆動します。
  • Every constructor argument of a controller is a column of tab_parameter.dynamics or a field of get_option, so that net.export can save it.
  • 制御器のコンストラクタ引数は、tab_parameter.dynamics の列か get_option のフィールドのどちらかにします。そうすると net.export で保存できます。
  • A branch defines key, header and get_admittance_matrix(obj, opt) with the options Status and Point. A network inherits from PowerNetwork in _GUILDAobject/+network/ and builds itself in its constructor, from CSV folders or in code.
  • ブランチは key、header と、オプション Status と Point を持つ get_admittance_matrix(obj, opt) を定義します。ネットワークは _GUILDAobject/+network/ で PowerNetwork を継承し、コンストラクタの中で CSV フォルダかコードから自身を組み立てます。

Testingテスト

  • s = comp.validate(false) (or con.validate) compares the contract, the source of each input, the residuals at the point and each Jacobian with finite differences; a broken model shows as FAIL.
  • s = comp.validate(false)（または con.validate）は、約束事、各入力の接続元、点での残差、各ヤコビアンと差分近似の差を比べます。壊れたモデルは FAIL と表示されます。
  • Then check the behaviour: a scenario without disturbances stays at the equilibrium, a fault and a trip complete with flag = 1, and the eigenvalues of net.get_sys(Format="ss") agree with an existing model the new one reduces to.
  • 次に挙動を確かめます。外乱のないシナリオでは平衡点にとどまり、事故と解列は flag = 1 で完了し、net.get_sys(Format="ss") の固有値は、新しいモデルが帰着する既存モデルと一致します。
  • Tests live in the submodule _GUILDAverification/+DebugScript. Add a %% section or a script test_I<issue>_<slug>.m, register a new script in test_categories.m, and list a slow test in test_levels.m. Each script also passes on its own with runtests.
  • テストはサブモジュール _GUILDAverification/+DebugScript にあります。%% セクションかスクリプト test_I<issue>_<slug>.m を追加し、新しいスクリプトは test_categories.m に登録し、時間のかかるテストは test_levels.m に記載します。各スクリプトは runtests で単独でも通るようにします。
  • Run DebugScript.run_all("Category", [...], "Level", "small") for the area you changed after each step, "medium" before merging a branch, and "large" (all tests) on the development branch and before a release.
  • 変更した領域のテストを、各段階のあとに DebugScript.run_all("Category", [...], "Level", "small") で、ブランチのマージ前に "medium" で、開発ブランチとリリース前に "large"（全テスト）で実行します。
