Git Workflow

Three kinds of branches: main for releases, a version branch for integration, and short-lived work branches. Branch names and commit messages share the same change types.

Pull requests

  1. SyncKeep the work branch up to date by merging the integration branch into it.
  2. Open PRInto the integration branch. Title uses the same <type>: <summary> format.
  3. Link IssueWrite Closes #<issue> in the description so the Issue is closed on merge.
  4. CheckCheck the items in Definition of Done.
  5. Merge & deleteAfter review, merge the pull request and delete the work branch.

Release

  1. PR into mainOpen a pull request from the integration branch into main.
  2. Tag vX.YAfter merging, tag the merge commit on main as vX.Y. Existing tags:v1.0v1.1v2.0v2.1
  3. Next branchCreate the next integration branch from main.

Do not

  • Direct commitsCommit directly to main.
  • Force-pushForce-push to main or the integration branch.
  • Generated / personal filesCommit generated files or personal settings (see Generated files).
  • Other prefixesCreate work branches with other prefixes such as dev/ or develop/.

Enforced by Claude Code hooks (.claude/settings.json, .claude/hooks/): Claude Code sessions in this repository are blocked from creating branches with other names, committing on main, versionX.Y or non-work branches, force-pushing or deleting main / versionX.Y, and editing generated files; a commit message that breaks the format is sent back for git commit --amend.
