Git WorkflowGit ワークフロー

Three kinds of branches hold the source: main for releases, a version branch for integration, short-lived work branches. A separate gh-pages branch holds the published documentation site. Branch names and commit messages share the same change types.

ソースは 3 種類のブランチで管理: リリース用の main、統合用のバージョンブランチ、短期間の作業ブランチ。別に gh-pages ブランチが公開用のドキュメントサイトを保持。ブランチ名とコミットメッセージは同じ変更種別。

Release of a versionバージョンのリリース

  1. Open a review pull requestレビュー用 PR の作成Open a pull request from the integration branch into main for review. Do not merge it on GitHub.レビュー用に、統合ブランチから main へのプルリクエストを作成。GitHub 上ではマージしない。
  2. release.shFrom a clean versionX.Y, run bash .claude/release/release.sh X.Y. It merges into main with --no-ff, removes the assistant config, commits chore: release vX.Y, and tags the merge commit vX.Y.クリーンな versionX.Y で bash .claude/release/release.sh X.Y を実行。--no-ff で main にマージ、アシスタント設定を削除、chore: release vX.Y をコミット、マージコミットに vX.Y のタグ。
  3. Push main and the tagmain とタグのプッシュCheck the result, then run the printed git push origin main vX.Y. GitHub marks the pull request as merged.結果を確認してから、表示された git push origin main vX.Y を実行。GitHub 上でプルリクエストはマージ済みに。
  4. Start the next integration branch次の統合ブランチの作成Run bash .claude/release/start-version.sh X.Y PREV: it creates the next versionX.Y from main and restores the assistant config from versionPREV.bash .claude/release/start-version.sh X.Y PREV を実行。main から次の versionX.Y を作成し、versionPREV からアシスタント設定を復元。

Assistant config never lands in main. .claude/, .codex/ and .github/copilot-instructions.md are tracked on the integration and work branches only, so users who clone main or run GUILDA.gitpull never get them.

release.sh removes them from the release merge and checks that main has none; start-version.sh brings them back. If the merge conflicts, the script aborts: merge main into versionX.Y, resolve the conflicts there, and run it again.

アシスタント設定は main に入れない。 .claude/、.codex/、.github/copilot-instructions.md は統合ブランチと作業ブランチでだけ管理。main のクローンや GUILDA.gitpull のユーザーには届かない。

release.sh がリリースマージからこれらを除き、main に残っていないことを確認。start-version.sh が復元。マージでコンフリクトが起きるとスクリプトは中断。その場合は main を versionX.Y にマージしてそこで解消し、再実行。

Publishing the documentationドキュメントの公開

  • Served by GitHub Pages at https://guilda-dev.github.io/guilda/ from the gh-pages branch.gh-pages ブランチから GitHub Pages が https://guilda-dev.github.io/guilda/ で配信。
  • The generated class reference is never committed to source branches, so a MATLAB command builds the site and commits the result to gh-pages. Nothing else updates the site.生成されたクラスリファレンスはソースブランチにコミットしないため、MATLAB コマンドがサイトをビルドし、結果を gh-pages にコミット。サイトの更新はこの方法のみ。
  1. Check out the source branchソースブランチのチェックアウトSwitch to main or versionX.Y with no uncommitted changes to tracked files.main または versionX.Y に切り替え、追跡対象ファイルに未コミットの変更がない状態に。
  2. Run publish_docpublish_doc の実行In MATLAB, run GUILDA.publish_doc(). It rebuilds the class reference and commits the site to gh-pages.MATLAB で GUILDA.publish_doc() を実行。クラスリファレンスを再構築し、サイトを gh-pages にコミット。
  3. Confirm the pushプッシュの承認Confirm the dialog to push gh-pages to origin.ダイアログで承認し、gh-pages を origin にプッシュ。
  4. Check the published site公開サイトの確認The site updates within a few minutes. Open it and check the changed pages.数分以内にサイトが更新。サイトを開いて変更したページを確認。

What the command doesコマンドの処理内容

  • Checks the checkoutチェックアウトの確認Refuses to run on any branch other than main or versionX.Y, or when tracked files have uncommitted changes.main と versionX.Y 以外のブランチ、または追跡対象ファイルに未コミットの変更がある場合は実行を拒否。
  • Rebuilds the class referenceクラスリファレンスの再構築Regenerates _GUILDAdoc/database/ from scratch and stops if any class export reports errors._GUILDAdoc/database/ を一から再生成。クラスのエクスポートでエラーが報告されれば停止。
  • Writes the siteサイトの書き出しIn a temporary Git worktree of gh-pages (created as an orphan branch the first time), writes _GUILDAdoc/, LICENSE, a root index.html that redirects to _GUILDAdoc/index.html, and an empty .nojekyll.gh-pages の一時的な Git ワークツリー（初回は orphan ブランチとして作成）に、_GUILDAdoc/、LICENSE、_GUILDAdoc/index.html へリダイレクトするルートの index.html、空の .nojekyll を書き出し。
  • Commits the siteサイトのコミットCommits docs: publish <branch>@<short-sha>, naming the source branch and commit. If nothing changed, it makes no commit.ソースのブランチとコミットを示す docs: publish <branch>@<short-sha> をコミット。変更がなければコミットなし。
  • Pushes gh-pagesgh-pages のプッシュAsks for confirmation, then pushes gh-pages to origin.確認を求めてから gh-pages を origin にプッシュ。

One-time setup. A repository admin sets Settings → Pages → Build and deployment to Deploy from a branch, with branch gh-pages and folder / (root).

The site shows the branch that was published last; the latest commit message on gh-pages names it.

サイトの内容は最後に公開したブランチ。どのブランチかは gh-pages の最新のコミットメッセージに記載。

Prohibited actions禁止事項

  • Direct commits to mainmain への直接コミットCommit directly to main.main への直接コミット。
  • Manual merges into mainmain への手動マージMerge or cherry-pick into main by hand or on GitHub; release with release.sh.手作業や GitHub 上での main へのマージ・チェリーピック。リリースは release.sh で。
  • Force-push to shared branches共有ブランチへの強制プッシュForce-push to main or the integration branch.main や統合ブランチへの強制プッシュ。
  • Committing generated or personal files自動生成ファイル・個人用ファイルのコミットCommit generated files or personal settings (see Generated files).自動生成ファイルや個人設定のコミット（自動生成ファイル を参照）。
  • Hand edits to gh-pagesgh-pages の手動編集Commit to, merge into, or merge from gh-pages by hand; publish with GUILDA.publish_doc.gh-pages への手動のコミット、gh-pages との間の手動マージ。公開は GUILDA.publish_doc で。
  • Other branch prefixesその他のブランチ接頭辞Create work branches with other prefixes such as dev/ or develop/.dev/ や develop/ など、他の接頭辞での作業ブランチの作成。

Enforced by Claude Code hooks (.claude/settings.json, .claude/hooks/): Claude Code sessions in this repository are blocked from creating branches with other names, committing on main, versionX.Y or non-work branches, force-pushing or deleting main / versionX.Y, running git merge or git cherry-pick on main (use release.sh), and editing generated files; a commit message that breaks the format is sent back for git commit --amend.Claude Code のフックによる強制（.claude/settings.json、.claude/hooks/）: このリポジトリの Claude Code セッションでは、他の名前のブランチの作成、main・versionX.Y・作業ブランチ以外でのコミット、main / versionX.Y の強制プッシュや削除、main 上での git merge や git cherry-pick の実行（release.sh を使用）、自動生成ファイルの編集をブロック。形式に従わないコミットメッセージは git commit --amend での修正に差し戻し。
