Git Workflow and Project ManagementGit ワークフローとプロジェクト管理

Four kinds of branches hold the source: main for releases, a version branch versionX.Y that receives snapshots, the development branch refactor/design-alignment, and short-lived work branches. A separate gh-pages branch holds the published class reference and developer pages; the rest of the documentation is the site repository checked out as the submodule _GUILDAdocPages. Branch names and commit messages share the same change types. All work is tracked in GitHub Issues: one Issue, one work branch, one pull request.

ソースは 4 種類のブランチで管理します。リリース用の main、スナップショットを受け取るバージョンブランチ versionX.Y、開発ブランチ refactor/design-alignment、短期間の作業ブランチです。別に gh-pages ブランチが公開用のクラスリファレンスと開発者向けのページを保持します。それ以外のドキュメントは、サブモジュール _GUILDAdocPages としてチェックアウトするサイトのリポジトリにあります。ブランチ名とコミットメッセージには同じ変更種別を使います。作業はすべて GitHub Issues で管理し、1 つの Issue に作業ブランチ 1 つとプルリクエスト 1 つが対応します。

Snapshot integrationスナップショットの統合

The development branch is copied into versionX.Y from time to time as one snapshot commit. The snapshot has the content of the development branch only: its history, which records the coding assistants, stays out of versionX.Y.

開発ブランチの内容は、ときどき 1 つのスナップショットコミットとして versionX.Y に取り込みます。スナップショットが持つのは開発ブランチの内容だけです。コーディングアシスタントの記録を含む開発ブランチの履歴は、versionX.Y に入りません。

  1. Update the local branchesローカルのブランチの更新Make sure the local refactor/design-alignment has the work to integrate, and that the local versionX.Y is not behind origin/versionX.Y (git fetch origin versionX.Y:versionX.Y). No worktree may have versionX.Y checked out.ローカルの refactor/design-alignment に統合する作業が入っていること、ローカルの versionX.Y が origin/versionX.Y より遅れていないこと（git fetch origin versionX.Y:versionX.Y）を確かめます。versionX.Y をチェックアウトしているワークツリーがあってはいけません。
  2. integrate.shFrom any checkout of the development branch, run bash .claude/release/integrate.sh X.Y. No branch switch is needed and the working tree is not touched.開発ブランチのチェックアウトで bash .claude/release/integrate.sh X.Y を実行します。ブランチの切り替えは不要で、作業ツリーも変わりません。
  3. Review and push確認とプッシュCheck the result with git show --stat versionX.Y, then the maintainer runs the printed git push origin versionX.Y. The script never pushes.git show --stat versionX.Y で結果を確かめてから、メンテナーが表示された git push origin versionX.Y を実行します。スクリプトはプッシュしません。

What integrate.sh doesintegrate.sh の処理内容

  • Checks the branchesブランチの確認Refuses to run when refactor/design-alignment or versionX.Y does not exist locally, when versionX.Y is behind origin/versionX.Y or checked out in a worktree, and when the development branch has not moved since the last snapshot.refactor/design-alignment や versionX.Y がローカルにない場合、versionX.Y が origin/versionX.Y より遅れている場合やワークツリーでチェックアウトされている場合、前回のスナップショットから開発ブランチが進んでいない場合は実行を拒否します。
  • Builds the snapshot treeスナップショットの内容の作成Reads the tree of the development branch into a temporary index, removes the excluded paths below, cuts every block between the marker lines # >>> dev-only … # <<< dev-only or <!-- dev-only:start --> … <!-- dev-only:end --> (markers included) out of the files that have them, and writes the result as a tree. Unmatched markers stop it. It stops if this tree equals the current versionX.Y.開発ブランチの内容を一時的なインデックスに読み込み、下の除外パスを取り除きます。さらに、目印の行 # >>> dev-only … # <<< dev-only または <!-- dev-only:start --> … <!-- dev-only:end --> で囲まれた部分を、目印の行ごとファイルから削り、その結果をツリーとして書き出します。目印の対応が取れていなければ停止します。このツリーが現在の versionX.Y と同じなら停止します。
  • Commits the snapshotスナップショットのコミットCreates one commit whose only parent is the current tip of versionX.Y, with the message chore: integrate refactor/design-alignment (<short-sha>) naming the development commit.現在の versionX.Y の先端だけを親とする 1 つのコミットを作ります。メッセージは開発ブランチのコミットを示す chore: integrate refactor/design-alignment (<short-sha>) です。
  • Checks the excluded paths除外パスの確認Lists the new commit's files, and searches its whole tree (submodules aside) for the names of the coding assistants. If an excluded path or any match is left, it shows them and fails without moving versionX.Y.新しいコミットのファイルを一覧し、ツリー全体（サブモジュールの中は除く）からコーディングアシスタントの名前を検索します。除外パスや一致する箇所が残っていれば、それを表示し、versionX.Y を動かさずに失敗します。
  • Moves the branchブランチの更新Fast-forwards versionX.Y to the new commit and prints the change summary and the push command.versionX.Y を新しいコミットへ早送りし、変更の概要とプッシュのコマンドを表示します。

Release of a versionバージョンのリリース

At a release, the maintainers merge versionX.Y into main with --no-ff, tag the merge commit vX.Y, and create the next versionX.Y from main.

リリースでは、メンテナーが versionX.Y を --no-ff で main にマージし、マージコミットに vX.Y のタグを付け、main から次の versionX.Y を作成します。

  1. Open a review pull requestレビュー用 PR の作成Open a pull request from versionX.Y into main for review. Do not merge it on GitHub.レビュー用に、versionX.Y から main へのプルリクエストを作成します。GitHub 上ではマージしません。
  2. release.shFrom a clean checkout of the development branch (versionX.Y has no .claude/), run bash .claude/release/release.sh X.Y. It merges versionX.Y into main with --no-ff, removes any excluded path from the merge result, commits chore: release vX.Y, tags the merge commit vX.Y, and switches back to the development branch.開発ブランチのクリーンなチェックアウトで（versionX.Y には .claude/ がありません）、bash .claude/release/release.sh X.Y を実行します。--no-ff で versionX.Y を main にマージし、マージ結果に除外パスがあれば取り除き、chore: release vX.Y をコミットし、マージコミットに vX.Y のタグを付けて、開発ブランチに戻ります。
  3. Push main and the tagmain とタグのプッシュCheck the result, then run the printed git push origin main vX.Y. GitHub marks the pull request as merged.結果を確認してから、表示された git push origin main vX.Y を実行します。GitHub 上でプルリクエストはマージ済みになります。
  4. Create the next version branch次のバージョンブランチの作成Run bash .claude/release/start-version.sh X.Y: it creates the next versionX.Y at main without switching to it. Push it with git push -u origin versionX.Y, make it the default branch on GitHub, and add snapshots with integrate.sh.bash .claude/release/start-version.sh X.Y を実行します。main の位置に次の versionX.Y を作成します（そのブランチには切り替えません）。git push -u origin versionX.Y でプッシュし、GitHub の既定のブランチに設定して、integrate.sh でスナップショットを追加します。

Assistant config never lands in versionX.Y or main. .claude/, .codex/ and .github/copilot-instructions.md are tracked on the development branch and the work branches only, so users who clone or pull versionX.Y or main never get them.

integrate.sh leaves them out of every snapshot; release.sh also removes any excluded path from the release merge and checks that main has none. If the release merge conflicts, the script aborts: resolve the conflict on the development branch, integrate again, and run it again.

アシスタント設定は versionX.Y にも main にも入れません。 .claude/、.codex/、.github/copilot-instructions.md は、開発ブランチと作業ブランチでだけ管理します。versionX.Y や main をクローンまたは pull したユーザーには届きません。

integrate.sh がすべてのスナップショットからこれらを除きます。release.sh もリリースマージから除外パスを取り除き、main に残っていないことを確認します。リリースマージでコンフリクトが起きると、スクリプトは中断します。その場合は開発ブランチで解消し、もう一度統合してから再実行します。

What the command doesコマンドの処理内容

  • Checks the checkoutチェックアウトの確認Refuses to run when tracked files have uncommitted changes (submodules aside) or files under _GUILDAdoc are untracked. Any branch can be published; the commit message names it.追跡対象ファイルに未コミットの変更がある場合（サブモジュールは除く）や、_GUILDAdoc の下に追跡されていないファイルがある場合は実行を拒否します。どのブランチからでも公開でき、コミットメッセージにそのブランチ名が残ります。

Writing rules for the pagesページの記述の規則

  • Timeless wording時点に依存しない記述Write for a reader who starts with the current GUILDA version. No wording that needs knowledge of older versions: “v3”, “v4”, “no longer”, “renamed”, “formerly”. History goes only in the Update Log data.Fine: format versions of external files, math symbols, and a deprecation rule (how a deprecated name keeps working) that does not narrate past versions.現在の GUILDA から使い始める読者に向けて記述します。過去のバージョンの知識を前提とする表現（「v3」「v4」「旧」「従来」「以前」「廃止」など）は使いません。経緯は Update Log のデータにだけ記載します。外部ファイルの形式のバージョン、数式の記号、過去を語らない非推奨の規則（非推奨の名前を動かし続ける仕組み）は使えます。
  • Prose style and bullets本文の文体と箇条書きJapanese prose is written in です・ます調, as natural Japanese that a person would write, not a word-for-word translation of the English: no “X: Y” in place of a sentence, no bullets that only list nouns. Headings, table headers, and labels stay noun phrases. Bullet points are still preferred, so the point is caught at a glance. English equally concise; bullets where the structure changes.日本語の本文は、です・ます調の自然な日本語で書きます。英語を直訳せず、文の代わりに「X: Y」と書いたり、名詞を並べただけの箇条書きにしたりしません。見出し、表の見出し、ラベルは名詞句のままにします。要点が一目でわかるよう、箇条書きを優先します。英語も同じく簡潔に書き、構造が変わる箇所は箇条書きにします。
  • Two-column layouts2 列のレイアウトIf a two-column block wraps into many lines, first turn it into bullets; if still too long, use one column with the items stacked.改行の多い 2 列のブロックは、まず箇条書きにします。それでも長ければ 1 列にして項目を縦に並べます。
  • Headings that name their subject対象を明示する見出しHeadings and labels (TOC, table headers, step labels) name what they are about, e.g. “Identifying objects (tags)”, not a bare “Identity:”; terseness is for body text.見出し・ラベル（目次、表の見出し、ステップのラベル）では、何についての項目かを明示します。例: 「識別：」ではなく「オブジェクトの識別（タグ）」とします。簡潔さは本文に適用します。
  • Same structure in both languages両言語で同じ構造English and Japanese have the same blocks, bullets, and order.英語と日本語で、ブロック、箇条書き、順序をそろえます。

The Update Log is for users of GUILDA, not for developers. It lists what a user can see: new models, new features or analyses, and bug fixes that change results or behaviour. The For Developer tab shows the newest four entries; updatelog.html lists all, newest first.

Update Log は GUILDA の利用者向けです（開発者向けではありません）。対象は、新しいモデル、新しい機能・解析、結果や動作が変わるバグ修正など、利用者から見える変更です。For Developer タブに最新 4 件、updatelog.html に全件を新しい順に表示します。
