Git Workflow

GUILDA uses three kinds of branches: main for releases, a version branch for integration, and short-lived work branches. Branch names and commit messages share the same set of change types.

Branch names

Work branches are named <type>/<issue>-<slug>.

TypeUse forExample
featureNew functions, classes, or modelsfeature/42-grid-forming-inverter

  • <issue> is the GitHub Issue number. Create the Issue first.
  • <slug> is a short English summary in lowercase words joined by hyphens (a-z, 0-9, -).
  • Keep the whole name under about 50 characters.

Commit messages

Write the first line as <type>: <summary>.

TypeUse forMatching branch type
featNew functions, classes, or modelsfeature
fixBug fixesfix
refactorRestructuring without changing behaviorrefactor
docsHelp comments, documentation pages, tutorialsdocs
testTest and debug scriptstest
choreSettings, .gitignore, file moves, and other maintenanceany
  • The summary is in English, starts with a lowercase verb in the imperative (add, fix, remove), and has no trailing period.
  • Keep the first line within 72 characters. Add a body after a blank line when the reason for the change is not obvious.
  • One commit contains one logical change. A branch may mix types, for example feat: and docs: commits on a feature/ branch.
fix: use bus index instead of position in OPF constraints

The constraint matrix was built from the position in a_Bus, which
breaks after a bus is removed. Refs #51.

Pull requests

  1. Keep the work branch up to date by merging the integration branch into it.
  2. Open a pull request into the integration branch. Use the same <type>: <summary> format for the title.
  3. Write Closes #<issue> in the description so the Issue is closed on merge.
  4. Check the items in Definition of Done.
  5. After review, merge the pull request and delete the work branch.

Release

  1. Open a pull request from the integration branch into main.
  2. After merging, tag the merge commit on main as vX.Y (existing tags: v1.0, v1.1, v2.0, v2.1).
  3. Create the next integration branch from main.

Do not

  • Commit directly to main.
  • Force-push to main or the integration branch.
  • Commit generated files or personal settings (see Generated files).
  • Create work branches with other prefixes such as dev/ or develop/.
