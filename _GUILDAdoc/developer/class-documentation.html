Class Documentation

Write <@Tag> comments next to the MATLAB code. GUILDA.doc combines them with what the code itself declares and builds the Reference pages.

How it works

Nobody edits the Reference by hand. It is rebuilt from the source every time the source changes.

Where comments go

Each numbered comment ends up in the matching place on the class page. Everything without a number is read from the code.

Class

% lines directly below classdef. A blank line or a %% section line ends the block.

Property

% lines directly above the declaration. A trailing % text on the same line is used only when there is no block above.

Method

% lines directly after the function line: in @Class/<method>.m, in a function inside the classdef, or in @Class/private/<method>.m. For an abstract method or a signature-only declaration, put the block above the signature in the methods block.

Argument

A trailing % text (or a comment line above it) inside the arguments block becomes that argument's description.

Which tags

Write one tag per line as % <@Tag> value. A value can continue on the following % lines until the next tag.

RequiredRecommendedOptional
Class Summary DescRoleConstructor NotesSeeAlsoSinceDeprecated
Public property Summary Unit (physical quantities)
Role		 DescTypeSizeDefaultConstraintsNotesSeeAlsoSinceDeprecated
Public method Summary DescParametersReturns SignaturesCallsExamplesNotesThrowsSeeAlsoSinceDeprecated

Private, protected and hidden members do not need tags. Write them when they help the next developer.

Older names are still read: Abst → Summary, Description → Desc, varargin → Parameters, varargout → Returns, DetailsCode → Notes, Example → Examples, Seealso → SeeAlso. Use the new names in new code.

Value formats

Summary

One line, one English sentence. For a method, start with a verb: Calculate the power flow. It is what the tables and search show.

Plain text
Desc, Role, Constructor, Unit, Notes, Throws, Since, Deprecated …

Free text. Desc, Constructor and Notes support Markdown: - lists, 1. lists, `code`, **bold**, # headings, [links](url) and fenced code blocks. Text art drawn with box characters is kept exactly as written.

JSON lists
Signatures, Examples, SeeAlso

A JSON string or an array of strings: ["PowerNetwork", "Bus"]. SeeAlso entries that name a class become links.

JSON objects
Parameters, Returns, Calls

A JSON array of objects. It must start with [; MATLAB arrays and cell arrays are not accepted.

% <@Parameters>
% [{"Name": "r_gain", "Unit": "pu", "Description": "Controller gain."}]
% <@Returns>
% [{"Name": "flag", "Description": "true when the solver converged."}]
% <@Calls>
% [{"Class": "PowerFlowCalculation", "Method": "solve", "Condition": ""}]

Parameters fields: Name, Type, Unit, Description, Required, Default, Constraints. Returns fields: Name, Type, Unit, Description. Calls fields: Class, Method (both required), Condition (blank means always).

Untagged text

Text before the first tag is not lost: its first line is used as Summary and the rest as Desc, unless those tags exist. Prefer writing the tags.

Don't repeat the code

The exporter reads property declarations and arguments blocks. Write the fact once, in the code, where MATLAB also checks it.

Duplicated 
% <@Summary> Base power.
% <@Type> double
% <@Size> 1x1
% <@Default> 100
% <@Unit> MVA
r_Sbase (1,1) double = 100
Written once 
% <@Summary> Base power.
% <@Unit> MVA
r_Sbase (1,1) double = 100
Properties

Use <@Type>, <@Size>, <@Default> and <@Constraints> only when the declaration cannot say it, for example an untyped property that holds a PowerFlowCalculation. A tag wins over the declaration on the page.

Methods

Give inputs an arguments block with size, class, validators and defaults. In <@Parameters>, write only what the block cannot say (Description, Unit). Entries are matched by Name.

Signatures

Built automatically from the function line and the arguments block, e.g. [tab_PFsol, flag, output] = calculate_powerflow(obj, mode, Name=Value). Add <@Signatures> only for extra call forms.

What the exporter checks

Every run prints a line per class and a summary. Problems are reported where the member is defined, not again for each subclass.

  • Errors
    • Invalid JSON in a structured tag (Signatures, Examples, SeeAlso, Parameters, Returns, Calls).
    • A Calls entry without both Class and Method.

    With GUILDA.doc("strict", true) the run fails when there are errors.

  • Warnings
    • A class, or its own public non-hidden method, has no Summary or Desc.
    • An unknown tag, or the same tag twice (the last value is used).
    • A <@Parameters> name that is not an input of the method.
    • A method declared in the classdef with no implementation file.
  • Coverage

    Documented / total for classes, public methods and public properties. It is shown at the top of the Reference tab, and undocumented classes get a no docs marker there.

Keeping it up to date

  1. Edit the sourceAdd or change classes and comments under _GUILDAsystem or _GUILDAobject.
  2. Run GUILDA.docIt rebuilds the database only when needed, then opens the pages. A rebuild takes seconds.
  3. Check the outputRead the warnings in the Command Window and look at your class page.
update="auto" (default)

Rebuild when the database is missing, or when any file or folder under the two source folders, or the exporter itself, is newer than database/list_Classes.js. Folder times also catch deleted and renamed files.

update=true / false

Always or never rebuild. "always" and "never" work too.

Generated files

_GUILDAdoc/database/list_Classes.js (index with the schema, coverage and validation results) and one database/GUILDAsystem|GUILDAobject/<Class>.js per class, loaded on demand. Both use schema version 4. They are generated, not tracked by git: never edit them, rebuild instead.

Other options

GUILDA.doc("class", "PowerNetwork") opens one class page. "open", false only rebuilds.
