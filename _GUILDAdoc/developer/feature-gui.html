GUI Feature DesignGUI 機能の設計

obj.launch_gui() shows any model (network, bus, branch, component, controller) in a window: a breadcrumb from the root, its class and tag, a Docs button, the stale state, the children in a searchable table, editable parameter tables and the equilibrium tables. The tables come from the six abstract classes, and the meaning of the parameters and the model is in the class reference that the Docs button opens, so a new model class needs no GUI code. GUILDA.launch_gui puts these GUIs together in one app (see The GUILDA app).

obj.launch_gui() は、ネットワーク、母線、ブランチ、機器、制御器のどのモデルでもウィンドウに表示します。画面には、ルートからのパンくず、クラスとタグ、Docs ボタン、stale 状態、検索できる子の表、編集できるパラメータの表、平衡点の表が並びます。表は 6 つの抽象クラスが作り、パラメータやモデルの説明は Docs ボタンで開くクラスのリファレンスに載っています。そのため、新しいモデルクラスを作っても GUI 用のコードを書く必要はありません。GUILDA.launch_gui は、これらの GUI を 1 つのアプリにまとめます（GUILDA のアプリを参照）。

What the feature does and how to call it機能の目的と呼び出し方

net = network.IEEE14bus();
h = net.a_Bus{1}.launch_gui();    % a new uifigure
h = net.launch_gui(h_container);  % fills h_container
h = net.launch_gui(History=hist); % runs and logs the actions in hist (a HistoryGUILDA)
  • launch_gui(obj, h_container, History=hist): public method of LayerPackage, so every network, bus, branch, component, local and global controller, and scenario has it.
  • No container (or []): a new uifigure named after the class and the tag.
  • A container: the GUI fills a uifigure, uipanel, uitab or uigridlayout whose figure was made by uifigure(); the layout follows the size of the container.
  • Output: h, a DrawerModelGUI. h.a_target is the model shown, h.h_container the container; h.render(model) shows another model in the same place.
  • The GUI adds and removes models and writes parameters, each as a line of MATLAB code run by History (a HistoryGUILDA; see Adding and removing models). The default history prints each >> code in the Command Window, and h.history.get_script() returns the actions as a script. It runs no analysis (initialize, power flow, ...).
  • A figure made by figure() is rejected, also through a panel inside it (GUILDA:DrawerModelGUI:NotUIContainer):
    • the GUI is built from UI components (uigridlayout, uibutton, uihyperlink, uitable, uihtml, uialert), which belong in a uifigure;
    • before R2025a a figure() does not take them; since R2025a it does, so the check reads the dynamic property isUIFigure, which only uifigure() adds. The same containers work in every release.
  • launch_gui(obj, h_container, History=hist) は LayerPackage の public メソッドです。そのため、ネットワーク、母線、ブランチ、機器、ローカル制御器、グローバル制御器、シナリオのどれからでも呼べます。
  • コンテナを渡さない場合（[] を渡した場合も同じ）は、クラス名とタグを名前にした uifigure を新しく開きます。
  • コンテナを渡すと、その中に GUI を展開します。渡せるのは、uifigure() で作った図に属する uifigure、uipanel、uitab、uigridlayout です。レイアウトはコンテナの大きさに合わせて変わります。
  • 戻り値の h は DrawerModelGUI です。h.a_target で表示中のモデルを、h.h_container でコンテナを参照できます。h.render(model) を呼ぶと、同じ場所に別のモデルを表示します。
  • GUI はモデルの追加・削除とパラメータの書き込みを行います。どの操作も 1 行の MATLAB コードにして History（HistoryGUILDA）で実行します（モデルの追加と削除を参照）。既定の実行記録は、各 >> コード をコマンドウィンドウに表示します。h.history.get_script() は操作をスクリプトとして返します。解析（initialize、潮流計算など）は実行しません。
  • figure() で作った図には表示できません。その図の中のパネルを渡しても同じです（GUILDA:DrawerModelGUI:NotUIContainer）。理由は次のとおりです。
    • GUI は UI コンポーネント（uigridlayout、uibutton、uihyperlink、uitable、uihtml、uialert）で組み立てています。これらは uifigure に置くための部品です。
    • R2025a より前の figure() には、これらの部品を置けません。R2025a 以降は置けるので、uifigure() だけが追加する動的プロパティ isUIFigure を見て判定しています。こうすると、どのリリースでも同じコンテナが使えます。

Screen layout画面構成

  • Header: a band in the blue of the logo over a lime line.
    • Row 1, the breadcrumb: the models from the root to the model shown, joined by ›. Each of them but the model shown is a link; a click shows that model in the same container.
    • Row 2: the tag (bold), the class, the Docs button and the stale state. Docs runs GUILDA.doc("class", class(model)), which opens the reference page of the class. The stale state, from sct_stale, is Stale: none, or each stale tag with its first message and the number of the others, in warning colors.
  • Child table: the children of one kind at a time, in a compact table. The kinds come in the order Bus, Branch, Component, LocalController, GlobalController, Scenario (then any other model); the Parameter containers are left out.
    • A drop-down chooses the kind (Bus (14), Branch (20), ...), and a search field keeps the rows that contain its text in any column.
    • The columns come from DrawerTagPicker.element_table of the network: bus Tag, Type, Components; branch Tag, From, To, Class; component Tag, Class, Key; local controller Tag, Role, Class; global controller Tag, Class, Units; scenario Tag, Time, Description. A model outside a network gets Tag and Class.
    • A click on a row shows that model in the same container. The context menu of a row has Open in new window, which calls launch_gui(History=h.history) of that model, and Remove (see Adding and removing models).
    • The table of a kind is built when the kind is first shown, and the next render of the same model reuses it while the log has no new entry; the kind and the search text are kept too.
    • Above the table, the add buttons of the model (+ Bus, + Branch, + Controller, + Scenario, ...), in the color of their kind; the tooltip names the method.
  • Tabs, in this order:
    1. Parameter: a line that points to the Docs for the meaning of each parameter, then one panel with an editable table per container of a_Parameter, titled by its s_tag. A container of one row whose parameters are all scalars is a vertical table, one row per parameter with its full name and a column Value; two of them stand side by side. Any other container has one column per parameter; the columns fit their contents and the table scrolls sideways when they do not fit. No parameters. when there is none.
    2. the tables of the abstract class (Summary, Equilibrium; see Pages of each abstract class). The equilibrium tables are vertical: one variable per row.
  • ヘッダ: ロゴと同じ青の帯で、下にライムの線を引きます。
    • 1 行目はパンくずです。ルートから表示中のモデルまでを › でつなぎます。表示中のモデル以外はリンクになっていて、クリックするとそのモデルを同じコンテナに表示します。
    • 2 行目には、タグ（太字）、クラス、Docs ボタン、stale 状態が並びます。Docs を押すと GUILDA.doc("class", class(model)) が実行され、そのクラスのリファレンスが開きます。stale 状態は sct_stale をもとに表示します。古い層がなければ Stale: none と表示し、あれば stale のタグごとに最初のメッセージと残りの件数を警告色で示します。
  • 子の表: 子のモデルを種類ごとに 1 つずつ、小さな表で示します。種類の順は Bus、Branch、Component、LocalController、GlobalController、Scenario で、それ以外のモデルは最後です。Parameter のコンテナは表に入れません。
    • ドロップダウンで種類（Bus (14)、Branch (20) など）を選びます。検索欄に文字を入れると、どれかの列にその文字を含む行だけを残します。
    • 列は系統の DrawerTagPicker.element_table から取ります。母線は Tag、Type、Components、ブランチは Tag、From、To、Class、機器は Tag、Class、Key、ローカル制御器は Tag、Role、Class、グローバル制御器は Tag、Class、Units、シナリオは Tag、Time、Description です。系統の外のモデルでは Tag と Class だけです。
    • 行をクリックすると、そのモデルを同じコンテナに表示します。行のコンテキストメニューには、そのモデルの launch_gui(History=h.history) を実行する Open in new window と、Remove があります（モデルの追加と削除を参照）。
    • 種類の表は、その種類を初めて表示するときに作ります。同じモデルを描き直すときは、実行記録に新しい項目がなければ作った表を使い回します。選んだ種類と検索の文字も残ります。
    • 表の上には、そのモデルの追加ボタン（+ Bus、+ Branch、+ Controller、+ Scenario など）を種類の色で置きます。ツールチップにメソッドを示します。
  • タブ（この順）:
    1. Parameter: 先頭に、各パラメータの意味は Docs で確認するよう促す 1 行があります。その下に、a_Parameter のコンテナごとに編集できる表をパネルにして並べます。パネルの題は s_tag です。1 行だけで、すべてのパラメータがスカラーのコンテナは縦の表にします。1 つのパラメータが 1 行になり、名前を省略せずに示し、値は Value の列に入ります。縦の表は 2 つずつ横に並べます。それ以外のコンテナでは 1 つのパラメータが 1 列になり、列幅は内容に合わせ、収まらないときは横にスクロールします。コンテナがなければ No parameters. と表示します。
    2. 続いて、抽象クラスが作る表のタブ（Summary、Equilibrium）が並びます。詳しくは抽象クラスごとのページを参照してください。平衡点の表では、1 つの変数が 1 行になり、縦に並びます。

Theme and colorsテーマと配色

  • A fixed light theme based on the GUILDA logo. The colors do not follow the MATLAB theme: under a dark theme, colors set on some components and left to the theme on others would leave parts unreadable.
  • All colors are in one place, _GUILDAsystem/+tools/gui_palette.m (shared with HistoryGUILDA and DrawerOptionDialog), which returns them as a struct of RGB triplets. Every part sets its colors (background, text, table rows) from it.
  • A new uifigure made by launch_gui() gets Theme="light" where uifigure has a Theme property.
  • The theme of the figure of a given container is left as it is; the GUI does not change the app it is embedded in.
  • GUILDA のロゴの色をもとにした、固定のライトテーマを使います。MATLAB のテーマには合わせません。ダークテーマで一部の部品だけ色を指定し、残りをテーマに任せると、読めない箇所が出るためです。
  • 色はすべて _GUILDAsystem/+tools/gui_palette.m にまとめています（HistoryGUILDA と DrawerOptionDialog と共有）。この関数は色を RGB の 3 要素で持つ構造体を返し、各部品は背景や文字、表の行の色をそこから取ります。
  • launch_gui() が新しく作る uifigure には、Theme プロパティがあれば Theme="light" を設定します。
  • 渡されたコンテナの図のテーマは変えません。埋め込み先のアプリには手を加えない方針です。

Pages of each abstract class抽象クラスごとのページ

Each abstract class puts its own pages first, then those of PowerSystemModel, whose base implementation returns none. Every page is a read-only table. Values in the tables are as of the last net.initialize(); the header shows whether they are stale.

各抽象クラスは自分のページを先に置き、その後ろに PowerSystemModel のページを続けます（基底の実装は空です）。ページはどれも編集できない表です。表の値は最後に net.initialize() を実行した時点の値で、古くなっているかどうかはヘッダでわかります。

What a model class writes for the GUIモデルクラスが GUI のために書くもの

Nothing. A class made from an abstract class (a new generator, load, controller, branch, network) adds no method or property for the GUI:

  • Tables: from the properties of the abstract class (sv_x, sv_u, the equilibrium, a_Parameter), which every model already fills.
  • Meaning of the parameters and the model: in the class reference, made from the class help as in Class Documentation; the Docs button opens it.

何も書く必要はありません。抽象クラスから作るクラス（新しい発電機、負荷、制御器、ブランチ、ネットワーク）に、GUI のためのメソッドやプロパティを足すことはありません。

  • 表: 抽象クラスのプロパティ（sv_x、sv_u、平衡点、a_Parameter）から作ります。これらはどのモデルにも必ず設定されています。
  • パラメータとモデルの説明: クラスのリファレンスに載せます。リファレンスは、クラスのドキュメントに沿って書いたクラスの help から作られ、Docs ボタンで開きます。

Editing parametersパラメータの編集

  • An edited cell is written at once, as code run by the history (edit_parameter); there is no Apply button. Each changed variable of the table is one line on tab_parameter of the model, from the root variable, e.g. net.a_Bus{1}.tab_parameter.powerflow.V = 1.02;. In a table of several rows (a global controller) only the changed row is written (...dynamics.kP(2) = 120;), and a column whose class changed is written whole.
  • Parameter does the rest, as for an edit from the command line: it checks the class, names, height and row names, logs only the changed values, and marks the layers stale (see Class Design: Handling of model edits). The GUI then refreshes the stale state of the header.
  • On an error, the table goes back to the stored values and an alert shows the message; nothing is stored, and the entry stays in the log as failed. A text that is not a value of the column (letters in a number column, for example) is refused the same way, without running anything; a column of another class (a cell, for example) is shown but cannot be edited.
  • The equilibrium tables are not editable and keep the values of the last initialize; the GUI does not run it. Run net.initialize() from the command line, then h.render() to show the new values.
  • セルを編集すると、すぐにコードにして実行記録で実行します（edit_parameter）。適用ボタンはありません。表の変わった変数ごとに、ルートの変数からモデルの tab_parameter へ書く 1 行を作ります。例: net.a_Bus{1}.tab_parameter.powerflow.V = 1.02;。行が複数ある表（グローバル制御器）では変わった行だけを書き（...dynamics.kP(2) = 120;）、クラスが変わった列は列全体を書きます。
  • その後の処理は、コマンドラインから編集したときと同じく Parameter が行います。クラス、名前、高さ、行名を検査し、変わった値だけをログに残し、層の stale に反映します（クラス設計: モデル編集の扱いを参照）。GUI はそれを受けて、ヘッダの stale 状態を更新します。
  • エラーになったときは、表を保存済みの値に戻し、アラートでメッセージを表示します。この場合は何も保存せず、記録には失敗として残ります。列の値にならない文字（数値の列の英字など）も、何も実行せずに同じく拒否します。それ以外のクラスの列（cell など）は表示だけで、編集できません。
  • 平衡点の表は編集できません。値は最後に initialize を実行した時点の値です。GUI からは initialize を実行しないので、新しい値を見るにはコマンドラインで net.initialize() を実行し、h.render() で表示し直します。

The code reaches a model from the root variable of the history through the lists and indices of its parents: net.a_Bus{3}.a_Component{1}.a_LocalController{1}, net.a_Branch{2}, net.a_Scenario{1}.   • Add. A button calls DrawerOptionDialog.ask(fig, "<Class>.<method>", Object=<expression>, History=h.history). With History the form evaluates its choices on the object, so a tag input is a list of the tags (several can be selected: add_branch takes the two end buses from the list). When the form returns code, it is run.
  • Remove. The context menu of a row of the child table has Remove, which runs the remove_* method of the parent with the tag of the row: remove_bus, remove_branch, remove_global_controller, remove_scenario, remove_component or remove_local_controller (on the component, with RemoveNested=true when a controller is nested in it). The rows of the Events, Offsets and Inputs tables of a Scenario have Remove event, which runs remove_event with the tags of the row (or of the selected rows); a fault, trip or opening has two rows per target, and removing one row removes the whole event. A visible figure asks first (uiconfirm); a hidden figure or matlab -batch has nobody to ask and runs it.
  • After an action the GUI is drawn again (also after a failed one, which may have changed part of a handle model) and, when it succeeded, the event ModelChanged is notified, so a host (the network diagram of GUILDA.launch_gui) can redraw. A failed action shows its error in an alert (the HiddenAlert warning on a hidden figure) and stays in the log as failed.
  • Script. h.history.get_script() holds the done entries. It does not create the root variable: a history made by launch_gui holds net only as a variable, so the script runs where net exists. To get a script that starts from nothing, create the network through the history first (hist.run("Model building", "New network", "net = PowerNetwork();")) and pass History=hist.
  • ルートの変数からのコード: どの操作も、h.history.run("Model building", ラベル, コード) が実行する 1 行のコードです。コードは、実行記録のルートの変数から、親のリストと番号をたどってモデルに届きます。例: net.a_Bus{3}.a_Component{1}.a_LocalController{1}、net.a_Branch{2}、net.a_Scenario{1}。ルートの変数は、ネットワークなら net、それ以外はルートのクラスの名前（bus、branch、comp、con、gcon）です。実行記録にその変数がなければ launch_gui が設定します。変数が別のモデルを持つ実行記録は拒否します（GUILDA:DrawerModelGUI:OtherRoot）。
  • 追加: ボタンは DrawerOptionDialog.ask(fig, "<クラス>.<メソッド>", Object=<式>, History=h.history) を呼びます。History を渡すと、フォームは選択肢をそのオブジェクトで評価するので、タグの入力はタグの一覧になります（複数選べます。add_branch の両端の母線は一覧から 2 つ選びます）。フォームがコードを返したら、それを実行します。
  • 削除: 子の表の行のコンテキストメニューの Remove は、行のタグを渡して親の remove_* を実行します。remove_bus、remove_branch、remove_global_controller、remove_scenario、remove_component、remove_local_controller（機器に対して実行し、入れ子の制御器があれば RemoveNested=true を付けます）のどれかです。Scenario の Events、Offsets、Inputs の表の行には Remove event があり、その行（または選択した行）のタグで remove_event を実行します。故障、解列、開放は対象ごとに 2 行を持ち、1 行を選んで削除するとイベント全体が消えます。表示中の図では先に確認します（uiconfirm）。非表示の図と matlab -batch では確認する相手がいないので、そのまま実行します。
  • 操作の後: GUI を描き直します（失敗した場合も描き直します。失敗した実行がハンドルのモデルの一部を変えている場合があるためです）。成功したときはイベント ModelChanged を通知するので、ホスト（GUILDA.launch_gui のネットワーク図）が描き直せます。失敗した操作はアラートでエラーを表示し（非表示の図では警告 HiddenAlert）、記録には失敗として残ります。
  • スクリプト: h.history.get_script() は成功した記録を返します。ルートの変数を作る行は含みません。launch_gui が作った実行記録は net を変数として持つだけなので、スクリプトは net がある場所で実行します。何もない状態から始まるスクリプトにするには、先にネットワークを実行記録で作り（hist.run("Model building", "New network", "net = PowerNetwork();")）、History=hist を渡します。

DrawerModelGUI and renderDrawerModelGUI と render

  • DrawerModelGUI(a_target, h_container, f_model, history) (an _auxiliary class): follows the parents to the root and checks the root variable of the history (or sets it), checks the container (or opens a light-themed uifigure), keeps them, f_model and the history (read-only h.history), and calls render(a_target).
  • render(a_target) (public): draws the whole GUI of a model. The breadcrumb, the child table and an embedding app call it; render() draws the shown model again.
  • It removes only what it drew before: the children of the container with Tag "DrawerModelGUI", and the context menus of their child table and event tables (owned by the figure). Other components of the container stay. In a uigridlayout container the new grid takes the Layout (row and column) of the old one.
  • Then it follows the parents up to the root for the breadcrumb and builds a 2 × 2 uigridlayout (Tag "DrawerModelGUI"): the header across the top, the add buttons over the child table (300 px; as wide as the buttons without children) and the tab group; without children and add buttons the tab group spans both columns. In a uifigure container it also sets the window name.
  • Nothing is cached: each render reads the model again, so it shows the current state.
  • DrawerModelGUI(a_target, h_container, f_model, history)（_auxiliary のクラス）: 親をたどってルートを求め、実行記録のルートの変数を確かめ（なければ設定し）、コンテナを検査します（コンテナがなければライトテーマの uifigure を作ります）。これらと f_model、実行記録（読み取り専用の h.history）を保持してから render(a_target) を実行します。
  • render(a_target)（public）: モデルの GUI 全体を描きます。パンくず、子の表、埋め込み先のアプリから呼ばれます。引数なしの render() は、表示中のモデルを描き直します。
  • 最初に、前回自分が描いた部品だけを削除します。対象は、コンテナの子のうち Tag が "DrawerModelGUI" の部品と、子の表とイベントの表のコンテキストメニュー（図が所有）です。コンテナにある他の部品はそのまま残ります。uigridlayout のコンテナでは、新しいグリッドが古いグリッドの Layout（行と列）を引き継ぎます。
  • 次に、親をたどってルートまでのパンくずを求め、2 × 2 の uigridlayout（Tag は "DrawerModelGUI"）を作ります。上段にヘッダを、下段に追加ボタンと子の表（300 px。子がなければボタンの幅）とタブグループを置きます。子も追加ボタンもなければ、タブグループが 2 列分を使います。uifigure のコンテナでは、ウィンドウ名も設定します。
  • キャッシュは持ちません。render のたびにモデルを読み直すので、常に現在の状態が表示されます。

Why f_modelf_model を使う理由

  • parent, children and gui_content are protected members of the model. DrawerModelGUI is outside the model hierarchy, so it cannot read them.
  • launch_gui makes an anonymous function inside a method of LayerPackage; it keeps the access of the place where it was made: 
    f_model = @(o) struct("parent", {o.parent}, "children", {o.children}, "pages", {o.gui_content()});
  • DrawerModelGUI keeps it in a private property and calls it for every model it shows, and for each parent on the way to the root. The members stay protected; no public accessor is added for the GUI.
  • parent、children、gui_content はモデルの protected メンバーです。DrawerModelGUI はモデルの継承階層の外にあるので、これらを直接は読めません。
  • そこで launch_gui は、LayerPackage のメソッドの中で無名関数を作ります。無名関数は、作られた場所のアクセス権を持ち続けます。 
    f_model = @(o) struct("parent", {o.parent}, "children", {o.children}, "pages", {o.gui_content()});
  • DrawerModelGUI はこの関数を private プロパティに持ち、表示するモデルと、ルートまでの各親に対して呼び出します。これでメンバーは protected のままで済み、GUI のために public なアクセサーを足す必要もありません。

Run log and option forms実行記録とオプション入力

Three classes in _GUILDAsystem/_auxiliary serve the GUIs that run functions (GUILDA.launch_gui and the model and result GUIs): every action is a line of MATLAB code, HistoryGUILDA runs and records it, DrawerOptionDialog writes it from a form, and DrawerTagPicker lets the user choose a tag or a model key from a table.

_GUILDAsystem/_auxiliary の 3 つのクラスは、関数を実行する GUI（GUILDA.launch_gui、モデルや結果の GUI）が共通に使います。GUI の操作はすべて 1 行の MATLAB コードで表し、HistoryGUILDA がそれを実行して記録し、DrawerOptionDialog がフォームからそのコードを作ります。DrawerTagPicker は、タグやモデルキーを表から選ばせます。

h = HistoryGUILDA(Header="Built in the GUI");
h.attach_view(h_panel);                                   % the log view
s_code = DrawerOptionDialog.ask(fig, "PowerNetwork.calculate_powerflow", Object="net", Output="res_pf");
if s_code ~= ""
    [l_ok, s_detail] = h.run("Power flow", "Calculate", s_code);
end
h.export_script("session.m")                             % the done entries as a script

HistoryGUILDA: the run logHistoryGUILDA: 実行記録

  • run(s_group, s_label, s_code) evaluates the code string itself, in a workspace of the object; there is no separate callback. The exported script is therefore exactly what the GUI ran.
  • Variables assigned by the code stay for the next runs (res_pf after res_pf = net.calculate_powerflow();); set_variable and get_variable reach them from outside.
  • Each run is a row of tab_entry: Group, Label, Code, Status ("run", "done", "fail") and Detail (the first lines of the output captured by evalc, or the error message, with the elapsed time). An error is not rethrown, and the workspace stays as it was. The event Changed is notified when an entry starts and when it ends.
  • Entries are never removed: model edits accumulate. get_script writes the Header, then the "done" entries in the order they ran, as a %% <Group> section for each run of consecutive entries of one group, with % <Label> before each code. Failed entries stay in the log but not in the script.
  • Workspace: the code runs in a private function whose only variables are varargin and varargout. It unpacks the stored variables, runs the code with evalc and packs every variable back, so the code may use any other name. varargin and varargout cannot be variables of the log.
  • attach_view(h_container) draws a uilistbox with [mark] Label → Detail (□ ▶ ✔ ✖) and the >> code lines, redrawn on Changed. A double click on a >> line opens the file of the method it calls when it can be found. Echo=true also prints the code and the output in the Command Window, for a GUI used on its own.
  • run(s_group, s_label, s_code) は、渡されたコード文字列そのものを、オブジェクトが持つワークスペースで評価します。別のコールバックは持ちません。そのため、書き出したスクリプトは GUI が実行した内容と必ず一致します。
  • コードが代入した変数は次の実行でも使えます（res_pf = net.calculate_powerflow(); の後の res_pf など）。外からは set_variable と get_variable で読み書きします。
  • 実行は tab_entry の 1 行になります。列は Group、Label、Code、Status（"run"、"done"、"fail"）、Detail（evalc で取り込んだ出力の最初の数行、またはエラーメッセージと経過時間）です。エラーは再送出せず、ワークスペースも実行前のままにします。記録の開始時と終了時にイベント Changed を通知します。
  • 記録は削除しません。モデルの編集は積み上がります。get_script は Header の後に、"done" の記録を実行順に書きます。同じグループが続く範囲ごとに %% <Group> の節を作り、各コードの前に % <Label> を入れます。失敗した記録は一覧には残りますが、スクリプトには入りません。
  • ワークスペースの仕組み: コードは、変数が varargin と varargout だけの private 関数の中で実行します。保存した変数をこの関数に展開し、evalc でコードを実行し、すべての変数を回収します。そのため、コードではこれ以外のどの名前も使えます。varargin と varargout は記録の変数にできません。
  • attach_view(h_container) は uilistbox を作り、[印] Label → Detail（□ ▶ ✔ ✖）と >> コード の行を表示します。Changed のたびに描き直します。>> の行をダブルクリックすると、その行が呼ぶメソッドのファイルが見つかれば開きます。Echo=true にすると、コードと出力をコマンドウィンドウにも表示します。単独で使うモデルや結果の GUI 向けです。

DrawerOptionDialog: option formsDrawerOptionDialog: オプションの入力フォーム

The form of a method is built from its entry in _GUILDAsystem/resources/functionSignatures.json, which GUILDA.update_keymap(Signature=true) writes from the arguments blocks (the methods that build or remove a model or an event of a Scenario, the constructors and the edit methods of the event classes (the key of a constructor is the class name, such as EventFault), simulate, get_sys (signed as PowerSystemModel.get_sys, where it is defined), the power flow, OPF and CPF calculations, and the plot_*, disp_*, get_* and export methods of the results). obj and the inputs in Exclude get no field. Parent and the script: h_parentParent とスクリプト: h_parent

Tab contractタブの取り決め

Each tab is a set of private files of DrawerGUILDA named after its key, private/tab_<key>_*.m, registered in private/tab_list.m (key, title, history group, build function). The frame never changes to fill a tab. The build function sct_hook = tab_<key>_build(h_panel, sct_app) runs on the first show, fills h_panel and returns the hooks; every hook is optional.

Where to extend the feature機能を拡張する箇所

  • A new model class: nothing to add; see What a model class writes for the GUI.
  • A table for every model of a kind: in gui_content of that abstract class (_GUILDAsystem/@<AbstractClass>/gui_content.m). Put the new pages first, then gui_content@PowerSystemModel(obj), and use only the type table. The classdef declares it as methods(Access=protected) sct_page = gui_content(obj) end.
  • A table for every model: in _GUILDAsystem/_auxiliary/@LayerPackage/gui_content.m.
  • A color: in tools.gui_palette only; the parts read their colors from it.
  • A button of the result GUI: add the method to sig_methods of GUILDA.update_keymap and run GUILDA.update_keymap(Signature=true); a public plot_*, disp_*, get_* or export method of the five result classes that is not there fails F34.
  • An add button: the list sm_add in render.m (label and "<Class>.<method>"); the method must be in sig_methods of GUILDA.update_keymap. A remove: remove_child in private/build_navigation.m.
  • A tab of the app: its own files _GUILDAsystem/_auxiliary/@DrawerGUILDA/private/tab_<key>_*.m (see Tab contract); a new tab also needs a row in private/tab_list.m.
  • Tests: _GUILDAverification/+DebugScript/test_F32_model_gui.m, test_F33_model_gui_network.m and test_F51_model_gui_actions.m (the actions) build the GUI in hidden figures; an alert there becomes the HiddenAlert warning, and a remove runs without a confirmation.
  • 新しいモデルクラス: GUI のために追加するものはありません。モデルクラスが GUI のために書くものを参照してください。
  • ある種類のすべてのモデルに共通の表: その抽象クラスの gui_content（_GUILDAsystem/@<抽象クラス>/gui_content.m）に書きます。新しいページを先に並べ、その後ろに gui_content@PowerSystemModel(obj) の結果を続けます。ページの種類は table だけです。classdef には methods(Access=protected) sct_page = gui_content(obj) end と宣言します。
  • すべてのモデルに共通の表: _GUILDAsystem/_auxiliary/@LayerPackage/gui_content.m に書きます。
  • 色: 変えるのは tools.gui_palette だけです。各部品はここから色を取ります。
  • 結果の GUI のボタン: メソッドを GUILDA.update_keymap の sig_methods に加え、GUILDA.update_keymap(Signature=true) を実行します。5 つの結果クラスの公開の plot_*、disp_*、get_*、export が入っていないと F34 が失敗します。
  • 追加ボタン: render.m のリスト sm_add（ラベルと "<クラス>.<メソッド>"）に加えます。メソッドは GUILDA.update_keymap の sig_methods に入っている必要があります。削除: private/build_navigation.m の remove_child に加えます。
  • アプリのタブ: そのタブのファイル _GUILDAsystem/_auxiliary/@DrawerGUILDA/private/tab_<キー>_*.m に書きます（タブの取り決めを参照）。新しいタブは private/tab_list.m にも 1 行加えます。
  • テストは _GUILDAverification/+DebugScript/test_F32_model_gui.m、test_F33_model_gui_network.m、test_F51_model_gui_actions.m（操作）です。どれも非表示の図に GUI を作るので、アラートは警告 HiddenAlert に置き換わり、削除は確認なしで実行します。
