Class Designクラス設計

How the model classes relate as a whole, and the rules across them: ownership, parent references, identity, settings, edits, variable order. What one class owns and does: on its Reference page. Read before adding a property or a method to a model class.モデルクラス全体の関係と、クラスをまたぐルール（所有、親への参照、識別、設定、編集、変数の順序）。1つのクラスが所有するもの・行う処理は、各クラスのリファレンスページ。モデルクラスへのプロパティ・メソッド追加の前に一読。

The class structure is stable on purpose: other developers build on it. These rules decide where data and logic go inside the existing classes, instead of adding new classes. They apply to all code in GUILDA.クラス構成は意図的に固定。ほかの開発者がその上に開発を重ねるため。ここでのルールは、新しいクラスの導入ではなく、既存クラスの中でのデータとロジックの置き場所を決めるもの。GUILDA のすべてのコードに適用。

Design principles設計原則

  1. No data is held by two classes同じデータを2つのクラスで持たない

    Each value has a single owner. Anything derived from it is a Dependent property that reads the owner on access. Do not write code that copies a value and keeps the copies in sync: it is a source of bugs.

    各値の所有者は1つ。導出できるものは、アクセス時に所有者を読む Dependent プロパティに。値をコピーしてコピー同士を同期させるコードはバグの原因のため禁止。

    Examples: PowerNetwork.cv_Vequilibrium / cv_Iequilibrium / rv_Xequilibrium (collected from the buses), Branch.cv_Vequilibrium / cv_Iequilibrium (from the end buses and its own admittance), Component.tab_parameter (assembled from the Parameter objects), Component.rv_Xequilibrium_all (the component plus its controllers).

    例: PowerNetwork.cv_Vequilibrium / cv_Iequilibrium / rv_Xequilibrium（母線から収集）、Branch.cv_Vequilibrium / cv_Iequilibrium（両端の母線と自身のアドミタンスから計算）、Component.tab_parameter（Parameter オブジェクトから組み立て）、Component.rv_Xequilibrium_all（機器とその制御器）。

  2. Data and functions follow real-world rolesデータと機能は現実の役割に従う

    A class holds what the physical element has and computes what the physical element determines:

    クラスは、物理的な要素が持つものを保持し、要素が決めるものを計算。

    • Branch: its impedances; builds its own admittance matrix.ブランチ: 自身のインピーダンスを保持し、自身のアドミタンス行列を作成
    • Bus: the algebraic variable, its voltage V.母線: 代数変数である電圧 V
    • Components and controllers: the differential equations and output equations.機器・制御器: 微分方程式と出力方程式
  3. Same method name, same meaning on every layer同じメソッド名は、どの階層でも同じ意味

    Same meaning and same shape of inputs and outputs on every class. A higher layer aggregates the lower ones.

    どのクラスでも同じ意味、同じ入出力の形。上位の階層が下位の階層を集約。

    • get_sys: the linearized model of each layer.get_sys: 各階層の近似線形化モデル
      • LocalController: the controller alone.LocalController: 制御器単体
      • Component: the component and its controllers.Component: 機器とその制御器
      • Bus: the aggregate of its components.Bus: その機器の集約
      • PowerNetwork: the whole system.PowerNetwork: システム全体
      • On LocalController, Component, and Bus: input, state, and output names are unique, and states are not outputs. An output with the name of a state of its owner is labelled Y_ + name.LocalController・Component・Bus: 入力・状態・出力の名前は一意、状態は出力に含めない。所有者の状態と同じ名前の出力のラベルは Y_ + 名前
      • Inputs, states, and outputs of each layer: on the get_sys method page of each class in the Reference.各階層の入力・状態・出力: リファレンスの各クラスの get_sys のページ
    • get_admittance_matrix: on Branch, its 2×2 matrix; on PowerNetwork, the matrix of the whole network.get_admittance_matrix: Branch では自身の 2×2 行列、PowerNetwork ではネットワーク全体の行列
    • get_variable_map: on Component and Bus, the rows of the network map that belong to it, in the same relative order (see Variable order).get_variable_map: Component と Bus では、ネットワークの変数マップのうち自身に属する行（同じ相対順序。変数の順序を参照）
    • OPF: no method on the model classes. SolverOPF reads tab_parameter of the buses, components, and branches and builds the problem itself, as SolverPF does for the power flow (see OPF customization).OPF: モデルのクラスにメソッドなし。SolverOPF が母線・機器・ブランチの tab_parameter を読み取って問題を構築（潮流計算の SolverPF と同じ。OPF のカスタマイズを参照）
  4. Edits only record; analyses check編集は記録するだけ、確認は解析が行う

    Editing a parameter or a mode only updates the value and records what became stale; nothing is rebuilt per edit. An analysis checks the flags when it starts (see Edit handling).

    パラメータやモードの編集は、値の更新と、古くなったものの記録のみ。編集ごとの再構築なし。フラグの確認は解析の開始時（モデル編集の扱いを参照）。

Components and controllers機器と制御器

Controllers keep their own contract, different from Component on purpose. A component outputs the current I to the network and exposes its outputs Y and states x to its controllers; a controller only outputs inputs u for the component. Every connection is made by name.

制御器は、意図的に Component と異なる独自の契約。機器はネットワークへ電流 I を出力し、出力 Y と状態 x を制御器に公開。制御器の出力は機器への入力 u のみ。接続はすべて名前で。

  • Observing. A local controller reads the component it is attached to (for a PSS under an AVR, the component above them) by the names of its inputs sv_u:観測: ローカル制御器は、接続先の機器（AVR の下の PSS では、その上の機器）を入力名 sv_u で読む
    • A name in the component's sv_y reads that output; otherwise a name in its sv_x reads that state. When both have the name, the output wins.機器の sv_y にある名前はその出力、なければ sv_x にある名前はその状態。両方にあれば出力が優先
    • The reserved input names Xall and Yall observe all the states and all the outputs of the component.予約された入力名 Xall・Yall: 機器のすべての状態・すべての出力を観測
    • X and Y are not reserved: an input with either name is an error.X と Y は予約名ではない。どちらかの名前の入力はエラー
    • An input with the name of an output of a nested controller (for example Vpss) reads that output; any other input stays at its equilibrium.入れ子の制御器の出力と同じ名前の入力（例: Vpss）はその出力を読む。それ以外の入力は平衡点の値のまま
    • A global controller reads the states x of the components it controls, by the names of its inputs sv_u.グローバル制御器: 制御する機器の状態 x を入力名 sv_u で読む
  • Driving.駆動
    • The outputs sv_y of a controller drive the inputs of the same name of the component, or of the controller above it.制御器の出力 sv_y が、機器またはその上の制御器の同じ名前の入力を駆動
    • A component has two top-level controllers at most, the AVR or "local" controller and the governor, and they drive different inputs (for example Vfield and Pmech).機器の最上位の制御器は高々2つ: AVR または "local" の制御器とガバナ。駆動する入力は別々（例: Vfield と Pmech）
    • An input disturbance of a scenario or a global controller on such an input of the component adds to the output of the local controller, in the simulation and in get_sys.機器のそのような入力へのシナリオの入力外乱やグローバル制御器は、ローカル制御器の出力に加算（シミュレーションでも get_sys でも）

実行ごとの作業データ。モデルクラスに置き、解析クラスが書き込む。モデルのデータではない。

  • Data: iv_odeX / iv_odeI / iv_odeU / iv_odeY, lv_odeUfromLC / iv_odeYtoU, l_isFault, rv_Xoffset / rv_Uoffset, l_isConnect of components and global controllers, iv_CPFV / iv_CPFX / f_PQ2Bus.対象: iv_odeX / iv_odeI / iv_odeU / iv_odeY、lv_odeUfromLC / iv_odeYtoU、l_isFault、rv_Xoffset / rv_Uoffset、機器とグローバル制御器の l_isConnect、iv_CPFV / iv_CPFX / f_PQ2Bus
  • Write access: the analysis classes only, SolverODE for the simulation data and SolverCPF for the CPF data. Scenario only reads the network.書き込み: 解析クラスのみ。シミュレーションのデータは SolverODE、連続潮流計算のデータは SolverCPF。Scenario はネットワークを読むだけ
  • Exceptions: SolverODE and Component may write iv_ode* of buses and components and Component.lv_odeUfromLC; Component may also write its own l_isConnect.例外: 母線と機器の iv_ode* と Component.lv_odeUfromLC は SolverODE と Component も書き込み可。Component は自身の l_isConnect にも書き込み可
  • Restricted for reading too: Bus.l_isFault, Component.l_isConnect.読み取りも制限: Bus.l_isFault、Component.l_isConnect
  • What a simulation restores: API Design: Side effects.シミュレーションが元に戻すもの: API 設計: 副作用

Parent references親への参照

Each child keeps a read-only reference to its parent: Bus.a_PowerNetwork, Branch.a_PowerNetwork, Component.a_Bus, LocalController.a_Component, GlobalController.a_PowerNetwork, Scenario.a_PowerNetwork, and the parent of each Parameter. Rules:

各子は親への読み取り専用の参照を保持: Bus.a_PowerNetwork、Branch.a_PowerNetwork、Component.a_Bus、LocalController.a_Component、GlobalController.a_PowerNetwork、Scenario.a_PowerNetwork、各 Parameter の親。ルールは次のとおり。

  1. Only the parent sets and clears it設定と解除は親だけが行う

    Set by the parent's constructor or add_* method, cleared by its remove_* method, so a removed object has no parent reference.

    • Enforced by SetAccess: the property is writable only by the parent class (e.g. SetAccess={?PowerNetwork}), so no other code writes it. No setter method.
    • No class validation: [] when unset, and cleared with []. The class it holds is named by the <@Type> tag of its comment (e.g. <@Type> PowerNetwork) and shown on the class page.
    • On attaching, the parent calls the child's log_edit(..., "Topology"), which marks its equilibrium stale.

    親のコンストラクタまたは add_* メソッドが設定し、remove_* メソッドが解除。削除されたオブジェクトは親を参照しない。

    • SetAccess で強制: 書き込めるのは親クラスだけ（例: SetAccess={?PowerNetwork}）で、ほかのコードからの書き込みなし。setter メソッドなし
    • クラス検証なし: 未設定は []、解除も [] の代入。入るクラスはコメントの <@Type> タグ（例: <@Type> PowerNetwork）で示し、クラスページに表示
    • 接続時、親が子の log_edit(..., "Topology") を呼び、子の equilibrium を古いと印付け
  2. A child only reads its parent子は親を読むだけ

    For the tag path, for edit notification, and for shared settings such as the frequency.

    タグのパス、編集の通知、周波数などの共有設定のため。

  3. A child never writes upward or sideways子は上にも横にも書き込まない

    No writes to its parent or siblings, and no copy of its parent's data. Edits travel upward only as a call: log_edit calls the hook handle_edit on each layer from the edited one up to the top, and each layer changes only its own state (its own stale tags in sct_stale; the network also keeps one slack bus).

    親や兄弟への書き込みなし、親のデータのコピーも持たない。編集は呼び出しとしてだけ上へ伝達: log_edit が編集した層から最上位までの各層のフック handle_edit を呼び出し、各層は自分の状態だけを変更（sct_stale の自分の stale タグ。ネットワークは slack 母線の 1 つへの維持も）。

Identifying objects: tags, not indicesオブジェクトの識別: インデックスではなくタグ

Tag (e.g. B001)タグ（例: B001）

The permanent ID of an object. Use it in saved data and in scenarios: a disturbance names its buses, branches, and units by tag, checked against the network when it is added and again when it is simulated.

オブジェクトの恒久的な ID。保存するデータとシナリオで使用。外乱は母線・ブランチ・機器をタグで指定し、外乱の追加時とシミュレーション時にネットワークと照合。

Index (e.g. net.a_Bus{3})インデックス（例: net.a_Bus{3}）

Only the current position. It shifts after remove_*, so never store it.

現在の位置にすぎない。remove_* の後にずれるため、保存しない。

  • Automatic tag: the largest number in use plus one (buses B###, branches ###, components per bus).自動で付くタグ: 使用中の最大の番号 + 1（母線は B###、ブランチは ###、機器は母線ごと）
  • A number is not reused while a larger one exists, so a new tag never names an existing or earlier object.より大きい番号が存在する間は番号を再利用しない。新しいタグが既存または過去のオブジェクトを指すことはない
  • Global controller tag: chosen by the user, and must be unique.グローバル制御器のタグ: ユーザーが選択。一意であること

Solver settings of analyses解析のソルバー設定

Persistent defaults: net.solver_*永続的な既定値: net.solver_*

The solver objects hold the default settings of each analysis. A change made there stays, so repeated runs keep the last settings.

ソルバーオブジェクトが各解析の既定の設定を保持。ここでの変更は残るため、繰り返し実行しても最後の設定を維持。

Run-time Name-Value options実行時の Name-Value オプション

Override the defaults for that call only. The stored defaults do not change.

その呼び出しに限り既定値を上書き。保存されている既定値は不変。

System data (line constants, power-flow specifications, limits) is not a solver setting: set it beforehand on the model objects through properties and tab_parameter (see API Design, rule 2).

系統データ（線路定数、潮流計算の指定値、制限値）はソルバーの設定ではない。プロパティと tab_parameter を通じて、事前にモデルオブジェクトに設定（API 設計のルール 2 を参照）。

Handling of model editsモデル編集の扱い

Each layer keeps what of its own is out of date in sct_stale (LayerPackage): one field per stale tag of the class, each a string column of messages, empty when up to date. The constructor creates the fields with the message "initialize has not been run": PowerNetwork powerflow and odefcn (the network frequency); Component, LocalController and GlobalController equilibrium and odefcn (the f_* handles); Bus and Branch none. An edit calls log_edit(log, tag) on the edited layer, which calls the hook handle_edit(a_layer, tag, log) on every layer from there up to the top; a_layer is the edited layer, the owner for a Parameter container. Each class compares a_layer == obj and the tag, and appends the message "tags of the edited layer joined by /: log" (e.g. dynamics/SG1B001/B001/IEEE9bus: edit D: 2 -> 2.1) to its own fields for the edits that affect them (obj.sct_stale.equilibrium(end+1,1) = log). Each class also clears only its own fields. PowerNetwork.handle_edit also keeps one slack bus. The tags of edits: the parameter groups (dynamics, powerflow, base, operation, OPF, graph), Topology, Slack, Tag.

各層は自分の古くなった部分を sct_stale（LayerPackage）に保持: クラスの stale タグごとに 1 フィールド、値はメッセージの string 列、空なら最新。コンストラクタがメッセージ "initialize has not been run" 付きでフィールドを作成: PowerNetwork は powerflow と odefcn（系統周波数）、Component・LocalController・GlobalController は equilibrium と odefcn（f_* ハンドル）、Bus と Branch はなし。編集は編集した層の log_edit(log, tag) を呼び出し、それがその層から最上位までの各層のフック handle_edit(a_layer, tag, log) を呼び出し。a_layer は編集した層（Parameter コンテナは所有者）。各クラスは a_layer == obj とタグを比べ、影響を受ける自分のフィールドに、メッセージ "編集した層からのタグを / で連結: log"（例 dynamics/SG1B001/B001/IEEE9bus: edit D: 2 -> 2.1）を追加（obj.sct_stale.equilibrium(end+1,1) = log）。消去も各クラスが自分のフィールドのみ。PowerNetwork.handle_edit は slack 母線を 1 つに維持する役割も。編集のタグ: パラメータの区分（dynamics、powerflow、base、operation、OPF、graph）、Topology、Slack、Tag。

Only PowerNetwork.initialize brings the layers up to date. It solves the operating point when Method is given or powerflow is stale and writes it with Bus.set_equilibrium; then the buses initialize their components (stale handles rebuilt with build_odefcn, a stale equilibrium recomputed from the held V and I) and those their local controllers, and the global controllers come last. Each layer decides from its own fields; the network decides only about its own power flow and clears its fields at the end. The analyses only check: each reads, inline and in the loops it already has, the stale tags it needs (sct_stale has public GetAccess) and changes nothing. A network Hz edit reaches no child: it marks the network odefcn, which every analysis reads; in initialize each component and controller rebuilds its handles when its odefcn is not empty or the frequency it built them with (r_odefcnHz) differs from get_Hz().

層を最新にするのは PowerNetwork.initialize のみ。Method の指定時か powerflow が古いときに運転点を解き、Bus.set_equilibrium で書き込み。続いて母線が機器を、機器が局所制御器を初期化（古いハンドルは build_odefcn で再構築、古い平衡点は保持中の V と I から再計算）、大域制御器は最後。各層が自分のフィールドから判断し、ネットワークが判断するのは自分の潮流のみ、最後に自分のフィールドを消去。解析は確認のみ: 各解析が、必要な stale タグ（sct_stale、GetAccess は public）を既存のループの中でその場で読み取り、何も変更しない。ネットワークの Hz の編集はどの子にも届かない: ネットワークの odefcn に記録し、どの解析もそれを読み取る。initialize では各機器・制御器が、自分の odefcn が空でないか、ハンドル作成時の周波数（r_odefcnHz）が get_Hz() と異なればハンドルを再構築。

OPF customizationOPF のカスタマイズ

The model objects hold only parameters. SolverOPF.build_problem reads them and builds one optimproblem; no OPF state lives on a bus, component, or branch. The OPF is used by no other analysis, so it follows the power flow (the solver pulls the data). The dynamics keep cached f_* handles on the classes because several analyses (simulate, get_sys) reuse them.

モデルのオブジェクトはパラメータのみを保持。SolverOPF.build_problem がそれを読み取り、1 つの optimproblem を構築。母線・機器・ブランチに OPF の状態なし。OPF を使う解析はほかにないため、潮流計算と同じくソルバーがデータを取得する方式。動特性は複数の解析（simulate、get_sys）が再利用するため、キャッシュした f_* ハンドルをクラスに保持。
