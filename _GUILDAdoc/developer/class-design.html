The class structure is stable on purpose: other developers build on it, so these rules decide where data and logic go inside the existing classes instead of introducing new ones. The rules apply to all code in GUILDA.クラス構成は意図的に固定しています。ほかの開発者がその上に開発を重ねるため、ここでのルールは、新しいクラスを導入するのではなく、既存のクラスの中でデータとロジックをどこに置くかを決めるものです。このルールは GUILDA のすべてのコードに適用されます。

Design principles設計原則

  1. No data is held by two classes同じデータを2つのクラスで持たない

    Each value has a single owner. Anything that can be derived from it is a Dependent property that reads the owner when it is accessed. Code that copies a value and keeps the copies in sync is a source of bugs; do not write it.

    各値の所有者は1つだけです。そこから導出できるものは、アクセスされたときに所有者を読む Dependent プロパティにします。値をコピーし、コピー同士を同期させるコードはバグの原因になるので、書かないでください。

    Examples: PowerNetwork.cv_Vequilibrium / cv_Iequilibrium / rv_Xequilibrium (collected from the buses), Branch.cv_Vequilibrium / cv_Iequilibrium (from the end buses and its own admittance), Component.tab_parameter (assembled from the Parameter objects), and Component.rv_Xequilibrium_all (the component plus its controllers).

    例: PowerNetwork.cv_Vequilibrium / cv_Iequilibrium / rv_Xequilibrium（母線から収集）、Branch.cv_Vequilibrium / cv_Iequilibrium（両端の母線と自身のアドミタンスから計算）、Component.tab_parameter（Parameter オブジェクトから組み立て）、Component.rv_Xequilibrium_all（機器とその制御器）。

  2. Data and functions follow real-world rolesデータと機能は現実の役割に従う

    A class holds what the physical element has and computes what the physical element determines. A branch holds its impedances and builds its own admittance matrix. A bus holds the algebraic variable, its voltage V. Components and controllers hold the differential equations and output equations.

    クラスは、物理的な要素が持つものを保持し、物理的な要素が決めるものを計算します。ブランチは自身のインピーダンスを保持し、自身のアドミタンス行列を作ります。母線は代数変数である電圧 V を保持します。機器と制御器は微分方程式と出力方程式を保持します。

  3. Same method name, same meaning on every layer同じメソッド名は、どの階層でも同じ意味

    A method with the same name means the same thing on every class and has the same shape of inputs and outputs. A higher layer aggregates the lower ones.

    同じ名前のメソッドは、どのクラスでも同じ意味を持ち、入力と出力の形も同じです。上位の階層は下位の階層を集約します。

    • get_sys: on LocalController, the linearized model of the controller alone; on Component, the model of the component and its controllers; on Bus, the aggregate of its components; on PowerNetwork, the whole system. On LocalController, Component, and Bus the input, state, and output names are unique, and states are not outputs (LocalController.get_sys adds them only with full=true). An output with the name of a state of its owner is labelled Y_ + name. PowerNetwork.get_sys keeps the shape of v3, described below.get_sys: LocalController では制御器単体の近似線形化モデル、Component では機器とその制御器のモデル、Bus ではその機器の集約、PowerNetwork ではシステム全体です。LocalController、Component、Bus では入力・状態・出力の名前は一意で、状態は出力に含まれません（LocalController.get_sys は full=true のときだけ状態を出力に加えます）。所有者の状態と同じ名前の出力には、Y_ + 名前のラベルが付きます。PowerNetwork.get_sys は、以下のとおり v3 の形を保ちます。
      • LocalController: inputs V, ucon; states xcon; outputs ycon.LocalController: 入力は V、ucon、状態は xcon、出力は ycon です。
      • Component: inputs the port (V for "V2I", I for "I2V"), umac, ucon; states xmac, xcon; outputs the other port, ymac, ycon. The signals from the component to its controllers are connected inside.Component: 入力はポート（"V2I" では V、"I2V" では I）、umac、ucon、状態は xmac、xcon、出力はもう一方のポート、ymac、ycon です。機器からその制御器への信号は内部で接続されます。
      • Bus: the same, aggregated over its components, with the bus port.Bus: 同じ形を、その機器について集約したもので、母線のポートを持ちます。
      • PowerNetwork: inputs u; no port, because the network closes the buses. By default the outputs follow the states, as in v3, and they depend on Algorithm (see ResultLIN.get_ss); Input and Output select other channels.PowerNetwork: 入力は u です。ネットワークが母線を閉じるため、ポートはありません。既定では v3 と同じく出力は状態に従い、Algorithm によって変わります（ResultLIN.get_ss を参照）。Input と Output でほかのチャネルを選べます。
    • get_admittance_matrix: on Branch, its 2×2 matrix; on PowerNetwork, the matrix of the whole network.get_admittance_matrix: Branch では自身の 2×2 行列、PowerNetwork ではネットワーク全体の行列です。
    • get_variable_map: on Component and Bus, the rows of the network map that belong to it, in the same relative order (see Variable order).get_variable_map: Component と Bus では、ネットワークの変数マップのうち自身に属する行を、同じ相対順序で返します（変数の順序を参照）。
    • build_opf_problem and set_opffcn: each class adds its own variables, cost, and constraints; PowerNetwork collects them.build_opf_problem と set_opffcn: 各クラスが自身の変数、コスト、制約を追加し、PowerNetwork がそれらを集めます。
  4. Edits only record; analyses check編集は記録するだけ、確認は解析が行う

    Editing a parameter or a mode only updates the value and records what became stale. Nothing is rebuilt on each edit. An analysis checks the flags when it starts (see Edit handling).

    パラメータやモードの編集は、値を更新し、何が古くなったかを記録するだけです。編集のたびに再構築されるものはありません。解析が開始時にフラグを確認します（編集の扱いを参照）。

Contract契約
Controllers keep their own contract, different from Component on purpose: a component outputs the current I to the network and exposes its outputs Y and states x to its controllers, while a controller only outputs inputs u for the component. Every connection is made by name.制御器は、意図的に Component とは異なる独自の契約を持ちます。機器はネットワークへ電流 I を出力し、出力 Y と状態 x を制御器に公開しますが、制御器は機器への入力 u を出力するだけです。接続はすべて名前で行います。
Observes観測
A local controller reads the component it is attached to (for a PSS under an AVR, the component above them) by the names of its inputs sv_u: a name in the component's sv_y reads that output; otherwise a name in its sv_x reads that state. When both have the name, the output wins. The reserved input names Xall and Yall observe all the states and all the outputs of the component (controller.local_LQR uses Xall). The names X and Y are not reserved: an input with either name is an error. An input with the name of an output of a nested controller (for example Vpss) reads that output; any other input stays at its equilibrium. A global controller reads the states x of the components it controls, by the names of its inputs sv_u.ローカル制御器は、接続先の機器（AVR の下の PSS では、その上の機器）を入力名 sv_u によって読みます。機器の sv_y にある名前はその出力を読み、そうでなければ sv_x にある名前はその状態を読みます。両方に同じ名前がある場合は出力が優先されます。予約された入力名 Xall と Yall は、機器のすべての状態とすべての出力を観測します （controller.local_LQR は Xall を使います）。X と Y は予約名ではなく、どちらかの名前の入力はエラーになります。入れ子の制御器の出力と同じ名前の入力（たとえば Vpss）はその出力を読み、それ以外の入力は平衡点の値のままです。グローバル制御器は、制御する機器の状態 x を入力名 sv_u によって読みます。

Parent references親への参照

Each child keeps a read-only reference to its parent: Bus.a_PowerNetwork, Branch.a_PowerNetwork, Component.a_Bus, LocalController.a_Component, GlobalController.a_PowerNetwork, and the parent of each Parameter. They follow these rules:

各子は、親への読み取り専用の参照を保持します。Bus.a_PowerNetwork、Branch.a_PowerNetwork、Component.a_Bus、LocalController.a_Component、GlobalController.a_PowerNetwork、および各 Parameter の親です。これらは次のルールに従います。

  1. Only the parent sets and clears it設定と解除は親だけが行う

    The reference is set by the parent's constructor or add_* method and cleared by its remove_* method, so a removed object no longer points to its old parent. No other code writes it.

    参照は親のコンストラクタまたは add_* メソッドが設定し、remove_* メソッドが解除します。そのため、削除されたオブジェクトが以前の親を指し続けることはありません。ほかのコードは書き込みません。

  2. A child only reads its parent子は親を読むだけ

    For the tag path, for edit notification, and for shared settings such as the frequency.

    タグのパス、編集の通知、周波数などの共有設定のために読みます。

  3. A child never writes upward or sideways子は上にも横にも書き込まない

    It does not write to its parent or to its siblings, and it never stores a copy of its parent's data. The one exception is the edit notification: a Parameter marks the handle cache of the object that owns it as stale (s_edit.str_odefcn = "editted").

    親や兄弟には書き込まず、親のデータのコピーも保持しません。唯一の例外は編集の通知で、Parameter は自身を所有するオブジェクトのハンドルキャッシュを古いものとして印を付けます（s_edit.str_odefcn = "editted"）。

Identity: tags, not indices識別: インデックスではなくタグ

Tag (e.g. B001)タグ（例: B001）

The permanent ID of an object. Use it in saved data and in event definitions.

オブジェクトの恒久的な ID です。保存するデータやイベントの定義ではこれを使います。

Index (e.g. net.a_Bus{3})インデックス（例: net.a_Bus{3}）

Only the current position. It shifts after remove_*, so never store it.

現在の位置にすぎません。remove_* の後にずれるので、保存しないでください。

An automatic tag takes the largest number in use plus one (buses B###, branches ###, components per bus). A number is never reused while a larger one exists, so a new tag never names an existing or earlier object. A global controller's tag is chosen by the user and must be unique.

自動で付くタグは、使用中の最大の番号に1を加えたものです（母線は B###、ブランチは ###、機器は母線ごと）。より大きい番号が存在する間は番号が再利用されないため、新しいタグが既存のオブジェクトや以前のオブジェクトを指すことはありません。グローバル制御器のタグはユーザーが選び、一意でなければなりません。

Solver settingsソルバー設定

Persistent defaults: net.solver_*永続的な既定値: net.solver_*

The solver objects hold the default settings of each analysis. A change made there stays, so repeated runs keep the last settings.

ソルバーオブジェクトは各解析の既定の設定を保持します。そこで行った変更は残るため、繰り返し実行しても最後の設定が保たれます。

Run-time Name-Value options実行時の名前と値のオプション

Override the defaults for that call only. They do not change the stored defaults.

その呼び出しに限り既定値を上書きします。保存されている既定値は変わりません。

System data (line constants, power-flow specifications, limits) is not a solver setting: it is set beforehand on the model objects through properties and tab_parameter (see API Design, rule 2).

系統データ（線路定数、潮流計算の指定値、制限値）はソルバーの設定ではありません。プロパティと tab_parameter を通じて、事前にモデルオブジェクトに設定します（API 設計のルール 2 を参照）。

Variable order変数の順序

net.get_variable_map() is the single definition of the order of the model variables. Every analysis that lists variables uses it: the Jacobian blocks of a linearization, the Point option, and simulation results. Do not define another order. The one exception is the state order of get_ss and get_sys, kept from v3: "Kron" and "DAE" put the states of the global controllers first, and "Feedback" puts them last.

net.get_variable_map() は、モデル変数の順序の唯一の定義です。近似線形化のヤコビ行列のブロック、Point オプション、シミュレーション結果など、変数を並べるすべての解析がこれを使います。別の順序を定義しないでください。唯一の例外は v3 から引き継いだ get_ss と get_sys の状態の順序で、"Kron" と "DAE" はグローバル制御器の状態を先頭に、"Feedback" は末尾に置きます。

BlockブロックOrder順序
1. states x1. 状態 xFor each bus, for each component: the component's states, then its local controllers' states (depth first: an AVR, then the PSS under it). Then the states of each global controller.母線ごと、機器ごとに、機器の状態、続いてそのローカル制御器の状態（深さ優先: AVR、その下の PSS の順）。その後に各グローバル制御器の状態。
2. bus voltages2. 母線電圧Vre, Vim of each bus, interleaved per bus.各母線の Vre、Vim を、母線ごとに交互に並べます。
3. inputs u3. 入力 uFor each bus, for each component: its inputs.母線ごと、機器ごとに、その入力。

The Label column of the map equals the state and input names of get_sys, so find a variable by its label, not by its position. The bus variables of "DAE" have their own numbered names (such as theta1), and "Feedback" can have fewer states because its connection removes some. net.linearize(Point=x) linearizes at any state x given in this order, or at a time of a simulation result (Point={sim, t}).

マップの Label 列は get_sys の状態名・入力名と一致するので、変数は位置ではなくラベルで探してください。"DAE" の母線変数には独自の番号付きの名前（theta1 など）があり、"Feedback" は接続によって一部の状態が消えるため、状態が少なくなることがあります。net.linearize(Point=x) は、この順序で与えた任意の状態 x、またはシミュレーション結果のある時刻（Point={sim, t}）で近似線形化します。

Optional analyses: Hessians任意対応の解析: ヘッセ行列

An analysis that only some models support is a method on the base class with a per-class contract. get_hessian on Component, LocalController, and GlobalController works this way.

一部のモデルだけが対応する解析は、クラスごとの契約を持つ基底クラスのメソッドにします。Component、LocalController、GlobalController の get_hessian はこの方式です。

The class supports itクラスが対応している場合

It defines static Hessian_dx (required), Hessian_I, and Hessian_Y with the arguments of Jacobi_*. Each returns n_eq × n_z × n_z with z = [x; V; I; u].

Jacobi_* と同じ引数をとる静的メソッド Hessian_dx（必須）、Hessian_I、Hessian_Y を定義します。それぞれ z = [x; V; I; u] について n_eq × n_z × n_z を返します。

The class does notクラスが対応していない場合

The base method stops with GUILDA:<Layer>:HessianNotSupported, which names the class.

基底クラスのメソッドが、クラス名を示す GUILDA:<Layer>:HessianNotSupported で停止します。

Each class supplies its own derivatives. No symbolic differentiation is used, so the Symbolic Math Toolbox is not required.

各クラスが自身の導関数を提供します。記号微分は使わないため、Symbolic Math Toolbox は不要です。

OPF customizationOPF のカスタマイズ

Each object holds its own OPF terms, set with obj.set_opffcn("Cost", @(v,p) ..., "Constraint", @(v,p) struct(...), "DefaultConstraint", false) and restored with obj.reset_opffcn(). v holds the object's optimization variables and p its parameters.

各オブジェクトは自身の OPF 項を保持します。obj.set_opffcn("Cost", @(v,p) ..., "Constraint", @(v,p) struct(...), "DefaultConstraint", false) で設定し、obj.reset_opffcn() で元に戻します。v はオブジェクトの最適化変数、p はそのパラメータです。

Term項Effect効果
CostReplaces the default cost of the object. A load has no default cost.オブジェクトの既定のコストを置き換えます。負荷には既定のコストがありません。

network levelネットワーク全体net.set_opffcn takes terms over several objects; its v reaches each object's variables by tag (e.g. v.Component.(tag).P).net.set_opffcn は複数のオブジェクトにまたがる項を受け取ります。その v からは、タグで各オブジェクトの変数にアクセスします（例: v.Component.(tag).P）。

DC OPF では |V| = 1 と、MATPOWER と同じブランチのサセプタンス b = 1/(X·tap) を使います。
