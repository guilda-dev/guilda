Class Designクラス設計

How the model classes relate as a whole, and the rules across them: ownership, parent references, identity, settings, edits, variable order. What one class owns and does: on its Reference page. Read before adding a property or a method to a model class.モデルクラス全体の関係と、クラスをまたぐルール（所有、親への参照、識別、設定、編集、変数の順序）。1つのクラスが所有するもの・行う処理は、各クラスのリファレンスページ。モデルクラスへのプロパティ・メソッド追加の前に一読。

The class structure is stable on purpose: other developers build on it. These rules decide where data and logic go inside the existing classes, instead of adding new classes. They apply to all code in GUILDA.クラス構成は意図的に固定。ほかの開発者がその上に開発を重ねるため。ここでのルールは、新しいクラスの導入ではなく、既存クラスの中でのデータとロジックの置き場所を決めるもの。GUILDA のすべてのコードに適用。

Design principles設計原則

  1. No data is held by two classes同じデータを2つのクラスで持たない

    Each value has a single owner. Anything derived from it is a Dependent property that reads the owner on access. Do not write code that copies a value and keeps the copies in sync: it is a source of bugs.

    各値の所有者は1つ。導出できるものは、アクセス時に所有者を読む Dependent プロパティに。値をコピーしてコピー同士を同期させるコードはバグの原因のため禁止。

    Examples: PowerNetwork.cv_Vequilibrium / cv_Iequilibrium / rv_Xequilibrium (collected from the buses), Branch.cv_Vequilibrium / cv_Iequilibrium (from the end buses and its own admittance), Component.tab_parameter (assembled from the Parameter objects), Component.rv_Xequilibrium_all (the component plus its controllers).

    例: PowerNetwork.cv_Vequilibrium / cv_Iequilibrium / rv_Xequilibrium（母線から収集）、Branch.cv_Vequilibrium / cv_Iequilibrium（両端の母線と自身のアドミタンスから計算）、Component.tab_parameter（Parameter オブジェクトから組み立て）、Component.rv_Xequilibrium_all（機器とその制御器）。

  2. Data and functions follow real-world rolesデータと機能は現実の役割に従う

    A class holds what the physical element has and computes what the physical element determines:

    クラスは、物理的な要素が持つものを保持し、要素が決めるものを計算。

    • Branch: its impedances; builds its own admittance matrix.ブランチ: 自身のインピーダンスを保持し、自身のアドミタンス行列を作成
    • Bus: the algebraic variable, its voltage V.母線: 代数変数である電圧 V
    • Components and controllers: the differential equations and output equations.機器・制御器: 微分方程式と出力方程式
  3. Same method name, same meaning on every layer同じメソッド名は、どの階層でも同じ意味

    Same meaning and same shape of inputs and outputs on every class. A higher layer aggregates the lower ones.

    どのクラスでも同じ意味、同じ入出力の形。上位の階層が下位の階層を集約。

    • get_sys: the linearized model of each layer.get_sys: 各階層の近似線形化モデル
      • LocalController: the controller alone.LocalController: 制御器単体
      • Component: the component and its controllers.Component: 機器とその制御器
      • Bus: the aggregate of its components.Bus: その機器の集約
      • PowerNetwork: the whole system.PowerNetwork: システム全体
      • On LocalController, Component, and Bus: input, state, and output names are unique, and states are not outputs. An output with the name of a state of its owner is labelled Y_ + name.LocalController・Component・Bus: 入力・状態・出力の名前は一意、状態は出力に含めない。所有者の状態と同じ名前の出力のラベルは Y_ + 名前
      • Inputs, states, and outputs of each layer: on the get_sys method page of each class in the Reference.各階層の入力・状態・出力: リファレンスの各クラスの get_sys のページ
    • get_admittance_matrix: on Branch, its 2×2 matrix; on PowerNetwork, the matrix of the whole network.get_admittance_matrix: Branch では自身の 2×2 行列、PowerNetwork ではネットワーク全体の行列
    • get_variable_map: on Component and Bus, the restriction of the network map: the rows of variables and signals that belong to it, in the same relative order, and the connections inside it ([tab, tab_connection] on a component, [tab, c_idx, tab_connection] on a bus). The connections of the global controllers are only in the network map (see Variable order).get_variable_map: Component と Bus では、ネットワークのマップの制限: 自身に属する変数と信号の行（同じ相対順序）と、内部の接続（機器は [tab, tab_connection]、母線は [tab, c_idx, tab_connection]）。グローバル制御器の接続はネットワークのマップのみ（変数の順序を参照）
    • OPF: no method on the model classes. SolverOPF reads tab_parameter of the buses, components, and branches and builds the problem itself, as SolverPF does for the power flow (see OPF customization).OPF: モデルのクラスにメソッドなし。SolverOPF が母線・機器・ブランチの tab_parameter を読み取って問題を構築（潮流計算の SolverPF と同じ。OPF のカスタマイズを参照）
  4. Edits only record; analyses check編集は記録するだけ、確認は解析が行う

    Editing a parameter or a mode only updates the value and records what became stale; nothing is rebuilt per edit. An analysis checks the flags when it starts (see Edit handling).

    パラメータやモードの編集は、値の更新と、古くなったものの記録のみ。編集ごとの再構築なし。フラグの確認は解析の開始時（モデル編集の扱いを参照）。

Components and controllers機器と制御器

Controllers keep their own contract, different from Component on purpose. A component outputs the current I to the network and exposes its outputs Y and states x to its controllers; its outputs depend on x and V only, not on u. A controller outputs only signals that drive inputs (of the component or of a local controller). No model function receives the bus current. Every connection is made by name and listed in the connection map of net.get_variable_map (see Variable order).

制御器は、意図的に Component と異なる独自の契約。機器はネットワークへ電流 I を出力し、出力 Y と状態 x を制御器に公開。機器の出力は x と V だけに依存し、u には非依存。制御器の出力は入力（機器またはローカル制御器の入力）を駆動する信号のみ。母線電流を受け取るモデル関数はなし。接続はすべて名前で、net.get_variable_map の接続表に一覧（変数の順序を参照）。

  • Observing. A local controller reads the component it is attached to (for a PSS under an AVR, the component above them) by the names of its inputs sv_u:観測: ローカル制御器は、接続先の機器（AVR の下の PSS では、その上の機器）を入力名 sv_u で読む
    • A name in the component's sv_y reads that output; otherwise a name in its sv_x reads that state. When both have the name, the output wins.機器の sv_y にある名前はその出力、なければ sv_x にある名前はその状態。両方にあれば出力が優先
    • The reserved input names Xall and Yall observe all the states and all the outputs of the component.予約された入力名 Xall・Yall: 機器のすべての状態・すべての出力を観測
    • X and Y are not reserved: an input with either name is an error.X と Y は予約名ではない。どちらかの名前の入力はエラー
    • An input with the name of an output of a nested controller (for example Vpss) reads that output; any other input stays at its equilibrium.入れ子の制御器の出力と同じ名前の入力（例: Vpss）はその出力を読む。それ以外の入力は平衡点の値のまま
    • A local controller receives the voltage V of the bus of its component.ローカル制御器: 機器の母線の電圧 V を受け取り
    • A global controller reads, on each component it controls, the output (else the state) named by each input sv_u, and receives the voltages of all buses in V.グローバル制御器: 制御する各機器の、入力名 sv_u の出力（なければ状態）を読み、全母線の電圧を V で受け取り
  • Driving.駆動
    • The outputs sv_y of a local controller drive the inputs of the same name of the component, or of the controller above it.ローカル制御器の出力 sv_y が、機器またはその上の制御器の同じ名前の入力を駆動
    • An output of a global controller, for each controlled unit, drives every local controller of the unit (nested ones included) with an input of that name; when there is none, the input of that name of the component. A local controller input it drives receives its value without the global controller plus the output. add_global_controller prints where each output goes (INFO), and an edit of the local controllers that changes it prints the change (GUILDA:Component:GconRouteChanged).グローバル制御器の出力: 制御対象ごとに、同名の入力を持つその機器のすべてのローカル制御器（入れ子を含む）を駆動。ない場合は機器の同名の入力。駆動されたローカル制御器の入力の値は「グローバル制御器がないときの値 + 出力」。各出力の接続先は add_global_controller が表示（INFO）。ローカル制御器の編集で接続先が変われば、その変化を表示（GUILDA:Component:GconRouteChanged）
    • A component has two top-level controllers at most, the AVR or "local" controller and the governor, and they drive different inputs (for example Vfield and Pmech).機器の最上位の制御器は高々2つ: AVR または "local" の制御器とガバナ。駆動する入力は別々（例: Vfield と Pmech）
    • The sources into one input are summed: an input disturbance of a scenario or a global controller on such an input of the component adds to the output of the local controller, in the simulation and in get_sys.同じ入力への源は加算。機器のそのような入力へのシナリオの入力外乱やグローバル制御器は、ローカル制御器の出力に加算（シミュレーションでも get_sys でも）

Working data of analyses解析の作業データ

Per-run working data of an analysis is not model data. The simulation keeps none on the models: SolverODE builds the positions and the state of each phase in its run context ctx. The remaining working data on the model classes is that of the continuation power flow.

解析の実行ごとの作業データはモデルのデータではない。シミュレーションはモデルに保持しない: SolverODE が位置とフェーズごとの状態を実行の文脈 ctx に構築。モデルクラスに残る作業データは連続潮流計算のもの。

  • Data: iv_CPFV / iv_CPFX / f_PQ2Bus.対象: iv_CPFV / iv_CPFX / f_PQ2Bus
  • Write access: SolverCPF only. SolverODE and Scenario only read the network.書き込み: SolverCPF のみ。SolverODE と Scenario はネットワークを読むだけ
  • Side effects of a simulation: API Design: Side effects.シミュレーションの副作用: API 設計: 副作用

Parent references親への参照

Each child keeps a read-only reference to its parent: Bus.a_PowerNetwork, Branch.a_PowerNetwork, Component.a_Bus, LocalController.a_Component, GlobalController.a_PowerNetwork, Scenario.a_PowerNetwork, and the parent of each Parameter. Rules:

各子は親への読み取り専用の参照を保持: Bus.a_PowerNetwork、Branch.a_PowerNetwork、Component.a_Bus、LocalController.a_Component、GlobalController.a_PowerNetwork、Scenario.a_PowerNetwork、各 Parameter の親。ルールは次のとおり。

  1. Only the parent sets and clears it設定と解除は親だけが行う

    Set by the parent's constructor or add_* method, cleared by its remove_* method, so a removed object has no parent reference.

    • Enforced by SetAccess: the property is writable only by the parent class (e.g. SetAccess={?PowerNetwork}), so no other code writes it. No setter method.
    • No class validation: [] when unset, and cleared with []. The class it holds is named by the <@Type> tag of its comment (e.g. <@Type> PowerNetwork) and shown on the class page.
    • On attaching, the parent calls the child's log_edit(..., "Topology"), which marks its equilibrium stale.

    親のコンストラクタまたは add_* メソッドが設定し、remove_* メソッドが解除。削除されたオブジェクトは親を参照しない。

    • SetAccess で強制: 書き込めるのは親クラスだけ（例: SetAccess={?PowerNetwork}）で、ほかのコードからの書き込みなし。setter メソッドなし
    • クラス検証なし: 未設定は []、解除も [] の代入。入るクラスはコメントの <@Type> タグ（例: <@Type> PowerNetwork）で示し、クラスページに表示
    • 接続時、親が子の log_edit(..., "Topology") を呼び、子の equilibrium を古いと印付け
  2. A child only reads its parent子は親を読むだけ

    For the tag path, for edit notification, and for shared settings such as the frequency.

    タグのパス、編集の通知、周波数などの共有設定のため。

  3. A child never writes upward or sideways子は上にも横にも書き込まない

    No writes to its parent or siblings, and no copy of its parent's data. Edits travel upward only as a call: log_edit calls the hook handle_edit on each layer from the edited one up to the top, and each layer changes only its own state (its own stale tags in sct_stale; the network also keeps one slack bus).

    親や兄弟への書き込みなし、親のデータのコピーも持たない。編集は呼び出しとしてだけ上へ伝達: log_edit が編集した層から最上位までの各層のフック handle_edit を呼び出し、各層は自分の状態だけを変更（sct_stale の自分の stale タグ。ネットワークは slack 母線の 1 つへの維持も）。

Identifying objects: tags, not indicesオブジェクトの識別: インデックスではなくタグ

Tag (e.g. B001)タグ（例: B001）

The permanent ID of an object. Use it in saved data and in scenarios: a disturbance names its buses, branches, and units by tag, checked against the network when it is added and again when it is simulated.

オブジェクトの恒久的な ID。保存するデータとシナリオで使用。外乱は母線・ブランチ・機器をタグで指定し、外乱の追加時とシミュレーション時にネットワークと照合。

Index (e.g. net.a_Bus{3})インデックス（例: net.a_Bus{3}）

Only the current position. It shifts after remove_*, so never store it.

現在の位置にすぎない。remove_* の後にずれるため、保存しない。

  • Automatic tag: the largest number in use plus one (buses B###, branches ###, components per bus).自動で付くタグ: 使用中の最大の番号 + 1（母線は B###、ブランチは ###、機器は母線ごと）
  • A number is not reused while a larger one exists, so a new tag never names an existing or earlier object.より大きい番号が存在する間は番号を再利用しない。新しいタグが既存または過去のオブジェクトを指すことはない
  • Global controller tag: chosen by the user, and must be unique.グローバル制御器のタグ: ユーザーが選択。一意であること
  • Every tag is a valid MATLAB variable name (isvarname: a letter first, then letters, digits and _), because tags name OPF variables and constraints and struct fields; any other tag stops with GUILDA:LayerPackage:InvalidTag. Write LINE20_1, not LINE20-1.タグはすべて MATLAB の変数名として有効な文字列（isvarname: 英字で始まり、英字・数字・_ のみ）。OPF の変数・制約の名前や struct のフィールド名に使うため。それ以外のタグは GUILDA:LayerPackage:InvalidTag で停止。LINE20-1 ではなく LINE20_1

Solver settings of analyses解析のソルバー設定

Persistent defaults: GUILDA.setting, net.solver_*永続的な既定値: GUILDA.setting、net.solver_*

Each analysis takes its settings from its section of GUILDA.setting (PowerFlowCalculation, OptimalPowerFlow, ContinuationPowerFlow, TimeSimulation, Linearization), read by the solver's get_options at each run. The solver objects keep only the conditions of their network (OPF: Cost, Constraint, DefaultCost, ReferenceBus; CPF: LoadBus). A change made in either place stays, so repeated runs keep the last settings.

各解析の設定は GUILDA.setting の解析ごとのセクション（PowerFlowCalculation、OptimalPowerFlow、ContinuationPowerFlow、TimeSimulation、Linearization）。実行のたびにソルバーの get_options が読み込み。ソルバーオブジェクトが保持するのはネットワークの条件のみ（OPF: Cost、Constraint、DefaultCost、ReferenceBus。CPF: LoadBus）。どちらの変更も残るため、繰り返し実行しても最後の設定を維持。

Run-time Name-Value options実行時の Name-Value オプション

Override the settings and conditions for that call only. Neither GUILDA.setting nor the solver changes.

その呼び出しに限り設定と条件を上書き。GUILDA.setting とソルバーは不変。

  • solver_* properties: class-validated (solver_PF SolverPF {mustBeScalarOrEmpty}, ...); a subclass of the network may replace a solver with a subclass of it
  • net.solver_PF: no settings; keeps the last converged solution (WarmStart) and a cache of the admittance matrix and the power equations, checked against the revision counters n_revY, n_revPF, n_revTopology of the network (increased by handle_edit)
  • net.solver_OPF: keeps the conditions Cost, Constraint, DefaultCost, ReferenceBus (public properties); also keeps the bus voltages of the last solved AC OPF (WarmStart) and the problem it built last, checked against the network (by object), its revision counter n_revOPF (every n_revPF edit, the operation and OPF parameters, tags, Hz), the settings, the start and the variable bounds
  • net.solver_CPF: keeps the condition LoadBus (public property); net.solver_ODE, net.solver_LIN: no settings
  • net.solver_PF and net.solver_OPF discard the kept solution only on a Topology edit of the network; net.reset_solver() replaces every solver
  • solver_* プロパティ: クラス検証あり（solver_PF SolverPF {mustBeScalarOrEmpty} など）。ネットワークのサブクラスはソルバーをそのサブクラスに置き換え可能
  • net.solver_PF: 設定なし。最後の収束解（WarmStart）と、アドミタンス行列・電力方程式のキャッシュを保持。ネットワークの版番号 n_revY、n_revPF、n_revTopology（handle_edit が増加）で照合
  • net.solver_OPF: 条件 Cost、Constraint、DefaultCost、ReferenceBus（public プロパティ）を保持。最後に解いた AC OPF の母線電圧（WarmStart）と、最後に構築した問題も保持。ネットワーク（オブジェクト）、その版番号 n_revOPF（n_revPF の編集すべて、operation・OPF パラメータ、タグ、Hz）、設定、初期点、変数の上下限で照合
  • net.solver_CPF: 条件 LoadBus（public プロパティ）を保持。net.solver_ODE、net.solver_LIN: 設定なし
  • net.solver_PF と net.solver_OPF が保持した解を破棄するのはネットワークの Topology の編集のときのみ。net.reset_solver() はすべてのソルバーを置き換え

Settings files and their version設定ファイルとその版

  • Each category of GUILDA.setting is a default file @GUILDA/config/Default<Category>.json (shipped): per setting Value, Type (double, logical, string, select with options) and Description, plus a top-level version
  • The values of the user go to @GUILDA/user/Default<Category>.json (not committed) with the version of the default file: written by Apply in the window, by GUILDA.setting(Category, Name=Value) and at startup
  • GUILDA.config reads the defaults merged with the user values and caches them; writing the user files reads them again, so the next call and analysis use the new values
  • A user file whose version differs from that of the default file, or has none, is ignored and written again with the defaults; the category is reported as INFO (GUILDA:GUILDA:ConfigReset)
  • Raise the version of a default file when you change a default value, a key name, the Type or options, or the structure of the file. The users then start from the new defaults, so no conversion of old user files is needed. A change of Description only needs no new version
  • GUILDA.setting の各カテゴリは既定ファイル @GUILDA/config/Default<Category>.json（配布物）。設定ごとに Value、Type（double、logical、string、options つきの select）、Description。最上位に version
  • 利用者の値は @GUILDA/user/Default<Category>.json（コミットしない）に既定ファイルの version とともに保存。書き込むのはウィンドウの Apply、GUILDA.setting(Category, Name=Value)、起動時の処理
  • GUILDA.config は既定値に利用者の値を重ねて読み、キャッシュ。利用者のファイルを書くと読み直すため、直後の呼び出しと解析が新しい値を使用
  • 利用者のファイルの version が既定ファイルと違う、または無い場合は、そのファイルを無視して既定値で書き直し。カテゴリ名を INFO（GUILDA:GUILDA:ConfigReset）で通知
  • 既定ファイルの version を上げるのは、既定値、キー名、Type や options、ファイルの構造を変えたとき。利用者は新しい既定値から始めるため、旧ファイルの変換は不要。Description だけの変更では上げない

System data (line constants, power-flow specifications, limits) is not a solver setting: set it beforehand on the model objects through properties and tab_parameter (see API Design, rule 2).

系統データ（線路定数、潮流計算の指定値、制限値）はソルバーの設定ではない。プロパティと tab_parameter を通じて、事前にモデルオブジェクトに設定（API 設計のルール 2 を参照）。

Handling of model editsモデル編集の扱い

Each layer keeps what of its own is out of date in sct_stale (LayerPackage): one field per stale tag of the class, each a string column of messages, empty when up to date. The constructor creates the fields with the message "initialize has not been run": PowerNetwork powerflow and odefcn (the network frequency), and input (inputs edited with Component.set_input; created empty, kept only by initialize(Method="FixedInput")); Component, LocalController and GlobalController equilibrium and odefcn (the f_* handles); Bus and Branch none. An edit calls log_edit(log, tag) on the edited layer, which calls the hook handle_edit(a_layer, tag, log) on every layer from there up to the top; a_layer is the edited layer, the owner for a Parameter container. Each class compares a_layer == obj and the tag, and appends the message "tags of the edited layer joined by /: log" (e.g. dynamics/SG1B001/B001/IEEE9bus: edit D: 2 -> 2.1) to its own fields for the edits that affect them (obj.sct_stale.equilibrium(end+1,1) = log). Each class also clears only its own fields. PowerNetwork.handle_edit also keeps one slack bus. The tags of edits: the parameter groups (dynamics, powerflow, base, operation, OPF, graph), Topology, Slack, Tag, input (set_input).

各層は自分の古くなった部分を sct_stale（LayerPackage）に保持: クラスの stale タグごとに 1 フィールド、値はメッセージの string 列、空なら最新。コンストラクタがメッセージ "initialize has not been run" 付きでフィールドを作成: PowerNetwork は powerflow と odefcn（系統周波数）と input（Component.set_input で編集した入力。空で作成し、保つのは initialize(Method="FixedInput") のみ）、Component・LocalController・GlobalController は equilibrium と odefcn（f_* ハンドル）、Bus と Branch はなし。編集は編集した層の log_edit(log, tag) を呼び出し、それがその層から最上位までの各層のフック handle_edit(a_layer, tag, log) を呼び出し。a_layer は編集した層（Parameter コンテナは所有者）。各クラスは a_layer == obj とタグを比べ、影響を受ける自分のフィールドに、メッセージ "編集した層からのタグを / で連結: log"（例 dynamics/SG1B001/B001/IEEE9bus: edit D: 2 -> 2.1）を追加（obj.sct_stale.equilibrium(end+1,1) = log）。消去も各クラスが自分のフィールドのみ。PowerNetwork.handle_edit は slack 母線を 1 つに維持する役割も。編集のタグ: パラメータの区分（dynamics、powerflow、base、operation、OPF、graph）、Topology、Slack、Tag、input（set_input）。

Only PowerNetwork.initialize brings the layers up to date. It solves the operating point (power flow, AC OPF or "FixedInput") when Method is given or powerflow is stale and writes it with Bus.set_equilibrium; then the buses initialize their components (stale handles rebuilt with set_odefcn, a stale equilibrium recomputed from the held V and I) and those their local controllers, and the global controllers come last. Each layer decides from its own fields; the network decides only about its own power flow and clears its fields at the end. The analyses only check: each reads, inline and in the loops it already has, the stale tags it needs (sct_stale has public GetAccess) and changes nothing. A network Hz edit reaches no child: it marks the network odefcn, which every analysis reads; in initialize each component and controller rebuilds its handles when its odefcn is not empty or the frequency it built them with (r_odefcnHz) differs from get_Hz().

層を最新にするのは PowerNetwork.initialize のみ。Method の指定時か powerflow が古いときに運転点（潮流計算、AC OPF、"FixedInput"）を解き、Bus.set_equilibrium で書き込み。続いて母線が機器を、機器がローカル制御器を初期化（古いハンドルは set_odefcn で再構築、古い平衡点は保持中の V と I から再計算）、大域制御器は最後。各層が自分のフィールドから判断し、ネットワークが判断するのは自分の潮流のみ、最後に自分のフィールドを消去。解析は確認のみ: 各解析が、必要な stale タグ（sct_stale、GetAccess は public）を既存のループの中でその場で読み取り、何も変更しない。ネットワークの Hz の編集はどの子にも届かない: ネットワークの odefcn に記録し、どの解析もそれを読み取る。initialize では各機器・制御器が、自分の odefcn が空でないか、ハンドル作成時の周波数（r_odefcnHz）が get_Hz() と異なればハンドルを再構築。

OPF customizationOPF のカスタマイズ

The model objects hold only parameters. SolverOPF.build_problem reads them and builds one optimproblem; no OPF state lives on a bus, component, or branch. The OPF is used by no other analysis, so it follows the power flow (the solver pulls the data). The dynamics keep cached f_* handles on the classes because several analyses (simulate, get_sys) reuse them.

モデルのオブジェクトはパラメータのみを保持。SolverOPF.build_problem がそれを読み取り、1 つの optimproblem を構築。母線・機器・ブランチに OPF の状態なし。OPF を使う解析はほかにないため、潮流計算と同じくソルバーがデータを取得する方式。動特性は複数の解析（simulate、get_sys）が再利用するため、キャッシュした f_* ハンドルをクラスに保持。

Per-unit system単位法
  • Voltages, currents, powers (P, Q), and branch constants (R, X, C): per unit on the system base (the system baseMVA on PowerNetwork).電圧、電流、電力（P、Q）、ブランチの定数（R、X、C）: システム基準（PowerNetwork にあるシステムの baseMVA）の単位法
  • Component dynamics parameters: also per unit on the system base.機器の動特性パラメータ: 同じくシステム基準の単位法
  • Component.baseMVA: the machine rating, used only to share reactive power.Component.baseMVA: 機器の定格。無効電力の分担にのみ使用
  • No class converts physical units: Bus.baseKV is stored but not used in any calculation.物理単位を換算するクラスなし。Bus.baseKV は保存のみで、計算には不使用

Time and frequency時間と周波数
  • Time t: seconds.時間 t: 秒
  • Nominal frequency Hz: a system base value on PowerNetwork; models read it with get_Hz().定格周波数 Hz: PowerNetwork にあるシステムの基準値。モデルは get_Hz() で読む
  • Argument omega0 passed to models: this nominal frequency in Hz; models multiply by 2π themselves (e.g. ddelta = 2*pi*omega0*omega).モデルに渡す引数 omega0: Hz 単位のこの定格周波数。2π はモデル自身が乗算（例: ddelta = 2*pi*omega0*omega）
  • Rotor speed omega: a per-unit deviation.回転子速度 omega: 単位法の偏差
Current direction電流の向き
  • A component's current I is the current it injects into its bus, so P + jQ = V·conj(I) is positive for generation.機器の電流 I: 機器が母線に注入する電流。P + jQ = V·conj(I) は発電で正
  • A load has negative injection (e.g. impedance load I = -V/Z).負荷の注入は負（例: インピーダンス負荷 I = -V/Z）
  • Network equation: I_bus = Y·V, where I_bus is the sum of the injections at each bus.ネットワーク方程式: I_bus = Y·V。I_bus は各母線での注入の和
Complex vs [real; imag]複素数と [real; imag]
  • Complex numbers: stored equilibria and power-flow results (c_*, cv_*), admittance matrices, and the inputs of get_equilibrium(V, I, P, Q).複素数: 保存される平衡点と潮流計算の結果（c_*、cv_*）、アドミタンス行列、get_equilibrium(V, I, P, Q) の入力
  • Real 2×1 vectors [re; im]: V passed to fcn_* and Jacobi_*, and the state vector of the simulator. Inside a model, convert with [1, 1j]*V.実数の 2×1 ベクトル [re; im]: fcn_* と Jacobi_* に渡される V、シミュレータの状態ベクトル。モデル内の変換は [1, 1j]*V
  • fcn_I returns a complex scalar.fcn_I の返り値は複素数のスカラー
The ports of a linearized component or bus are [Vre; Vim] to [Ire; Iim] for port="V2I", and the inverse for port="I2V".近似線形化した機器や母線のポート: port="V2I" では [Vre; Vim] から [Ire; Iim]、port="I2V" ではその逆。
