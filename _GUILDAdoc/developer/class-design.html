Class Designクラス設計

How the model classes relate as a whole, and the rules across them: ownership, parent references, identity, settings, edits, variable order. What one class owns and does: on its Reference page. Read before adding a property or a method to a model class.このページでは、モデルクラス全体の関係と、クラスをまたぐルール（所有、親への参照、識別、設定、編集、変数の順序）を説明します。1つのクラスが所有するもの・行う処理は、各クラスのリファレンスページにあります。モデルクラスにプロパティ・メソッドを追加する前に、一読してください。

The class structure is stable on purpose: other developers build on it. These rules decide where data and logic go inside the existing classes, instead of adding new classes. They apply to all code in GUILDA.クラス構成は意図的に固定しています。ほかの開発者がその上に開発を重ねるためです。ここでのルールは、新しいクラスを導入するためではなく、既存クラスの中でのデータとロジックの置き場所を決めるためにあります。GUILDA のすべてのコードに適用します。

Design principles設計原則

  1. No data is held by two classes同じデータを2つのクラスで持たない

    Each value has a single owner. Anything derived from it is a Dependent property that reads the owner on access. Do not write code that copies a value and keeps the copies in sync: it is a source of bugs.

    各値の所有者は1つです。導出できるものは、アクセス時に所有者を読む Dependent プロパティにします。値をコピーしてコピー同士を同期させるコードは、バグの原因になるため禁止です。

    Examples: PowerNetwork.cv_Vequilibrium / cv_Iequilibrium / rv_Xequilibrium (collected from the buses), Branch.cv_Vequilibrium / cv_Iequilibrium (from the end buses and its own admittance), Component.tab_parameter (assembled from the Parameter objects), Component.rv_Xequilibrium_all (the component plus its controllers).

    例: PowerNetwork.cv_Vequilibrium / cv_Iequilibrium / rv_Xequilibrium（母線から収集）、Branch.cv_Vequilibrium / cv_Iequilibrium（両端の母線と自身のアドミタンスから計算）、Component.tab_parameter（Parameter オブジェクトから組み立て）、Component.rv_Xequilibrium_all（機器とその制御器）があります。

  2. Data and functions follow real-world rolesデータと機能は現実の役割に従う

    A class holds what the physical element has and computes what the physical element determines:

    クラスは、物理的な要素が持つものを保持し、要素が決めるものを計算します。

    • Branch: its impedances; builds its own admittance matrix.ブランチは、自身のインピーダンスを持ち、自身のアドミタンス行列を作ります
    • Bus: the algebraic variable, its voltage V.母線は、代数変数である電圧 V を持ちます
    • Components and controllers: the differential equations and output equations.機器と制御器は、微分方程式と出力方程式を持ちます
  3. Same method name, same meaning on every layer同じメソッド名は、どの階層でも同じ意味

    Same meaning and same shape of inputs and outputs on every class. A higher layer aggregates the lower ones.

    どのクラスでも同じ意味、同じ入出力の形です。上位の階層が下位の階層を集約します。

    • get_sys: the linearized model of each layer.get_sys: 各階層の近似線形化モデル
      • LocalController: the controller alone.LocalController: 制御器単体
      • Component: the component and its controllers.Component: 機器とその制御器
      • Bus: the aggregate of its components.Bus: その機器の集約
      • PowerNetwork: the whole system.PowerNetwork: システム全体
      • On LocalController, Component, and Bus: input, state, and output names are unique, and states are not outputs. An output with the name of a state of its owner is labelled Y_ + name.LocalController、Component、Bus では、入力・状態・出力の名前を一意にし、状態は出力に含めません。所有者の状態と同じ名前の出力には、Y_ + 名前のラベルを付けます
      • Inputs, states, and outputs of each layer: on the get_sys method page of each class in the Reference.各階層の入力・状態・出力は、リファレンスにある各クラスの get_sys のページに載っています
    • get_admittance_matrix: on Branch, its 2×2 matrix; on PowerNetwork, the matrix of the whole network.get_admittance_matrix は、Branch では自身の 2×2 行列を、PowerNetwork ではネットワーク全体の行列を返します
    • get_variable_map: on Component and Bus, the restriction of the network map: the rows of variables and signals that belong to it, in the same relative order, and the connections inside it ([tab, tab_connection] on a component, [tab, c_idx, tab_connection] on a bus). The connections of the global controllers are only in the network map (see Variable order).get_variable_map は、Component と Bus では、ネットワークのマップを自身の分に絞ったものを返します。中身は、自身に属する変数と信号の行（相対順序は同じ）と、内部の接続です（機器は [tab, tab_connection]、母線は [tab, c_idx, tab_connection]）。グローバル制御器の接続はネットワークのマップだけにあります（変数の順序を参照）
    • OPF: no method on the model classes. The network collects tab_parameter of the buses, components, and branches into three tables and hands them to SolverOPF, which builds the problem from them and reads no model object (see OPF customization). The power flow is assembled the same way: calculate_powerflow collects Bus.get_pf_condition and the admittance matrix and hands them to SolverPF, which reads no model object.OPF のためのメソッドは、モデルのクラスにはありません。ネットワークが母線・機器・ブランチの tab_parameter を 3 つの表にまとめて SolverOPF に渡し、SolverOPF はその表から問題を構築します。モデルのオブジェクトは読みません（OPF のカスタマイズを参照）。潮流計算も同じ方式です。calculate_powerflow が Bus.get_pf_condition とアドミタンス行列を集めて SolverPF に渡し、SolverPF はモデルのオブジェクトを読みません
  4. Edits only record; analyses check編集は記録するだけ、確認は解析が行う

    Editing a parameter or a mode only updates the value and records what became stale; nothing is rebuilt per edit. An analysis checks the flags when it starts (see Edit handling).

    パラメータやモードの編集では、値の更新と、古くなったものの記録だけを行います。編集ごとの再構築はしません。フラグは解析の開始時に確認します（モデル編集の扱いを参照）。

Components and controllers機器と制御器

Controllers keep their own contract, different from Component on purpose. A component outputs the current I to the network and exposes its outputs Y and states x to its controllers; its outputs depend on x and V only, not on u. A controller outputs only signals that drive inputs (of the component or of a local controller). No model function receives the bus current. Every connection is made by name and listed in the connection map of net.get_variable_map (see Variable order).

制御器は、意図的に Component と異なる独自の契約を持ちます。機器はネットワークへ電流 I を出力し、出力 Y と状態 x を制御器に公開します。機器の出力は x と V だけに依存し、u には依存しません。制御器の出力は、入力（機器またはローカル制御器の入力）を駆動する信号だけです。母線電流を受け取るモデル関数はありません。接続はすべて名前で行い、net.get_variable_map の接続表に一覧があります（変数の順序を参照）。

  • Observing. A local controller reads the component it is attached to (for a PSS under an AVR, the component above them) by the names of its inputs sv_u:観測: ローカル制御器は、接続先の機器（AVR の下の PSS では、その上の機器）を入力名 sv_u で読みます
    • A name in the component's sv_y reads that output; otherwise a name in its sv_x reads that state. When both have the name, the output wins.機器の sv_y にある名前はその出力を、なければ sv_x にある名前はその状態を読みます。両方にあれば出力が優先されます
    • The reserved input names Xall and Yall observe all the states and all the outputs of the component.予約された入力名 Xall・Yall を使うと、機器のすべての状態・すべての出力を観測できます
    • X and Y are not reserved: an input with either name is an error.X と Y は予約名ではありません。どちらかの名前の入力はエラーになります
    • An input with the name of an output of a nested controller (for example Vpss) reads that output; any other input stays at its equilibrium.入れ子の制御器の出力と同じ名前の入力（例: Vpss）はその出力を読みます。それ以外の入力は平衡点の値のままです
    • A local controller receives the voltage V of the bus of its component.ローカル制御器は、機器の母線の電圧を V で受け取ります
    • A global controller reads, on each component it controls, the output (else the state) named by each input sv_u, and receives the voltages of all buses in V.グローバル制御器は、制御する各機器から入力名 sv_u の出力（なければ状態）を読み、全母線の電圧を V で受け取ります
  • Driving.駆動
    • The outputs sv_y of a local controller drive the inputs of the same name of the component, or of the controller above it.ローカル制御器の出力 sv_y が、機器またはその上の制御器の同じ名前の入力を駆動します
    • An output of a global controller, for each controlled unit, drives every local controller of the unit (nested ones included) with an input of that name; when there is none, the input of that name of the component. A local controller input it drives receives its value without the global controller plus the output. add_global_controller prints where each output goes (INFO), and an edit of the local controllers that changes it prints the change (GUILDA:Component:GconRouteChanged).グローバル制御器の出力は、制御対象ごとに、同名の入力を持つその機器のすべてのローカル制御器（入れ子を含む）を駆動します。ない場合は機器の同名の入力を駆動します。駆動されたローカル制御器の入力の値は「グローバル制御器がないときの値 + 出力」です。各出力の接続先は add_global_controller が表示します（INFO）。ローカル制御器の編集で接続先が変われば、その変化を表示します（GUILDA:Component:GconRouteChanged）
    • A component has two top-level controllers at most, the AVR or "local" controller and the governor, and they drive different inputs (for example Vfield and Pmech).機器の最上位の制御器は高々2つで、AVR または "local" の制御器とガバナです。駆動する入力は別々です（例: Vfield と Pmech）
    • The sources into one input are summed: an input disturbance of a scenario or a global controller on such an input of the component adds to the output of the local controller, in the simulation and in get_sys.同じ入力への源は加算します。機器のそのような入力へのシナリオの入力外乱やグローバル制御器は、ローカル制御器の出力に加算します（シミュレーションでも get_sys でも）

Working data of analyses解析の作業データ

Per-run working data of an analysis is not model data. The simulation keeps none on the models: net.build_simulation_data gathers the data of a run, and SolverODE builds the positions and the state of each phase in its run context ctx from that data only. The remaining working data on the model classes is that of the continuation power flow.

解析の実行ごとの作業データは、モデルのデータではありません。シミュレーションはモデルに何も保持しません。実行のデータは net.build_simulation_data が集め、SolverODE はそのデータだけから、位置とフェーズごとの状態を実行の文脈 ctx に構築します。モデルクラスに残る作業データは、連続潮流計算のものだけです。

  • Data: iv_CPFV / iv_CPFX / f_PQ2Bus.対象は iv_CPFV、iv_CPFX、f_PQ2Bus です
  • Write access: SolverCPF only. Scenario only reads the network; SolverODE reads no network.書き込むのは SolverCPF だけです。Scenario はネットワークを読むだけで、SolverODE はネットワークを読みません
  • Side effects of a simulation: API Design: Side effects.シミュレーションの副作用はAPI 設計: 副作用を参照してください

Parent references親への参照

Each child keeps a read-only reference to its parent: Bus.a_PowerNetwork, Branch.a_PowerNetwork, Component.a_Bus, LocalController.a_Component, GlobalController.a_PowerNetwork, Scenario.a_PowerNetwork, and the parent of each Parameter. Rules:

各子は、親への読み取り専用の参照を持ちます。Bus.a_PowerNetwork、Branch.a_PowerNetwork、Component.a_Bus、LocalController.a_Component、GlobalController.a_PowerNetwork、Scenario.a_PowerNetwork、各 Parameter の親がそれにあたります。ルールは次のとおりです。

  1. Only the parent sets it設定は親だけが行う

    Set by the parent's constructor or add_* method. A model object never exists without its parent: it is created only by the parent (rule 2) and deleted when it is taken out (rule 3). A scenario is the exception: remove_scenario clears its reference, and the scenario can be added again.

    • Enforced by SetAccess: the property is writable only by the parent class (e.g. SetAccess={?PowerNetwork}), so no other code writes it. No setter method.
    • No class validation: [] only while the object is being built, before the parent sets it. The class it holds is named by the <@Type> tag of its comment (e.g. <@Type> PowerNetwork) and shown on the class page.
    • On attaching, the parent calls the child's log_edit(..., "Topology"), which marks its equilibrium stale.

    親のコンストラクタまたは add_* メソッドが設定します。モデルのオブジェクトは親なしでは存在しません。作成するのは親だけで（規則 2）、取り外すと削除します（規則 3）。例外はシナリオで、remove_scenario が参照を解除し、もう一度追加できます。

    • SetAccess で強制します。書き込めるのは親クラスだけ（例: SetAccess={?PowerNetwork}）で、ほかのコードからは書き込みません。setter メソッドはありません
    • クラス検証はしません。[] になるのは作成の途中、親が設定する前だけです。入るクラスはコメントの <@Type> タグ（例: <@Type> PowerNetwork）で示し、クラスページに表示します
    • 接続時、親が子の log_edit(..., "Topology") を呼び、子の equilibrium を古いと印付けます
  2. Only the parent creates it作成は親だけが行う

    A model object is built from its model key by the parent: PowerNetwork.add_bus, add_branch and add_global_controller, Bus.add_component and replace_component, Component.add_local_controller.

    • The constructor of every concrete class is accessible only from that parent class: Access={?Bus} for components, {?Component} for local controllers, {?PowerNetwork} for branches and global controllers. A direct call stops with MATLAB:class:MethodRestricted.
    • The builder makes the handle with str2func inside its method, so the access check passes (GUILDA.keymap).
    • A class without its own constructor inherits the public default one, so each concrete class declares its constructor with this access, even when it only calls the superclass.

    モデルのオブジェクトは、親がモデルキーから作成します: PowerNetwork.add_bus、add_branch、add_global_controller、Bus.add_component、replace_component、Component.add_local_controller。

    • 具体クラスのコンストラクタは、親クラスからだけ呼べます。機器は Access={?Bus}、ローカル制御器は {?Component}、ブランチとグローバル制御器は {?PowerNetwork} です。直接呼ぶと MATLAB:class:MethodRestricted で止まります
    • 作成側はメソッドの中で str2func によりハンドルを作るため、アクセスの検査を通ります（GUILDA.keymap）
    • コンストラクタを持たないクラスは、公開の既定のコンストラクタを継承します。そのため具体クラスは、スーパークラスを呼ぶだけでも、このアクセスでコンストラクタを宣言します
  3. A removed object is deleted取り外したオブジェクトは削除する

    remove_bus, remove_branch, remove_global_controller, remove_component, replace_component, remove_local_controller and the replacement of a controller by add_local_controller take the object out of the parent and delete it, with the objects under it (tools.delete_layers): a bus with its components, a component or a controller with its local controllers.

    • A handle the user still holds becomes invalid (isvalid is false); using it stops with MATLAB's error for a deleted object.
    • Nothing else refers to a removed object: results, scenarios and edit messages keep tags, a ResultLIN keeps the network, a global controller's units cannot be removed while it is on the network, and the model view (DrawerModelGUI) shows "The model has been deleted."

    remove_bus、remove_branch、remove_global_controller、remove_component、replace_component、remove_local_controller、add_local_controller による制御器の置き換えは、オブジェクトを親から外し、その下のオブジェクトごと delete します（tools.delete_layers）。母線は機器ごと、機器と制御器はローカル制御器ごと削除します。

    • 利用者が持つハンドルは無効になります（isvalid が false）。使うと MATLAB の削除済みオブジェクトのエラーで止まります
    • 外したオブジェクトをほかに参照するものはありません。結果・シナリオ・編集のメッセージはタグを持ち、ResultLIN はネットワークを持ちます。グローバル制御器の制御対象は、制御器がネットワークにある間は削除できません。モデルの表示（DrawerModelGUI）は "The model has been deleted." を表示します
  4. No check for a missing parent親の欠落を検査しない

    Rules 1 to 3 rule out a model object without its parent or with a parent of another class, so methods do not test for it (isempty(obj.a_Bus), isa(comp, "Component")) and have no path for an object used alone.

    • Kept: a test of the layer type that chooses what to do (e.g. isa(layer, "Bus") in SolverLIN.point_vector), a bus without components, a network without buses, and the checks of user input.
    • Kept: a check for a state during construction, before the parent sets the reference (e.g. LayerPackage.set.s_tag, local_LQR.log_change).

    規則 1〜3 により、親のないオブジェクトや、親が別のクラスのオブジェクトは存在しません。そのためメソッドはそれを検査せず（isempty(obj.a_Bus)、isa(comp, "Component")）、単体で使うための経路も持ちません。

    • 残すもの: 層の型で処理を選ぶ検査（例: SolverLIN.point_vector の isa(layer, "Bus")）、機器のない母線、母線のないネットワーク、利用者の入力の検査
    • 残すもの: 作成の途中、親が参照を設定する前の状態の検査（例: LayerPackage.set.s_tag、local_LQR.log_change）
  5. A child only reads its parent子は親を読むだけ

    For the tag path, for edit notification, and for shared settings such as the frequency.

    タグのパス、編集の通知、周波数などの共有設定に使います。

  6. A child never writes upward or sideways子は上にも横にも書き込まない

    No writes to its parent or siblings, and no copy of its parent's data. Edits travel upward only as a call: log_edit calls the hook handle_edit on each layer from the edited one up to the top, and each layer changes only its own state (its own stale tags in sct_stale; the network also keeps one slack bus).

    親や兄弟には書き込まず、親のデータのコピーも持ちません。編集は呼び出しとしてだけ上へ伝えます。log_edit が編集した層から最上位までの各層のフック handle_edit を呼び出し、各層は自分の状態だけを変更します（sct_stale の自分の stale タグ。ネットワークは slack 母線を 1 つに保つ処理も行います）。

Identifying objects: tags, not indicesオブジェクトの識別: インデックスではなくタグ

Tag (e.g. B001)タグ（例: B001）

The permanent ID of an object. Use it in saved data and in scenarios: a disturbance names its buses, branches, and units by tag, checked against the network when it is added and again when it is simulated.

オブジェクトの恒久的な ID です。保存するデータとシナリオで使います。外乱は母線・ブランチ・機器をタグで指定し、外乱の追加時とシミュレーション時にネットワークと照合します。

Index (e.g. net.a_Bus{3})インデックス（例: net.a_Bus{3}）

Only the current position. It shifts after remove_*, so never store it.

現在の位置にすぎません。remove_* の後にずれるため、保存しません。

  • Automatic tag: the largest number in use plus one (buses B###, branches ###, components per bus).自動で付くタグは、使用中の最大の番号 + 1 です（母線は B###、ブランチは ###、機器は母線ごと）
  • A number is not reused while a larger one exists, so a new tag never names an existing or earlier object.より大きい番号が存在する間は、番号を再利用しません。新しいタグが既存または過去のオブジェクトを指すことはありません
  • Global controller tag: chosen by the user, and must be unique.グローバル制御器のタグは、ユーザーが選びます。一意でなければなりません
  • Every tag is a valid MATLAB variable name (isvarname: a letter first, then letters, digits and _), because tags name OPF variables and constraints and struct fields; any other tag stops with GUILDA:LayerPackage:InvalidTag. Write LINE20_1, not LINE20-1.タグはすべて MATLAB の変数名として有効な文字列（isvarname: 英字で始まり、英字・数字・_ のみ）です。OPF の変数・制約の名前や struct のフィールド名に使うためです。それ以外のタグは GUILDA:LayerPackage:InvalidTag で停止します。LINE20-1 ではなく LINE20_1 とします

Solver settings of analyses解析のソルバー設定

Persistent defaults: GUILDA.setting, net.solver_*永続的な既定値: GUILDA.setting、net.solver_*

Each analysis takes its settings from its section of GUILDA.setting (PowerFlowCalculation, OptimalPowerFlow, ContinuationPowerFlow, TimeSimulation, Linearization), read at each run by the analysis, which takes its options in an arguments block (calculate_powerflow, calculate_optimal_powerflow, calculate_continuation_powerflow, simulate, get_sys). The solver objects keep only the conditions of their network (CPF: LoadBus); the OPF conditions Cost, Constraint, DefaultCost, ReferenceBus are options of the call only. A change made in either place stays, so repeated runs keep the last settings.

各解析の設定は GUILDA.setting の解析ごとのセクション（PowerFlowCalculation、OptimalPowerFlow、ContinuationPowerFlow、TimeSimulation、Linearization）にあります。実行のたびに、arguments ブロックでオプションを受け取る各解析（calculate_powerflow、calculate_optimal_powerflow、calculate_continuation_powerflow、simulate、get_sys）が読み込みます。ソルバーオブジェクトが保持するのはネットワークの条件だけです（CPF: LoadBus）。OPF の条件 Cost、Constraint、DefaultCost、ReferenceBus は、呼び出しのときだけ指定するオプションです。どちらの変更も残るため、繰り返し実行しても最後の設定が維持されます。

Run-time Name-Value options実行時の Name-Value オプション

Override the settings and conditions for that call only. Neither GUILDA.setting nor the solver changes.

その呼び出しに限り設定と条件を上書きします。GUILDA.setting とソルバーは変わりません。

  • solver_* properties: class-validated (solver_PF SolverPF {mustBeScalarOrEmpty}, ...); a subclass of the network may replace a solver with a subclass of it
  • net.solver_PF: no settings; keeps only the last converged solution with its bus tags (private cv_Vwarm, sv_warmBus), used with WarmStart when the bus tags of the next run are the same in the same order. It builds the power equations at every call (no cache)
  • net.solver_OPF: no settings and no conditions; keeps only the bus voltages of the last solved AC OPF with their bus tags (private rm_Vwarm, sv_warmBus), used with WarmStart when the bus tags of the next run are the same in the same order. It builds the problem at every call (no cache)
  • net.solver_CPF: keeps the condition LoadBus (public property); net.solver_ODE, net.solver_LIN: no settings
  • net.solver_PF and net.solver_OPF ignore their kept solution when the bus tags differ; net.reset_solver() replaces every solver
  • solver_* プロパティにはクラス検証があります（solver_PF SolverPF {mustBeScalarOrEmpty} など）。ネットワークのサブクラスは、ソルバーをそのサブクラスに置き換えられます
  • net.solver_PF は設定を持ちません。保持するのは、最後の収束解とその母線のタグ（private の cv_Vwarm、sv_warmBus）だけで、次の実行の母線のタグが同じ順序で一致するときに WarmStart で使います。電力方程式は呼び出しのたびに作ります（キャッシュはありません）
  • net.solver_OPF は設定も条件も持ちません。保持するのは、最後に解いた AC OPF の母線電圧とその母線のタグ（private の rm_Vwarm、sv_warmBus）だけで、次の実行の母線のタグが同じ順序で一致するときに WarmStart で使います。問題は呼び出しのたびに構築します（キャッシュはありません）
  • net.solver_CPF は、条件 LoadBus（public プロパティ）を保持します。net.solver_ODE と net.solver_LIN は設定を持ちません
  • net.solver_PF と net.solver_OPF は、母線のタグが違えば保持した解を使いません。net.reset_solver() はすべてのソルバーを置き換えます

Settings files and their version設定ファイルとその版

  • Each category of GUILDA.setting is a default file @GUILDA/config/Default<Category>.json (shipped): per setting Value, Type (double, logical, string, select with options) and Description, plus a top-level version
  • The values of the user go to @GUILDA/user/Default<Category>.json (not committed) with the version of the default file: written by Apply in the window, by GUILDA.setting(Category, Name=Value) and at startup
  • GUILDA.config reads the defaults merged with the user values and caches them; writing the user files reads them again, so the next call and analysis use the new values
  • A user file whose version differs from that of the default file, or has none, is ignored and written again with the defaults; the category is reported as INFO (GUILDA:GUILDA:ConfigReset)
  • Raise the version of a default file when you change a default value, a key name, the Type or options, or the structure of the file. The users then start from the new defaults, so no conversion of old user files is needed. A change of Description only needs no new version
  • GUILDA.setting の各カテゴリは、既定ファイル @GUILDA/config/Default<Category>.json（配布物）にあります。設定ごとに Value、Type（double、logical、string、options つきの select）、Description を持ちます。最上位には version があります
  • 利用者の値は @GUILDA/user/Default<Category>.json（コミットしない）に既定ファイルの version とともに保存します。書き込むのは、ウィンドウの Apply、GUILDA.setting(Category, Name=Value)、起動時の処理です
  • GUILDA.config は既定値に利用者の値を重ねて読み、キャッシュします。利用者のファイルを書くと読み直すため、直後の呼び出しと解析が新しい値を使います
  • 利用者のファイルの version が既定ファイルと違う、または無い場合は、そのファイルを無視して既定値で書き直します。カテゴリ名を INFO（GUILDA:GUILDA:ConfigReset）で通知します
  • 既定ファイルの version を上げるのは、既定値、キー名、Type や options、ファイルの構造を変えたときです。利用者は新しい既定値から始めるため、旧ファイルの変換は不要です。Description だけの変更では上げません

System data (line constants, power-flow specifications, limits) is not a solver setting: set it beforehand on the model objects through properties and tab_parameter (see API Design, rule 2).

系統データ（線路定数、潮流計算の指定値、制限値）はソルバーの設定ではありません。プロパティと tab_parameter を通じて、事前にモデルオブジェクトに設定します（API 設計のルール 2を参照）。

Handling of model editsモデル編集の扱い

Each layer keeps what of its own is out of date in sct_stale (LayerPackage): one field per stale tag of the class, each a string column of messages, empty when up to date. The constructor creates the fields with the message "initialize has not been run": PowerNetwork powerflow and odefcn (the network frequency), and input (inputs edited with Component.set_input; created empty, kept only by initialize(Method="FixedInput")); Component, LocalController and GlobalController equilibrium and odefcn (the f_* handles); Bus and Branch none. An edit calls log_edit(log, tag) on the edited layer, which calls the hook handle_edit(a_layer, tag, log) on every layer from there up to the top; a_layer is the edited layer, the owner for a Parameter container. Each class compares a_layer == obj and the tag, and appends the message "tag of the edited layer: log", for a Parameter container "container tag/owner tag: log" (e.g. dynamics/B001SG1: edit D: 2 -> 2.1) to its own fields for the edits that affect them (obj.sct_stale.equilibrium(end+1,1) = log). Each class also clears only its own fields. PowerNetwork.handle_edit also keeps one slack bus. The tags of edits: the parameter groups (dynamics, powerflow, base, operation, OPF, graph), Topology, Slack, Tag, input (set_input).

各層は自分の古くなった部分を sct_stale（LayerPackage）に保持します。クラスの stale タグごとに 1 フィールドがあり、値はメッセージの string 列で、空なら最新です。コンストラクタがメッセージ "initialize has not been run" 付きでフィールドを作成します。PowerNetwork には powerflow と odefcn（系統周波数）と input（Component.set_input で編集した入力。空で作成し、保つのは initialize(Method="FixedInput") だけ）、Component・LocalController・GlobalController には equilibrium と odefcn（f_* ハンドル）を作ります。Bus と Branch にはフィールドがありません。編集は編集した層の log_edit(log, tag) を呼び出し、それがその層から最上位までの各層のフック handle_edit(a_layer, tag, log) を呼び出します。a_layer は編集した層です（Parameter コンテナでは所有者）。各クラスは a_layer == obj とタグを比べ、影響を受ける自分のフィールドに、メッセージ "編集した層のタグ: log"、Parameter コンテナは "コンテナのタグ/所有者のタグ: log"（例 dynamics/B001SG1: edit D: 2 -> 2.1）を追加します（obj.sct_stale.equilibrium(end+1,1) = log）。消去も、各クラスが自分のフィールドだけを対象に行います。PowerNetwork.handle_edit は slack 母線を 1 つに維持する役割も持ちます。編集のタグには、パラメータの区分（dynamics、powerflow、base、operation、OPF、graph）、Topology、Slack、Tag、input（set_input）があります。

Only PowerNetwork.initialize brings the layers up to date. It solves the operating point (power flow, AC OPF or "FixedInput") when Method is given or powerflow is stale and writes it with Bus.set_equilibrium; then the buses initialize their components (stale handles rebuilt with set_odefcn, a stale equilibrium recomputed from the held V and I) and those their local controllers, and the global controllers come last. Each layer decides from its own fields; the network decides only about its own power flow and clears its fields at the end. The analyses only check: each reads, inline and in the loops it already has, the stale tags it needs (sct_stale has public GetAccess) and changes nothing. A network Hz edit reaches no child: it marks the network odefcn, which every analysis reads; in initialize each component and controller rebuilds its handles when its odefcn is not empty or the frequency it built them with (r_odefcnHz) differs from get_Hz().

層を最新にするのは PowerNetwork.initialize だけです。Method の指定時か powerflow が古いときに運転点（潮流計算、AC OPF、"FixedInput"）を解き、Bus.set_equilibrium で書き込みます。続いて母線が機器を、機器がローカル制御器を初期化し（古いハンドルは set_odefcn で再構築、古い平衡点は保持中の V と I から再計算）、グローバル制御器は最後に初期化します。各層が自分のフィールドから判断し、ネットワークが判断するのは自分の潮流だけで、最後に自分のフィールドを消去します。解析は確認だけを行います。各解析は、必要な stale タグ（sct_stale、GetAccess は public）を既存のループの中でその場で読み取り、何も変更しません。ネットワークの Hz の編集はどの子にも届きません。ネットワークの odefcn に記録し、どの解析もそれを読み取ります。initialize では各機器・制御器が、自分の odefcn が空でないか、ハンドル作成時の周波数（r_odefcnHz）が get_Hz() と異なれば、ハンドルを再構築します。

net.get_variable_map() が、モデル変数の順序、信号、それらの間の接続の唯一の定義です。

  • Each layer with a linear model has its own map, the restriction of the map of the network: bus.get_variable_map(), comp.get_variable_map(), and for a controller con.get_variable_map() (its x, the voltages it reads, its uc and yc). The leading variable rows of each map are the order of the point of its get_sys.線形モデルを持つ各階層は、ネットワークのマップを絞った自分のマップを持ちます。bus.get_variable_map()、comp.get_variable_map()、制御器では con.get_variable_map()（自分の x、読み取る電圧、uc と yc）です。各マップの先頭の変数の行が、その get_sys の点の順序です
  • The column Equilibrium holds the value of each row at the equilibrium set by net.initialize (outputs evaluated there); it is NaN before the first initialization. Only the table form computes it; the internal "rows" form does not.Equilibrium 列は、net.initialize が求めた平衡点での各行の値です（出力はそこで評価した値）。最初の初期化の前は NaN です。表の形だけが計算し、内部用の "rows" 形式は計算しません

Optional analyses (Hessians)任意対応の解析（ヘッセ行列）

An analysis that only some models support is a method on the base class with a per-class contract, as get_hessian on Component, LocalController, and GlobalController.

一部のモデルだけが対応する解析は、クラスごとの契約を持つ基底クラスのメソッドにします。例: Component、LocalController、GlobalController の get_hessian です。

The class supports itクラスが対応している場合

It defines static Hessian_dx (required), Hessian_I, and Hessian_Y with the arguments of Jacobi_*. Each returns n_eq × n_z × n_z with z = [x; V; u] (z = [x; V] for Hessian_Y of a component).

Jacobi_* と同じ引数の静的メソッド Hessian_dx（必須）、Hessian_I、Hessian_Y を定義します。それぞれ z = [x; V; u]（機器の Hessian_Y は z = [x; V]）について n_eq × n_z × n_z を返します。

The class does notクラスが対応していない場合

The base method stops with GUILDA:<Layer>:HessianNotSupported, which names the class.

基底クラスのメソッドが、クラス名を示す GUILDA:<Layer>:HessianNotSupported で停止します。

Each class supplies its own derivatives. No symbolic differentiation, so the Symbolic Math Toolbox is not required.

導関数は各クラスが提供します。記号微分は使わないため、Symbolic Math Toolbox は不要です。

OPF customizationOPF のカスタマイズ

The model objects hold only parameters; no OPF state lives on a bus, component, or branch. As for the power flow, the network assembles the data: calculate_optimal_powerflow and build_opf_problem collect tab_parameter into three tables of the buses, components and branches (tags as row names; net.get_opf_condition, which stacks Bus.get_opf_condition and Branch.get_opf_condition, the same tables the user can print), with the base and the reference bus, and SolverOPF.build_problem builds one optimproblem from these data only; the solver never reads a model object. The dynamics keep cached f_* handles on the classes because several analyses (simulate, get_sys) reuse them.

モデルのオブジェクトはパラメータだけを保持し、母線・機器・ブランチは OPF の状態を持ちません。潮流計算と同じく、データはネットワークが組み立てます。calculate_optimal_powerflow と build_opf_problem が tab_parameter を母線・機器・ブランチの 3 つの表（行名はタグ。Bus.get_opf_condition と Branch.get_opf_condition を積み重ねる net.get_opf_condition で、利用者が表示する表と同じです）にまとめ、基準値と基準母線とともに渡します。SolverOPF.build_problem はこのデータだけから 1 つの optimproblem を構築し、モデルのオブジェクトは読みません。動特性は複数の解析（simulate、get_sys）が再利用するため、キャッシュした f_* ハンドルをクラスに保持します。

Coding conventions of the classesクラス実装の規約

Topic対象の項目Convention規約
Errors and warningsエラーと警告
  • Errors: error(msg("GUILDA:<Object>:<Key>", arg1, ...)), with msg as the only argument.エラーは error(msg("GUILDA:<Object>:<Key>", arg1, ...)) の形で出します。msg が唯一の引数です
  • Warnings: show_msg("warning", "GUILDA:<Object>:<Key>", arg1, ...); INFO messages: show_msg("info", "GUILDA:<Object>:<Key>", arg1, ...), which prints INFO: before the text (do not write it in the XML). The settings Message.ShowWarning and Message.ShowInfo hide them; no disp or warning of GUILDA text without show_msg.警告は show_msg("warning", "GUILDA:<Object>:<Key>", arg1, ...)、INFO メッセージは show_msg("info", "GUILDA:<Object>:<Key>", arg1, ...) で出します。INFO: は show_msg が付けるため、XML には書きません。設定 Message.ShowWarning、Message.ShowInfo で非表示にできます。GUILDA の文を show_msg を通さずに disp や warning で出してはいけません
  • <Object>: the class folder or the file that calls msg or show_msg; a function in private/ or in a package uses its file name. A method of a subclass may also use the IDs of its superclass (e.g. component.generator.abstract uses GUILDA:Component:*).<Object> には、msg または show_msg を呼ぶクラスのフォルダ名またはファイル名を使います。private/ やパッケージ内の関数では、そのファイル名を使います。サブクラスのメソッドはスーパークラスの ID も使えます（例: component.generator.abstract が GUILDA:Component:* を使用）
  • Text: English, in SystemTools/GUILDA/en/<Object>.xml, whose <rsccat version> is the current GUILDA version.メッセージは英語で書き、SystemTools/GUILDA/en/<Object>.xml に置きます。その <rsccat version> は現在の GUILDA のバージョンです
  • Placeholders: pass numbers as text (e.g. string(n)) and give each placeholder its own number; with placeholders, write '' for a single quote and '{' for a brace.プレースホルダーには数値を文字列で渡し（例: string(n)）、それぞれ別の番号にします。プレースホルダーがある場合、一重引用符は ''、波かっこは '{' と書きます
  • Identifiers: a warning from show_msg has the identifier GUILDA:<Object>:<Key>, so lastwarn returns it and warning("off", id) turns it off. An error from error(msg(...)) has no identifier: ME.identifier is empty. MException keeps its own identifier.show_msg の警告の識別子は GUILDA:<Object>:<Key> です。lastwarn で取得でき、warning("off", id) で無効化できます。error(msg(...)) のエラーには識別子がありません（ME.identifier は空）。MException は独自の識別子を保持します

  • Voltages, currents, powers (P, Q), and branch constants (R, X, C): per unit on the system base (the system baseMVA on PowerNetwork).電圧、電流、電力（P、Q）、ブランチの定数（R、X、C）は、システム基準（PowerNetwork にあるシステムの baseMVA）の単位法で表します

Time and frequency時間と周波数
  • Time t: seconds.時間 t: 秒
  • Nominal frequency Hz: a system base value on PowerNetwork; models read it with get_Hz().定格周波数 Hz は、PowerNetwork にあるシステムの基準値です。モデルは get_Hz() で読みます
  • Argument omega0 passed to models: this nominal frequency in Hz; models multiply by 2π themselves (e.g. ddelta = 2*pi*omega0*omega).モデルに渡す引数 omega0 は、Hz 単位のこの定格周波数です。2π はモデル自身が掛けます（例: ddelta = 2*pi*omega0*omega）

Current direction電流の向き
  • A component's current I is the current it injects into its bus, so P + jQ = V·conj(I) is positive for generation.機器の電流 I は、機器が母線に注入する電流です。P + jQ = V·conj(I) は発電で正になります
  • A load has negative injection (e.g. impedance load I = -V/Z).負荷の注入は負になります（例: インピーダンス負荷 I = -V/Z）
  • Network equation: I_bus = Y·V, where I_bus is the sum of the injections at each bus.ネットワーク方程式は I_bus = Y·V です。I_bus は各母線での注入の和です
Complex vs [real; imag]複素数と [real; imag]
  • Complex numbers: stored equilibria and power-flow results (c_*, cv_*), admittance matrices, and the inputs of get_equilibrium(V, I, P, Q).保存される平衡点と潮流計算の結果（c_*、cv_*）、アドミタンス行列、get_equilibrium(V, I, P, Q) の入力は複素数です
  • Real 2×1 vectors [re; im]: V passed to fcn_* and Jacobi_*, and the state vector of the simulator. Inside a model, convert with [1, 1j]*V.fcn_* と Jacobi_* に渡される V と、シミュレータの状態ベクトルは、実数の 2×1 ベクトル [re; im] です。モデル内では [1, 1j]*V で変換します
  • fcn_I returns a complex scalar.fcn_I の返り値は複素数のスカラー
The ports of a linearized component or bus are [Vre; Vim] to [Ire; Iim].近似線形化した機器や母線のポートは、[Vre; Vim] から [Ire; Iim] へ向かいます。
