How the model classes relate as a whole, and the rules across them: ownership, parent references, identity, settings, edits, variable order. What one class owns and does: on its Reference page. Read before adding a property or a method to a model class.モデルクラス全体の関係と、クラスをまたぐルール（所有、親への参照、識別、設定、編集、変数の順序）。1つのクラスが所有するもの・行う処理は、各クラスのリファレンスページ。モデルクラスへのプロパティ・メソッド追加の前に一読。

The class structure is stable on purpose: other developers build on it. These rules decide where data and logic go inside the existing classes, instead of adding new classes. They apply to all code in GUILDA.クラス構成は意図的に固定。ほかの開発者がその上に開発を重ねるため。ここでのルールは、新しいクラスの導入ではなく、既存クラスの中でのデータとロジックの置き場所を決めるもの。GUILDA のすべてのコードに適用。

Design principles設計原則

  1. No data is held by two classes同じデータを2つのクラスで持たない

    Each value has a single owner. Anything derived from it is a Dependent property that reads the owner on access. Do not write code that copies a value and keeps the copies in sync: it is a source of bugs.

    各値の所有者は1つ。導出できるものは、アクセス時に所有者を読む Dependent プロパティに。値をコピーしてコピー同士を同期させるコードはバグの原因のため禁止。

    Examples: PowerNetwork.cv_Vequilibrium / cv_Iequilibrium / rv_Xequilibrium (collected from the buses), Branch.cv_Vequilibrium / cv_Iequilibrium (from the end buses and its own admittance), Component.tab_parameter (assembled from the Parameter objects), Component.rv_Xequilibrium_all (the component plus its controllers).

    例: PowerNetwork.cv_Vequilibrium / cv_Iequilibrium / rv_Xequilibrium（母線から収集）、Branch.cv_Vequilibrium / cv_Iequilibrium（両端の母線と自身のアドミタンスから計算）、Component.tab_parameter（Parameter オブジェクトから組み立て）、Component.rv_Xequilibrium_all（機器とその制御器）。

  2. Data and functions follow real-world rolesデータと機能は現実の役割に従う

    A class holds what the physical element has and computes what the physical element determines:

    クラスは、物理的な要素が持つものを保持し、要素が決めるものを計算。

    • Branch: its impedances; builds its own admittance matrix.ブランチ: 自身のインピーダンスを保持し、自身のアドミタンス行列を作成
    • Bus: the algebraic variable, its voltage V.母線: 代数変数である電圧 V
    • Components and controllers: the differential equations and output equations.機器・制御器: 微分方程式と出力方程式
  3. Same method name, same meaning on every layer同じメソッド名は、どの階層でも同じ意味

    Same meaning and same shape of inputs and outputs on every class. A higher layer aggregates the lower ones.

    どのクラスでも同じ意味、同じ入出力の形。上位の階層が下位の階層を集約。

    • get_sys: the linearized model of each layer.get_sys: 各階層の近似線形化モデル
      • LocalController: the controller alone.LocalController: 制御器単体
      • Component: the component and its controllers.Component: 機器とその制御器
      • Bus: the aggregate of its components.Bus: その機器の集約
      • PowerNetwork: the whole system.PowerNetwork: システム全体
      • On LocalController, Component, and Bus: input, state, and output names are unique, and states are not outputs. An output with the name of a state of its owner is labelled Y_ + name.LocalController・Component・Bus: 入力・状態・出力の名前は一意、状態は出力に含めない。所有者の状態と同じ名前の出力のラベルは Y_ + 名前
      • Inputs, states, and outputs of each layer: on the get_sys method page of each class in the Reference.各階層の入力・状態・出力: リファレンスの各クラスの get_sys のページ
    • get_admittance_matrix: on Branch, its 2×2 matrix; on PowerNetwork, the matrix of the whole network.get_admittance_matrix: Branch では自身の 2×2 行列、PowerNetwork ではネットワーク全体の行列
    • get_variable_map: on Component and Bus, the rows of the network map that belong to it, in the same relative order (see Variable order).get_variable_map: Component と Bus では、ネットワークの変数マップのうち自身に属する行（同じ相対順序。変数の順序を参照）
    • build_opf_problem and set_opffcn: each class adds its own variables, cost, and constraints; PowerNetwork collects them.build_opf_problem と set_opffcn: 各クラスが自身の変数・コスト・制約を追加し、PowerNetwork が集約
  4. Edits only record; analyses check編集は記録するだけ、確認は解析が行う

    Editing a parameter or a mode only updates the value and records what became stale; nothing is rebuilt per edit. An analysis checks the flags when it starts (see Edit handling).

    パラメータやモードの編集は、値の更新と、古くなったものの記録のみ。編集ごとの再構築なし。フラグの確認は解析の開始時（モデル編集の扱いを参照）。

Components and controllers機器と制御器

Controllers keep their own contract, different from Component on purpose. A component outputs the current I to the network and exposes its outputs Y and states x to its controllers; a controller only outputs inputs u for the component. Every connection is made by name.

制御器は、意図的に Component と異なる独自の契約。機器はネットワークへ電流 I を出力し、出力 Y と状態 x を制御器に公開。制御器の出力は機器への入力 u のみ。接続はすべて名前で。

  • Observing. A local controller reads the component it is attached to (for a PSS under an AVR, the component above them) by the names of its inputs sv_u:観測: ローカル制御器は、接続先の機器（AVR の下の PSS では、その上の機器）を入力名 sv_u で読む
    • A name in the component's sv_y reads that output; otherwise a name in its sv_x reads that state. When both have the name, the output wins.機器の sv_y にある名前はその出力、なければ sv_x にある名前はその状態。両方にあれば出力が優先
    • The reserved input names Xall and Yall observe all the states and all the outputs of the component.予約された入力名 Xall・Yall: 機器のすべての状態・すべての出力を観測
    • X and Y are not reserved: an input with either name is an error.X と Y は予約名ではない。どちらかの名前の入力はエラー
    • An input with the name of an output of a nested controller (for example Vpss) reads that output; any other input stays at its equilibrium.入れ子の制御器の出力と同じ名前の入力（例: Vpss）はその出力を読む。それ以外の入力は平衡点の値のまま
    • A global controller reads the states x of the components it controls, by the names of its inputs sv_u.グローバル制御器: 制御する機器の状態 x を入力名 sv_u で読む
  • Driving.駆動
    • The outputs sv_y of a controller drive the inputs of the same name of the component, or of the controller above it.制御器の出力 sv_y が、機器またはその上の制御器の同じ名前の入力を駆動
    • A component has two top-level controllers at most, the AVR or "local" controller and the governor, and they drive different inputs (for example Vfield and Pmech).機器の最上位の制御器は高々2つ: AVR または "local" の制御器とガバナ。駆動する入力は別々（例: Vfield と Pmech）
    • An input disturbance of a scenario or a global controller on such an input of the component adds to the output of the local controller, in the simulation and in get_sys.機器のそのような入力へのシナリオの入力外乱やグローバル制御器は、ローカル制御器の出力に加算（シミュレーションでも get_sys でも）

  • Data: iv_odeX / iv_odeI / iv_odeU / iv_odeY, lv_odeUfromLC / iv_odeYtoU, l_isFault, rv_Xoffset / rv_Uoffset, l_isConnect of components and global controllers, iv_CPFV / iv_CPFX / f_PQ2Bus.対象: iv_odeX / iv_odeI / iv_odeU / iv_odeY、lv_odeUfromLC / iv_odeYtoU、l_isFault、rv_Xoffset / rv_Uoffset、機器とグローバル制御器の l_isConnect、iv_CPFV / iv_CPFX / f_PQ2Bus

  • Exceptions: SolverODE and Component may write iv_ode* of buses and components and Component.lv_odeUfromLC; Component may also write its own l_isConnect.例外: 母線と機器の iv_ode* と Component.lv_odeUfromLC は SolverODE と Component も書き込み可。Component は自身の l_isConnect にも書き込み可
  • Restricted for reading too: Bus.l_isFault, Component.l_isConnect.読み取りも制限: Bus.l_isFault、Component.l_isConnect
  • What a simulation restores: API Design: Side effects.シミュレーションが元に戻すもの: API 設計: 副作用

Parent references親への参照

Each child keeps a read-only reference to its parent: Bus.a_PowerNetwork, Branch.a_PowerNetwork, Component.a_Bus, LocalController.a_Component, GlobalController.a_PowerNetwork, Scenario.a_PowerNetwork, and the parent of each Parameter. Rules:

各子は親への読み取り専用の参照を保持: Bus.a_PowerNetwork、Branch.a_PowerNetwork、Component.a_Bus、LocalController.a_Component、GlobalController.a_PowerNetwork、Scenario.a_PowerNetwork、各 Parameter の親。ルールは次のとおり。

  1. Only the parent sets and clears it設定と解除は親だけが行う

    Set by the parent's constructor or add_* method, cleared by its remove_* method, so a removed object has no parent reference. No other code writes it.

    親のコンストラクタまたは add_* メソッドが設定し、remove_* メソッドが解除。削除されたオブジェクトは親を参照しない。ほかのコードからの書き込みなし。

  2. A child only reads its parent子は親を読むだけ

    For the tag path, for edit notification, and for shared settings such as the frequency.

    タグのパス、編集の通知、周波数などの共有設定のため。

  3. A child never writes upward or sideways子は上にも横にも書き込まない

    No writes to its parent or siblings, and no copy of its parent's data. Edits travel upward only as a call: log_edit calls the hook handle_edit on each layer from the edited one up to the top, and each layer changes only its own state (the owner of a Parameter marks its own handle cache stale, s_odefcn = "editted").

    親や兄弟への書き込みなし、親のデータのコピーも持たない。編集は呼び出しとしてだけ上へ伝達: log_edit が編集した層から最上位までの各層のフック handle_edit を呼び出し、各層は自分の状態だけを変更（Parameter の所有者は自分のハンドルキャッシュを古いと印付け、s_odefcn = "editted"）。

Identifying objects: tags, not indicesオブジェクトの識別: インデックスではなくタグ

Tag (e.g. B001)タグ（例: B001）

The permanent ID of an object. Use it in saved data and in scenarios: a disturbance names its buses, branches, and units by tag, checked against the network when it is added and again when it is simulated.

オブジェクトの恒久的な ID。保存するデータとシナリオで使用。外乱は母線・ブランチ・機器をタグで指定し、外乱の追加時とシミュレーション時にネットワークと照合。

Index (e.g. net.a_Bus{3})インデックス（例: net.a_Bus{3}）

Only the current position. It shifts after remove_*, so never store it.

現在の位置にすぎない。remove_* の後にずれるため、保存しない。

  • Automatic tag: the largest number in use plus one (buses B###, branches ###, components per bus).自動で付くタグ: 使用中の最大の番号 + 1（母線は B###、ブランチは ###、機器は母線ごと）
  • A number is not reused while a larger one exists, so a new tag never names an existing or earlier object.より大きい番号が存在する間は番号を再利用しない。新しいタグが既存または過去のオブジェクトを指すことはない
  • Global controller tag: chosen by the user, and must be unique.グローバル制御器のタグ: ユーザーが選択。一意であること

Solver settings of analyses解析のソルバー設定

Persistent defaults: net.solver_*永続的な既定値: net.solver_*

The solver objects hold the default settings of each analysis. A change made there stays, so repeated runs keep the last settings.

ソルバーオブジェクトが各解析の既定の設定を保持。ここでの変更は残るため、繰り返し実行しても最後の設定を維持。

Run-time Name-Value options実行時の Name-Value オプション

Override the defaults for that call only. The stored defaults do not change.

その呼び出しに限り既定値を上書き。保存されている既定値は不変。

System data (line constants, power-flow specifications, limits) is not a solver setting: set it beforehand on the model objects through properties and tab_parameter (see API Design, rule 2).

系統データ（線路定数、潮流計算の指定値、制限値）はソルバーの設定ではない。プロパティと tab_parameter を通じて、事前にモデルオブジェクトに設定（API 設計のルール 2 を参照）。

Handling of model editsモデル編集の扱い

Edits are recorded in the edit log, which LayerPackage owns and keeps generic: each layer appends its own edits (those of a Parameter container on its owner) to the struct array sct_editLog once l_initialized is true, and disp_edit of a layer shows the edits of the layer and its subtree in edit order (net.disp_edit(): the whole network; bus.disp_edit(): the bus, its components and their controllers; with an output argument it returns the table). reset_edit clears the edits of a subtree and sets l_initialized: true at the end of initialize, false on an attach to a new parent. A removed layer takes its edits with it (the removal is a row of the parent). After storing a row, log_edit calls the hook handle_edit on every layer up to the top; LayerPackage knows nothing of what an edit makes stale. That belongs to PowerSystemModel: edit_effect maps the tag of an edit to the handles and the equilibrium, handle_edit marks the owner's handle cache stale (s_odefcn), and PowerNetwork.handle_edit keeps one slack bus and marks every handle cache on a network Hz edit. Whether the equilibrium is stale (net.l_staleEquilibrium) is read from the network's edit log when an analysis asks for it.

編集の記録先は LayerPackage が持つ汎用の編集ログ。l_initialized が true の層は自分の編集（Parameter コンテナの編集は所有者）を struct 配列 sct_editLog に追加し、層の disp_edit はその層と下の層の編集を編集順に表示（net.disp_edit(): ネットワーク全体、bus.disp_edit(): その母線と機器・制御器。出力引数があれば表を返す）。reset_edit は部分木の編集を消去して l_initialized を設定（initialize の最後に true、新しい親への接続で false）。削除した層は自分の編集を持ち去り（削除は親の行）。log_edit は行の記録後、最上位までの各層のフック handle_edit を呼び出し、何が古くなるかを LayerPackage は扱わない。それは PowerSystemModel の担当: edit_effect が編集のタグからハンドルと平衡点への影響を判定、handle_edit が所有者のハンドルキャッシュを古いと印付け（s_odefcn）、PowerNetwork.handle_edit が slack 母線を 1 つに保ち、ネットワークの Hz の編集ですべてのハンドルキャッシュを印付け。平衡点が古いかどうか（net.l_staleEquilibrium）は解析が求めたときにネットワークの編集ログから判定。

When an analysis starts:

解析の開始時:

  • Function handles that are not up to date are built automatically, for the affected components and controllers only. The constructor does not build them. Attaching a component to a bus or a controller to its parent marks the handles of that subtree as stale, because the network frequency they read may change.最新でない関数ハンドルは、影響を受ける機器と制御器についてのみ自動で作成。コンストラクタは作成しない。機器を母線に、制御器を親に接続すると、その部分木のハンドルを古いと印付け（ハンドルが読むネットワークの周波数が変わり得るため）
  • If the equilibrium is stale, simulate, linearize, and get_sys stop with GUILDA:PowerNetwork:EquilibriumStale, which names the edits and says to run net.initialize() first (see API Design, rule 5).平衡点が古い場合、simulate、linearize、get_sys は GUILDA:PowerNetwork:EquilibriumStale で停止。メッセージは原因の編集を示し、先に net.initialize() の実行を促す（API 設計のルール 5 を参照）
  • The check is part of each solver's solve (solver_ODE, solver_LIN), so calling a solver directly checks it too.この確認は各ソルバーの solve（solver_ODE、solver_LIN）の一部。ソルバーを直接呼び出しても確認

Order of state and input variables状態・入力変数の順序

net.get_variable_map() is the single definition of the order of the model variables.

net.get_variable_map() がモデル変数の順序の唯一の定義。

  • Used by every analysis that lists variables: the Jacobian blocks of a linearization, the Point option, simulation results. Do not define another order.変数を並べるすべての解析が使用: 近似線形化のヤコビ行列のブロック、Point オプション、シミュレーション結果。別の順序の定義は禁止
  • The one exception is the state order of get_ss and get_sys: "Kron" and "DAE" put the states of the global controllers first, and "Feedback" puts them last.唯一の例外は get_ss と get_sys の状態の順序: "Kron" と "DAE" はグローバル制御器の状態が先頭、"Feedback" は末尾
Variable block変数のブロックOrder順序
1. states x1. 状態 xFor each bus, for each component: the component's states, then its local controllers' states (depth first: the AVR or "local" controller, the PSS under the AVR, then the governor, whatever the order of attachment). Then the states of each global controller.母線ごと、機器ごとに、機器の状態、続いてそのローカル制御器の状態（深さ優先: AVR または "local" の制御器、AVR の下の PSS、ガバナの順。接続した順序によらない）。その後に各グローバル制御器の状態。
2. bus voltages2. 母線電圧Vre, Vim of each bus, interleaved per bus.各母線の Vre、Vim。母線ごとに交互に配置。
3. inputs u3. 入力 uFor each bus, for each component: its inputs.母線ごと、機器ごとに、その入力。
  • The Label column of the map equals the state and input names of get_sys: find a variable by its label, not by its position.マップの Label 列 = get_sys の状態名・入力名。変数は位置ではなくラベルで検索
  • The bus variables of "DAE" have their own numbered names (such as theta1); "Feedback" can have fewer states because its connection removes some."DAE" の母線変数は独自の番号付きの名前（theta1 など）。"Feedback" は接続で一部の状態が消えるため、状態が少ない場合あり
  • net.linearize(Point=x) linearizes at any state x given in this order, or at a time of a simulation result (Point={sim, t}).net.linearize(Point=x): この順序で与えた任意の状態 x、またはシミュレーション結果のある時刻（Point={sim, t}）で近似線形化

Optional analyses (Hessians)任意対応の解析（ヘッセ行列）

An analysis that only some models support is a method on the base class with a per-class contract, as get_hessian on Component, LocalController, and GlobalController.

一部のモデルだけが対応する解析は、クラスごとの契約を持つ基底クラスのメソッドに。例: Component、LocalController、GlobalController の get_hessian。

The class supports itクラスが対応している場合

It defines static Hessian_dx (required), Hessian_I, and Hessian_Y with the arguments of Jacobi_*. Each returns n_eq × n_z × n_z with z = [x; V; I; u].

Jacobi_* と同じ引数の静的メソッド Hessian_dx（必須）、Hessian_I、Hessian_Y を定義。それぞれ z = [x; V; I; u] について n_eq × n_z × n_z を返す。

The class does notクラスが対応していない場合

The base method stops with GUILDA:<Layer>:HessianNotSupported, which names the class.

基底クラスのメソッドが、クラス名を示す GUILDA:<Layer>:HessianNotSupported で停止。

Each class supplies its own derivatives. No symbolic differentiation, so the Symbolic Math Toolbox is not required.

導関数は各クラスが提供。記号微分は使わないため、Symbolic Math Toolbox は不要。

Each object holds its own OPF terms, set with obj.set_opffcn("Cost", @(v,p) ..., "Constraint", @(v,p) struct(...), "DefaultConstraint", false) and restored with obj.reset_opffcn(). v: the object's optimization variables; p: its parameters.

各オブジェクトが自身の OPF 項を保持。設定は obj.set_opffcn("Cost", @(v,p) ..., "Constraint", @(v,p) struct(...), "DefaultConstraint", false)、元に戻すのは obj.reset_opffcn()。v はオブジェクトの最適化変数、p はそのパラメータ。

OPF termOPF の項Effect効果
CostReplaces the default cost of the object.オブジェクトの既定のコストを置換。
ConstraintAdded to the default constraints. Each field name labels the constraint and its dual in result.lambda.Constraints.既定の制約に追加。各フィールド名が、result.lambda.Constraints での制約とその双対変数のラベル。
DefaultConstraintfalseRemoves the object's default constraints (e.g. the bounds of a component). The bus power balance always stays.オブジェクトの既定の制約（例: 機器の上下限）を除去。母線の電力バランスは常に残る。
network levelネットワーク全体net.set_opffcn takes terms over several objects; its v reaches each object's variables by tag (e.g. v.Component.(tag).P).net.set_opffcn は複数のオブジェクトにまたがる項を受け取る。その v から各オブジェクトの変数にタグでアクセス（例: v.Component.(tag).P）。

Coding conventions of the classesクラス実装の規約

Topic対象の項目Convention規約
Errors and warningsエラーと警告
  • Write error(msg("GUILDA:<Object>:<Key>", arg1, ...)) and warning(msg("GUILDA:<Object>:<Key>", arg1, ...)), with msg as the only argument.error(msg("GUILDA:<Object>:<Key>", arg1, ...)) と warning(msg("GUILDA:<Object>:<Key>", arg1, ...)) の形。msg が唯一の引数
  • <Object>: the class folder or the file that calls msg; a function in private/ or in a package uses its file name.<Object>: msg を呼ぶクラスのフォルダまたはファイル。private/ やパッケージ内の関数はそのファイル名
  • Text: English, in SystemTools/GUILDA/en/<Object>.xml, whose <rsccat version> is the current GUILDA version.メッセージ: 英語、SystemTools/GUILDA/en/<Object>.xml に配置。その <rsccat version> は現在の GUILDA のバージョン
  • Placeholders: pass numbers as text (e.g. string(n)) and give each placeholder its own number; with placeholders, write '' for a single quote and '{' for a brace.プレースホルダー: 数値は文字列で渡し（例: string(n)）、それぞれ別の番号。プレースホルダーがある場合、一重引用符は ''、波かっこは '{'
  • No MATLAB identifier: GUILDA:<Object>:<Key> names the XML entry, so ME.identifier and warning("off", id) cannot select them. MException keeps its own identifier.MATLAB の識別子なし: GUILDA:<Object>:<Key> は XML のエントリを指す名前のため、ME.identifier や warning("off", id) では選択不可。MException は独自の識別子を保持
Per-unit system単位法
  • Voltages, currents, powers (P, Q), and branch constants (R, X, C): per unit on the system base (the system baseMVA on PowerNetwork).電圧、電流、電力（P、Q）、ブランチの定数（R、X、C）: システム基準（PowerNetwork にあるシステムの baseMVA）の単位法
  • Component dynamics parameters: also per unit on the system base.機器の動特性パラメータ: 同じくシステム基準の単位法
  • Component.baseMVA: the machine rating, used only to share reactive power.Component.baseMVA: 機器の定格。無効電力の分担にのみ使用
  • No class converts physical units: Bus.baseKV is stored but not used in any calculation.物理単位を換算するクラスなし。Bus.baseKV は保存のみで、計算には不使用
Angles角度 Radians: bus angle Varg / Varg0, branch phase, rotor angle. Degrees appear only in labels of the network diagram.ラジアン: 母線の位相角 Varg / Varg0、ブランチの phase、回転子角。度はネットワーク図のラベルのみ。
Time and frequency時間と周波数
  • Time t: seconds.時間 t: 秒
  • Nominal frequency Hz: a system base value on PowerNetwork; models read it with get_Hz().定格周波数 Hz: PowerNetwork にあるシステムの基準値。モデルは get_Hz() で読む
  • Argument omega0 passed to models: this nominal frequency in Hz; models multiply by 2π themselves (e.g. ddelta = 2*pi*omega0*omega).モデルに渡す引数 omega0: Hz 単位のこの定格周波数。2π はモデル自身が乗算（例: ddelta = 2*pi*omega0*omega）
  • Rotor speed omega: a per-unit deviation.回転子速度 omega: 単位法の偏差
Current direction電流の向き
  • A component's current I is the current it injects into its bus, so P + jQ = V·conj(I) is positive for generation.機器の電流 I: 機器が母線に注入する電流。P + jQ = V·conj(I) は発電で正
  • A load has negative injection (e.g. impedance load I = -V/Z).負荷の注入は負（例: インピーダンス負荷 I = -V/Z）
  • Network equation: I_bus = Y·V, where I_bus is the sum of the injections at each bus.ネットワーク方程式: I_bus = Y·V。I_bus は各母線での注入の和
Complex vs [real; imag]複素数と [real; imag]
  • Complex numbers: stored equilibria and power-flow results (c_*, cv_*), admittance matrices, and the inputs of get_equilibrium(V, I, P, Q).複素数: 保存される平衡点と潮流計算の結果（c_*、cv_*）、アドミタンス行列、get_equilibrium(V, I, P, Q) の入力
  • Real 2×1 vectors [re; im]: V and I passed to fcn_* and Jacobi_*, and the state vector of the simulator. Inside a model, convert with [1, 1j]*V.実数の 2×1 ベクトル [re; im]: fcn_* と Jacobi_* に渡される V と I、シミュレータの状態ベクトル。モデル内の変換は [1, 1j]*V
  • fcn_I returns a complex scalar.fcn_I の返り値は複素数のスカラー
The ports of a linearized component or bus are [Vre; Vim] to [Ire; Iim] for port="V2I", and the inverse for port="I2V".近似線形化した機器や母線のポート: port="V2I" では [Vre; Vim] から [Ire; Iim]、port="I2V" ではその逆。

Name new properties with the Naming Conventions, place new classes as described in Folder Structure, and document them with Class Documentation tags.新しいプロパティの命名は命名規則、新しいクラスの配置はフォルダ構成、記述はクラスのドキュメントのタグに従う。
