Optimal Power Flow Feature Design最適潮流計算機能の設計

net.calculate_optimal_powerflow() finds the operating point of least generation cost within the operating limits. SolverOPF reads the parameters of the buses, components, and branches and builds one optimproblem; the Optimization Toolbox solves it. Output: a ResultOPF; the network is unchanged.

net.calculate_optimal_powerflow() は、運用上の制約を守りながら発電コストが最小になる運転点を求めます。SolverOPF が母線、機器、ブランチのパラメータを読み取って 1 つの optimproblem を組み立て、Optimization Toolbox で解きます。結果は ResultOPF として返し、ネットワークには手を加えません。

What the feature does and how to call it機能の目的と呼び出し方

[result, flag, output] = net.calculate_optimal_powerflow(Name=Value, ...)
[prob, x0] = net.build_opf_problem(Name=Value, ..., validate=false)   % the problem only
result = net.calculate_optimal_powerflow(Problem=prob, InitialPoint=x0)       % solve a modified problem
  • Settings: the OptimalPowerFlow section of GUILDA.setting, read at each run from GUILDA.config("OptimalPowerFlow"): @GUILDA/config/DefaultOptimalPowerFlow.json, overridden by a file of the same name in @GUILDA/user/.
  • Conditions Cost, Constraint, DefaultCost, ReferenceBus: the public properties of net.solver_OPF (a SolverOPF), kept between runs.
  • A Name-Value option applies to this call only.
  • 設定は GUILDA.setting の OptimalPowerFlow セクションにあり、実行のたびに GUILDA.config("OptimalPowerFlow") で読み込みます。既定値は @GUILDA/config/DefaultOptimalPowerFlow.json にあり、@GUILDA/user/ に同名のファイルを置くと上書きできます。
  • 条件 Cost、Constraint、DefaultCost、ReferenceBus は net.solver_OPF（SolverOPF）の public プロパティで、実行をまたいで残ります。
  • Name-Value オプションは、その呼び出しにだけ効きます。

Preconditions:

  • the Optimization Toolbox (checked when the analysis starts; also for net.initialize(Method="OPF"));
  • components: tab_parameter.OPF (cost HP·P² + fP·P + HQ·Q² + fQ·Q, initial point P0, Q0) and tab_parameter.operation (limits);
  • buses: operation (Vmin, Vmax) and powerflow (Varg, V: reference angle and flat start);
  • branches: operation (Pmax, Qmax, Imax, Smax, Vargmax).
  • an infinite bound (-Inf / Inf; NaN for the branch limits) adds no limit.

No initialize needed; the stale state is not checked. User terms: Cost, Constraint, Problem (see Class Design: OPF customization).

前提条件は次のとおりです。

  • Optimization Toolbox。解析を始めるときに確認します。net.initialize(Method="OPF") でも同じです。
  • 機器の tab_parameter.OPF と tab_parameter.operation。前者はコスト HP·P² + fP·P + HQ·Q² + fQ·Q と初期点 P0、Q0 を、後者は制約を表します。
  • 母線の operation（Vmin、Vmax）と powerflow。powerflow の Varg と V は、基準位相角とフラットスタートに使います。
  • ブランチの operation（Pmax、Qmax、Imax、Smax、Vargmax）。
  • 上下限を無限大（-Inf / Inf）にすると、その制約はかかりません。ブランチの制約値は NaN でも同じです。

initialize を先に実行する必要はなく、stale 状態も確かめません。独自の項は Cost、Constraint、Problem で加えます（クラス設計: OPF のカスタマイズを参照）。

  4. OPF-04 SolverOPF.solve → SolverOPF.build_problem(net, sct_options)describe; also called by net.build_opf_problem

    What it does処理内容
    • From solve (local cached_problem): the problem kept by the last solve when the network, n_revOPF, the settings, the start and the variable bounds are the same (see Side effects); otherwise build_problem, and the new problem is kept.
    • Writes the OPF settings and the network tree into the problem's Description.
    • Creates optimproblem (minimize, Objective.GenCost = 0).
    • "ELD": starts the single balance const.P = 0.
    • With Problem: builds without Cost and Constraint, only for x0 and the check of OPF-11.
    • Initial bus voltages (local initial_voltage): with sct_options.WarmStart true and the same buses (by object) and n_revTopology, the kept "AC OPF" solution; otherwise the flat start. net.build_opf_problem gives no WarmStart: its x0 is the flat start.
    • solve から呼ばれた場合は、内部関数 cached_problem がキャッシュを調べます。ネットワーク、n_revOPF、設定、初期点、変数の上下限が前回と同じなら、前回の solve で保持した問題をそのまま使います（副作用を参照）。違えば build_problem で組み立て直し、新しい問題を保持します。
    • OPF の設定とネットワークの木構造を、問題の Description に書き込みます。
    • 最小化の optimproblem を作り、Objective.GenCost = 0 から始めます。
    • "ELD" では、需給式を const.P = 0 の 1 本だけ用意します。
    • Problem を指定したときは、Cost と Constraint を入れずに組み立てます。この問題は x0 を作ることと、OPF-11 の確認にだけ使います。
    • 母線の初期電圧は内部関数 initial_voltage で決めます。sct_options.WarmStart が true で、母線（オブジェクトで照合）と n_revTopology が前回と同じなら、保持している "AC OPF" の解を使います。そうでなければフラットスタートです。net.build_opf_problem は WarmStart を渡さないので、その x0 は常にフラットスタートになります。
    What it reads読み取る情報
    tab_parameter (operation, powerflow, OPF) of buses, components, branches; disp_tree母線・機器・ブランチの tab_parameter（operation、powerflow、OPF）、disp_tree
    Returns or changes戻り値・変更する値
    prob, x0, const, sct_var (all variables by name; empty structs at first)prob、x0、const、sct_var（名前ごとの全変数。最初は空の構造体）

  12. OPF-12 SolverOPF.solve → SolverOPF.optimoption(prob, sct_options)check_solver

    What it does処理内容
    • Picks the solver: solvers(prob) for "auto"; a named solver is checked against the problem.
    • Always passes Display from Verbose ("iter" or "none"); the other settings only when they differ from the solver's defaults (NaN: the default).
    • PlotFcn: keys as optimplot<key> (key list: private/plot_keys.m), a handle as it is; with linprog / quadprog a value other than "none" stops with GUILDA:SolverOPF:PlotFcnUnsupported.

Side effects on the model and cachesモデルへの副作用とキャッシュ

  • Network and stale state unchanged.
  • net.solver_OPF keeps (private) the problem and x0 that solve built last, and uses them again while the network (by object), net.n_revOPF (increased by handle_edit for every n_revPF edit, the operation and OPF parameters, tags and Hz), Method, Cost and Constraint (by function handle), DefaultCost, ReferenceBus and the start are unchanged. The variables of an optimproblem are handles, so a bound changed on result.OPFprob would reach the kept problem: their bounds and types are compared before reuse. net.build_opf_problem always builds a new problem.
  • net.solver_OPF keeps (private) the bus voltages of the last solved "AC OPF" (flag > 0) for WarmStart, with the buses and n_revTopology they belong to; not used after a Topology edit; its settings are unchanged.
  • No stale tag is read, no equilibrium needed: runs on a network never initialized or edited since.
  • User terms live in net.solver_OPF (Cost, Constraint, DefaultCost, ReferenceBus), not in the model. Edits of operation and OPF parameters are reported with their group tags and make nothing stale (see Class Design: Handling of model edits).
  • The result keeps a reference to the network, not a copy. Record of the settings of the run: OPFprob.Description.
  • ネットワークと stale 状態は変わりません。
  • net.solver_OPF は、solve が最後に組み立てた問題と x0 を private で保持します。次の値がすべて同じなら、その問題を使い回します。ネットワーク（オブジェクト）、net.n_revOPF、Method、Cost と Constraint（関数ハンドルで比較）、DefaultCost、ReferenceBus、初期点です。net.n_revOPF は、n_revPF が増える編集のほか、operation や OPF のパラメータ、タグ、Hz を編集したときに handle_edit が増やします。optimproblem の変数はハンドルなので、result.OPFprob で上下限を変えると保持した問題にも及びます。そのため、使い回す前に変数の上下限と型を照合します。net.build_opf_problem は毎回新しく組み立てます。
  • net.solver_OPF は WarmStart のために、最後に解けた "AC OPF"（flag > 0）の母線電圧を、対応する母線と n_revTopology と一緒に private で保持します。Topology を編集した後は使いません。設定は変わりません。
  • stale タグは読まず、平衡点も使いません。そのため、初期化していないネットワークや、初期化の後に編集したネットワークでも実行できます。
  • ユーザーが定義した項はモデルに置かず、net.solver_OPF の Cost、Constraint、DefaultCost、ReferenceBus に持たせます。operation と OPF のパラメータを編集すると、その区分のタグで編集として記録されますが、古くなる層はありません（クラス設計: モデル編集の扱いを参照）。
  • 結果はネットワークのコピーではなく参照を持ちます。実行時の設定は OPFprob.Description に残ります。

Failure behavior and result flags失敗時の動作と結果フラグ

An unsolved problem is not an error:

  • flag: the exit flag of solve (an optim.problemdef.ExitFlag such as OptimalSolution, or a number);
  • result.l_success: true only when it is positive; output.message describes the outcome;
  • the tables: built from the last point the solver returned.

Errors stop the call before or during the build:

問題が解けなくてもエラーにはなりません。次のように結果で知らせます。

  • flag は solve の終了フラグです。OptimalSolution などの optim.problemdef.ExitFlag、または数値が入ります。
  • result.l_success は、フラグが正のときだけ true になります。結果の説明は output.message に入ります。
  • 表は、ソルバーが最後に返した点から作ります。
