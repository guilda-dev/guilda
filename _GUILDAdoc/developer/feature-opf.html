Optimal Power Flow Feature Design最適潮流計算機能の設計

net.calculate_optimal_powerflow() finds the operating point of least generation cost within the operating limits. The network collects the parameters of the buses, components, and branches into three tables; SolverOPF builds one optimproblem from these tables without reading the network, and the Optimization Toolbox solves it. Output: a ResultOPF; the network is unchanged.

net.calculate_optimal_powerflow() は、運用上の制約を守りながら発電コストが最小になる運転点を求めます。ネットワークが母線、機器、ブランチのパラメータを 3 つの表にまとめ、SolverOPF はネットワークを読まずにその表から 1 つの optimproblem を組み立て、Optimization Toolbox で解きます。結果は ResultOPF として返し、ネットワークには手を加えません。

What the feature does and how to call it機能の目的と呼び出し方

[result, flag, output] = net.calculate_optimal_powerflow(Name=Value, ...)
[prob, x0] = net.build_opf_problem(Name=Value, ..., validate=false)   % the problem only
result = net.calculate_optimal_powerflow(Problem=prob, InitialPoint=x0)       % solve a modified problem
  • Settings: the OptimalPowerFlow section of GUILDA.setting, read at each run from GUILDA.config("OptimalPowerFlow"): @GUILDA/config/DefaultOptimalPowerFlow.json, overridden by a file of the same name in @GUILDA/user/.
  • Conditions Cost, Constraint, DefaultCost, ReferenceBus: options of the call only (defaults [], [], true, "auto"); nothing is kept in net.solver_OPF (a SolverOPF).
  • Every option is in the arguments block of calculate_optimal_powerflow (and of build_opf_problem, which takes Method, Cost, Constraint, DefaultCost, ReferenceBus, validate). A Name-Value option applies to this call only. The result is written to a file with result.export(...).
  • 設定は GUILDA.setting の OptimalPowerFlow セクションにあり、実行のたびに GUILDA.config("OptimalPowerFlow") で読み込みます。既定値は @GUILDA/config/DefaultOptimalPowerFlow.json にあり、@GUILDA/user/ に同名のファイルを置くと上書きできます。
  • 条件 Cost、Constraint、DefaultCost、ReferenceBus は呼び出しのときだけのオプションで、既定値は []、[]、true、"auto" です。net.solver_OPF（SolverOPF）には何も残りません。
  • オプションはすべて calculate_optimal_powerflow の arguments ブロックにあります（build_opf_problem も同様で、Method、Cost、Constraint、DefaultCost、ReferenceBus、validate を受け取ります）。Name-Value オプションは、その呼び出しにだけ効きます。結果をファイルに書き出すには result.export(...) を使います。

Preconditions:

  • the Optimization Toolbox (checked when the analysis starts; also for net.initialize(Method="OPF"));
  • components: tab_parameter.OPF (cost HP·P² + fP·P + HQ·Q² + fQ·Q, initial point P0, Q0) and tab_parameter.operation (limits);
  • buses: operation (Vmin, Vmax) and powerflow (Varg, V: reference angle and flat start);
  • branches: operation (Pmax, Qmax, Imax, Smax, Vargmax).
  • an infinite bound (-Inf / Inf; NaN for the branch limits) adds no limit.

No initialize needed; the stale state is not checked. User terms: Cost, Constraint, Problem (see Class Design: OPF customization).

前提条件は次のとおりです。

  • Optimization Toolbox。解析を始めるときに確認します。net.initialize(Method="OPF") でも同じです。
  • 機器の tab_parameter.OPF と tab_parameter.operation。前者はコスト HP·P² + fP·P + HQ·Q² + fQ·Q と初期点 P0、Q0 を、後者は制約を表します。
  • 母線の operation（Vmin、Vmax）と powerflow。powerflow の Varg と V は、基準位相角とフラットスタートに使います。
  • ブランチの operation（Pmax、Qmax、Imax、Smax、Vargmax）。
  • 上下限を無限大（-Inf / Inf）にすると、その制約はかかりません。ブランチの制約値は NaN でも同じです。

initialize を先に実行する必要はなく、stale 状態も確かめません。独自の項は Cost、Constraint、Problem で加えます（クラス設計: OPF のカスタマイズを参照）。

Call sequence between classesクラス間の呼び出し順

Processing steps in detail処理ステップの詳細

Private helpers: opf_data in _GUILDAsystem/@PowerNetwork/private/ (the data of the problem); build_bus, build_component, build_branch, apply, variables in _GUILDAsystem/_auxiliary/@SolverOPF/private/; local functions in the file of the calling method (@PowerNetwork/calculate_optimal_powerflow.m, @SolverOPF/solve.m, @SolverOPF/build_problem.m, ...). The classes Bus, Component and Branch only hold the parameters; they have no OPF method. SolverOPF takes rows of the three tables of OPF-02 and never a model object.

非公開の補助関数は、_GUILDAsystem/@PowerNetwork/private/ にある opf_data（問題のデータ）と、_GUILDAsystem/_auxiliary/@SolverOPF/private/ にある build_bus、build_component、build_branch、apply、variables です。それ以外は、呼び出し元のメソッドのファイル（@PowerNetwork/calculate_optimal_powerflow.m、@SolverOPF/solve.m、@SolverOPF/build_problem.m など）にあるローカル関数です。Bus、Component、Branch はパラメータを持つだけで、OPF 用のメソッドはありません。SolverOPF が受け取るのは OPF-02 の 3 つの表の行で、モデルのオブジェクトは受け取りません。

  2. OPF-02 calculate_optimal_powerflow → private/opf_data(net, ReferenceBus)reference_bus, dc_parameters

    What it does処理内容
    • Collects the data of the problem as three tables with the tags as row names, in the order of net.a_Bus (components bus by bus) and net.a_Branch.
    • tab_bus: Vmin, Vmax, Gshunt, Bshunt, Type ("slack", "PV", "PQ"), V, Varg.
    • tab_component: Bus (tag of its bus), HP, fP, HQ, fQ, P0, Q0, Pmin, Pmax, Qmin, Qmax. A load (component.load.abstract) whose two bounds are infinite keeps its power-flow P / Q: both bounds and the start are set to it here.
    • tab_branch: From, To (tags of a_Bus{1}, a_Bus{2}), Y (2×2 admittance matrix), X, tap, phase (tap 1 and phase 0 when absent, NaN, or a zero tap), Pmax, Qmax, Vargmax, Imax, Smax.
    • The base (baseMVA, Hz) of the network becomes sct_options.base (p.base of Cost and Constraint).
    • ReferenceBus "auto" is resolved to the tag of the bus of tools.slack_bus_index, else of the first bus; a tag or "none" is kept as it is.
    • 問題のデータを、タグを行名とする 3 つの表にまとめます。行の順序は net.a_Bus（機器は母線ごと）と net.a_Branch の順です。
    • tab_bus の列は Vmin、Vmax、Gshunt、Bshunt、Type（"slack"、"PV"、"PQ"）、V、Varg です。
    • tab_component の列は Bus（接続先の母線のタグ）、HP、fP、HQ、fQ、P0、Q0、Pmin、Pmax、Qmin、Qmax です。上下限がともに無限大の負荷（component.load.abstract）は潮流計算の P / Q を保つため、ここで上下限と初期値をその値にします。
    • tab_branch の列は From、To（a_Bus{1}、a_Bus{2} のタグ）、Y（2×2 のアドミタンス行列）、X、tap、phase（ないとき、NaN のとき、tap がゼロのときは tap 1、phase 0）、Pmax、Qmax、Vargmax、Imax、Smax です。
    • ネットワークの基準値（baseMVA、Hz）は sct_options.base になります（Cost と Constraint の p.base）。
    • ReferenceBus が "auto" なら、tools.slack_bus_index の母線（なければ最初の母線）のタグに置き換えます。タグと "none" はそのままです。

  4. OPF-04 SolverOPF.solve → SolverOPF.build_problem(tab_bus, tab_component, tab_branch, sct_options)describe, initial_voltage; also called by net.build_opf_problem

    What it does処理内容

    • Writes the three tables (the branch table without Y) into the problem's Description.
    • Creates optimproblem (minimize, Objective.GenCost = 0).
    • "ELD": starts the single balance const.P = 0.
    • With Problem: builds without Cost and Constraint, only for x0 and the check of OPF-11.
    • Initial bus voltages (local initial_voltage): with sct_options.WarmStart true and kept bus tags equal to the row names of tab_bus (same order), the kept "AC OPF" solution; otherwise the flat start from Type, V, Varg of tab_bus. net.build_opf_problem gives no WarmStart: its x0 is the flat start.

    • "ELD" では、需給式を const.P = 0 の 1 本だけ用意します。
    • Problem を指定したときは、Cost と Constraint を入れずに組み立てます。この問題は x0 を作ることと、OPF-11 の確認にだけ使います。

Side effects on the model and cachesモデルへの副作用とキャッシュ

  • Network and stale state unchanged; the network is only read, in OPF-02.
  • No problem is kept: every call of calculate_optimal_powerflow and net.build_opf_problem collects the data (OPF-02) and builds the problem anew.
  • net.solver_OPF keeps (private rm_Vwarm, sv_warmBus) the bus voltages of the last solved "AC OPF" (flag > 0) with their bus tags for WarmStart; they are used only when the bus tags of the next run are the same in the same order. net.reset_solver() discards them. The solver holds no settings and no conditions.
  • No stale tag is read, no equilibrium needed: runs on a network never initialized or edited since.
  • User terms are options of the call (Cost, Constraint, DefaultCost, ReferenceBus), kept neither in net.solver_OPF nor in the model. Edits of operation and OPF parameters are reported with their group tags and make nothing stale (see Class Design: Handling of model edits).
  • The result keeps no reference to the network, only its tag (s_network); a later edit of the network does not change it. Record of the settings of the run: result.options and OPFprob.Description.
  • ネットワークと stale 状態は変わりません。ネットワークは OPF-02 で読むだけです。
  • 問題は保持しません。calculate_optimal_powerflow と net.build_opf_problem は、呼び出しのたびにデータを集め（OPF-02）、問題を組み立て直します。
  • net.solver_OPF は WarmStart のために、最後に解けた "AC OPF"（flag > 0）の母線電圧を、母線のタグと一緒に private（rm_Vwarm、sv_warmBus）で保持します。使うのは、次の実行の母線のタグが同じ順序で一致するときだけです。net.reset_solver() で破棄されます。ソルバーは設定も条件も持ちません。
  • stale タグは読まず、平衡点も使いません。そのため、初期化していないネットワークや、初期化の後に編集したネットワークでも実行できます。
  • ユーザーが定義した項は呼び出しのオプション（Cost、Constraint、DefaultCost、ReferenceBus）で、net.solver_OPF にもモデルにも残りません。operation と OPF のパラメータを編集すると、その区分のタグで編集として記録されますが、古くなる層はありません（クラス設計: モデル編集の扱いを参照）。
  • 結果はネットワークへの参照を持たず、タグ（s_network）だけを持ちます。後でネットワークを編集しても結果は変わりません。実行時の設定は result.options と OPFprob.Description に残ります。

Failure behavior and result flags失敗時の動作と結果フラグ

An unsolved problem is not an error:

  • flag: the exit flag of solve (an optim.problemdef.ExitFlag such as OptimalSolution, or a number);
  • result.l_success: true only when it is positive; output.message describes the outcome;
  • the tables: built from the last point the solver returned.

Errors stop the call before or during the build:

問題が解けなくてもエラーにはなりません。次のように結果で知らせます。

  • flag は solve の終了フラグです。OptimalSolution などの optim.problemdef.ExitFlag、または数値が入ります。
  • result.l_success は、フラグが正のときだけ true になります。結果の説明は output.message に入ります。
  • 表は、ソルバーが最後に返した点から作ります。
