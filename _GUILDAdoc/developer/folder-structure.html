Folder Structure

The role of each top-level folder, how the folders depend on each other, and where a new file goes.

Overview

Top-level folders

@GUILDA/via repository root

Entry point of the toolbox. Running >> GUILDA prepares the environment.

Belongs here
Environment setup, user settings and their shipped defaults, and commands that open the tutorials and this documentation.
Relation
Puts the other code folders on the MATLAB path. Contains no power system modeling or analysis.
_GUILDAsystem/on path

The modeling framework.

Belongs here
Base classes that define what a network, bus, branch, component, and controller are; the classes that perform analysis; general helper functions; compatibility wrappers for old names.
Relation
Depends on no concrete model in _GUILDAobject, so models can be added or removed without touching the framework.
_GUILDAobject/on path

Concrete models that users put into a network.

Belongs here
Model classes, grouped into packages by kind (branch / component / controller / network), with sub-packages for model families that share a base class. A network template is a class folder with data subfolders per element type.
Relation
Every model inherits from a base class in _GUILDAsystem.
_GUILDAtutorial/on path

Learning material for users.

Belongs here
Live scripts that walk through using GUILDA, and reference scripts per model family.
Relation
Uses only the public API of _GUILDAsystem and _GUILDAobject; opened from @GUILDA. Each tutorial is listed in the documentation.
_GUILDAdoc/not on path

This documentation site, viewed in a browser.

Belongs here
Hand-written pages, styles, and lists, plus a class reference generated from the help comments in the MATLAB source.
Relation
Reads the code folders but is never called by them. Opened from @GUILDA.
_GUILDAexport/not on pathGit-ignored

Default output folder for exported data.

Belongs here
Files written by GUILDA's export functions. Nothing hand-written.
Relation
Created on demand; safe to delete.

Inside a class or package folder, a subfolder without an @ or + prefix is not on the path: use it for data or archived code only. A class folder keeps one method per file; a small model may be a single classdef file instead.

Placement rules for new files

What are you adding?Put it in
A new generator, load, branch, or controller model→_GUILDAobject/+<package>/the matching package; make a sub-package when a family of models shares a base class
A new network template→_GUILDAobject/+network/@Name/with bus/, branch/, component/<key>/ data folders
A change to the model framework→_GUILDAsystem/@<CoreClass>/the base class folder being changed
A new analysis or support class→_GUILDAsystem/_auxiliary/@Name/inheriting from the common analysis-support base class
A helper function — used by one class only?→yes<that class>/private/no_GUILDAsystem/+tools/
A renamed or removed public API→_GUILDAsystem/_VersionSupport/a wrapper under the old name
A new tutorial→_GUILDAtutorial/and register it in _GUILDAdoc/database/list_Tutorials.js
Retired code kept for reference→archive/next to the original location (see Legacy)

Generated files — do not edit

These are rewritten by the system. Edit the green source, never the red output.

✎ editin _GUILDAsystem/@Bus/add_component.template
@Bus/replace_component.template
@PowerNetwork/add_branch.template

✕ do not editin _GUILDAsystem/@Bus/add_component.m
@Bus/replace_component.m
@PowerNetwork/add_branch.m
✎ edithelp comments in the MATLAB source
runsGUILDA.doc("update", true)
✕ do not editin _GUILDAdoc/database/list_Classes.js
GUILDAsystem/
GUILDAobject/
✎ changesettings changed by the user
runsGUILDA.setting
✕ do not edit or commit@GUILDA/user/

All outputs above are listed in .gitignore.

Legacy and archived folders

Retired code kept for reference goes into a folder named archive/ next to its original location. Having no @ or + prefix, it stays off the MATLAB path inside class and package folders. Do not use any other name or marker for retired or unfinished code.
